First-run setup lives in `allternit-ai/src/components/onboarding/`. One implementation ships to Desktop, ai.allternit.com (desktop and phone layouts) and the m.allternit.com PWA. The user guide is [First-run setup](/guides/first-run-setup).

## Gating

- **Desktop and ai.allternit.com desktop layout**: `OnboardingGate` in `ShellApp.tsx` asks `setupApi.getConfig()`; `shouldRunWizard()` is `!onboardingComplete`. On failure it keeps the local store state. `OnboardingPortal` renders `OnboardingFlow` full screen.
- **Phone shell** (ai.allternit.com phone layout and the PWA): `PhoneFirstRunGate` wraps `PhoneShell` in `SignedInPhone`. It follows the server flag when the config call answers. When it cannot answer (no computer online to relay it), it runs setup only for an account with no paired computer and no local record, and gives up after 8 seconds, so an existing user is never held on a splash.
- Completing setup on any surface saves `onboardingComplete` for the account; the other surfaces skip it after that.

## Honest outcomes

Every result card and tile tag is computed from what happened:

- **This computer**: tile says Detected only after `probeLocalBackend()` finds an Allternit `/health` JSON response. Pairing uses `runtimeBackendApi.registerManualBackend` only when `NEXT_PUBLIC_ALLTERNIT_RUNTIME_API` is on; otherwise it relies on the Desktop's account runtime id (`window.allternit.auth.getSession().runtimeId`). A browser tab that finds a local engine but cannot pair it says so.
- **Cloud computer**: `listCloudComputers()` and `getHostedEntitlement()`; specs come from the instance. No plan read → error, not "needs a plan".
- **Brains**: connected only when `data.defaultProvider` belongs to the chosen row. Allternit Cloud uses `fetchCloudModelCatalog()`.
- **Subscription brains** (`subs-chatgpt`, `subs-claude`, `subs-kimi`): status from `getSubscriptionStatus()` and `listFabricAccounts()`; ready means enabled and `session_health` ready or degraded. The rail runs `SubscriptionConnect` inline; a ready login becomes the default only after `ensureSubscriptionDisclosure()` resolves true. States reported: checking, no Sessions computer, computer offline, sign-in pending, error, ready.

## Haptic ripple

`firesHaptic(action)` is true only for `choose`. The block-square ripple is keyed by the reducer's `ripple` counter and starts at the picked tile (`rippleOriginFrom`). On the phone a choice also calls `vibrateSend()`. Reduced motion hides the ripple and every loop; state changes stay.

## Connected view

`loadInventory()` reads provider auth, the cloud catalog, runtimes (`useRuntimes`, settled after 6 s), cloud computers, bots (`listAgents` + `findMainBot`), messaging channels (`gatewayApi.listAccounts`, `channel_oauth`), Memory Drive mounts, bot projects, MCP connectors and Subscription Fabric logins. Runtime-backed sources are marked unavailable without making the call when no computer is reachable. `buildConnectedGraph()` marks nodes `new` (this session), `conn`, `inc` (included) or `avail`, caps side groups at four, and always includes a Main bot node.

## Main bot step (Meet your bots)

`MAIN_BOT_STEP_ENABLED` is on: the order is where → style → ai → mainbot → connected (30 progress blocks: 6 · 12 · 18 · 24 · 30). The `mainbot` step renders `MeetYourBotsCard` with `entry="setup"` (see [Meet your bots](/architecture/meet-your-bots)), on desktop, the ai.allternit.com phone layout and `PhoneOnboardingFlow`. Its main-bot page drives the shared picker hook `useBotSetup({ context: 'onboarding' })` (see [Bot setup picker](/architecture/bot-setup-picker)). The card creates nothing until **Start the job**; the step stays optional (Skip and Next both move on). Its done button continues to the connected view.

## Seeing it locally

Run the Vite dev server, clear `allternit-onboarding-storage` and `allternit-platform-mode` from localStorage, and load `/shell`. Abort `/api/onboarding/config` to force the local-store path. For the phone shell, start Vite with `VITE_DEV_AUTH_BYPASS=1` and use phone emulation on `/`.

## Your own server on web and phone

`ServerPairPanel` (`src/components/onboarding/setup/ServerPairPanel.tsx`) handles **Your own server** wherever the local runtime API is off (hosted web, phone layout, PWA). It snapshots `listPairedComputers()`, calls `createPairingCode()` (cloud `POST /api/v1/computers/pairing-codes`), shows the command, and polls the paired list every 4 s until a new computer id appears (outcome `paired`), the code expires (`error`), or the request fails (`error`). Desktop keeps the SSH and backend-URL forms. `NEXT_PUBLIC_ALLTERNIT_RUNTIME_API` stays off on the hosted build: it would also enable budget, prewarm, replay and runtime-settings calls that only a paired runtime can answer.
