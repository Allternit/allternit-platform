**Contract v1 draft; the build is in progress.** Nothing on this page ships today. The wire shapes live in `spec/Contracts/os/v1`.

## The rule

The model is the shell. Deterministic code is the kernel. The model decides what to try; the kernel decides what happens. The model can propose tool calls but receives no executor authority. These are enforced in code, not in prompts:

1. Every tool execution passes `check` first. No `check`, no execution.
2. The model never approves. Only a human session can resolve an approval.
3. No secret value reaches model context. The kernel attaches credentials at the call.
4. Every decision writes a receipt before the action runs.
5. Protected screens are never drawn by a model or an app.

## The six calls plus admit

| Call | What it does |
|---|---|
| `check` | Takes a policy check and returns allow, ask or deny. |
| `lease` | Issues a time-limited grant for a resource or for machine control. |
| `secret.use` | Uses a stored secret toward a host without showing the value. |
| `approval.request` and `approval.redeem` | Ask a human, then redeem the approved token once. |
| `audit.append` | Adds a row to the receipt chain. |
| `budget.reserve` and `budget.commit` | Hold and then spend a budget. |
| `deploy.admit` | Admits a deploy; always human-approved. |

## Action classes and autonomy

Each action has a class: `read`, `ui_layout`, `run_control`, `file_write`, `network`, `app_install`, `inbox_prepare`, `money`, `client_message`, `deploy`, `secret_new_host` and `irreversible`. A class the kernel does not know is `ask`, never allow.

The person picks one of three autonomy levels in onboarding: "Ask me first", "Ask only for risky actions" or "Full autonomy". The level changes what is allowed without asking for the first seven classes.

## Human-only classes

`money`, `client_message`, `deploy`, `secret_new_host` and `irreversible` always need a human approval, at every autonomy level. Policy may allow other classes; it never approves these five.

## Where `check` runs

In allternit-api, `check` runs inside the functions that execute tools, not in the HTTP routes, because some callers (the routine scheduler, the MCP server) never pass through HTTP. Each tool call gets exactly one check:

| Path | Function | How the class is picked |
|---|---|---|
| Native tools (`POST /tools/execute`, MCP `tools/call`, routine monitors) | `tool_routes::execute_tool_internal` | A fixed table: `file.read` is `read`, `file.write` and the shell tools are `file_write`, `http.*` is `network`, `file.remove` is `irreversible` |
| Org server tools | `server_tool_routes::execute_server_tool` | Always `ask`. A server tool can share a name with a native tool, so its name is never trusted |
| Attached MCP servers | `mcp_dispatcher::dispatch_call` | `ask`, except an app's `complete_checkout`, which is `money` |
| Computer members (`read_ui`, `act`, `use_credential`, ...) | `computer_v2::execute_v2` | The computer contract's `risk` field; `use_credential` is `secret_new_host` the first time a credential goes to a domain, `read` after a person approved that pair (see [Secrets](#secrets)) |

A tool that is not in a table is `ask`, never allow. Until onboarding records an autonomy level, every account is "Ask me first".

For an `ask` or human-only class, the call must carry an approval token bound to the `sha256:` hash of the canonical action `{tool, args}`. The token goes outside the arguments: `approval_token` on `/tools/execute` and on MCP `tools/call`, `kernel_approval_token` in a computer member's input. Without one, the kernel writes a receipt, opens an approval request for that exact action and refuses with code `approval_required` and the request id (HTTP 202 on `/tools/execute`). After a person approves, the caller retries the same call with the token. A token for a different payload, a spent token or an expired token is refused with a receipt.

### Modes

`ALLTERNIT_KERNEL_CHECK` picks how hard the check bites:

| Value | Receipt | Blocks |
|---|---|---|
| `off` | no | no; only the older permission policy applies |
| `shadow` (default) | yes, with what enforce would have done | no |
| `enforce` (the target) | yes | yes |

Shadow mode lets the build ship without breaking live tool calls while the receipts show what enforce would refuse. In shadow mode a kernel failure is logged and the tool runs; in enforce mode it is a denial (`kernel_unavailable`). The older permission policy on `/tools/execute` still runs first. A tool runs only when both allow it, so a kernel denial always wins.

## Approval tokens

A request carries the exact action payload and a deadline. A human session resolves it and the kernel issues a single-use approval token. The kernel rejects any resolve from a run token, bot token, agent credential, MCP client token or model request, and writes a receipt for the rejection. A human cannot approve a request made by a run they control.

On Allternit Desktop, approving also needs a user-presence check. Before the approve reaches the kernel, the Desktop app asks for Touch ID on macOS or Windows Hello on Windows. It then attaches a short-lived proof bound to that one request. The kernel refuses a Desktop approve without that proof and writes a receipt. On a computer with neither Touch ID nor Windows Hello (Linux, or a Mac or PC without them), approve from the web or phone app, which use your signed-in session. Deny needs no presence check.

## The signing key

The kernel signs approval tokens and receipts with one Ed25519 key. Where it lives depends on the host:

| Host | Where the key lives |
|---|---|
| Desktop on macOS | macOS Keychain |
| Desktop on Windows | Windows credential protection (DPAPI) |
| Desktop on Linux | Secret Service (GNOME Keyring or KWallet) |
| Cloud computers and servers (headless) | A file only the API's user can read (`0600`): `ALLTERNIT_KERNEL_SIGNING_KEY`, or `<data dir>/kernel/authority-ed25519.key` |

On Desktop the app's main process keeps the key in the OS keystore and passes it to the local API when the API starts. The key never goes in a file or an environment variable there. When you update from a build that kept the key in a file, Desktop moves the key into the keystore and then deletes the file. If the keystore is locked or turned down, approvals stay off until it unlocks. Desktop does not fall back to a new file.

Desktop also never replaces a lost key with a new one. After the first launch it leaves a marker (no key material) next to the data folder. If the keystore entry later reads as missing or damaged while that marker exists, Desktop starts the API without a key and approvals return `kernel_unavailable`, with a clear error in the log. A new key would otherwise leave every old receipt unverifiable without telling you. Restore the entry to turn approvals back on.

## The receipt chain

One append-only log, `kernel_receipts`, kept as a hash chain per principal and tenant (your account in your workspace), not per run and not per kind of receipt. The run a receipt belongs to is a column on the row. Each row holds the previous hash in its chain, its own hash and an Ed25519 signature. The hash covers the previous hash, the kind, the principal, the tenant, a hash of the payload, the decision and the time, so none of them can be edited unnoticed. The row also records which key signed it.

The kernel writes the receipt before it changes anything, in the same database transaction as the change. Request, resolve (approve, deny, expiry), redeem and every denial work this way. If the write fails, the answer is deny (`kernel_unavailable`). Two writers on one chain are serialized, so the chain stays a line. Before extending a chain the kernel checks the last row, and refuses to extend a chain that fails (`chain_broken`).

### Receipt routes

Both routes need a person's session (the same check as resolve) and read only your own chain. A run, agent, bot, MCP client or API key is refused.

| Route | What it returns |
|---|---|
| `GET /api/v1/kernel/receipts` | Your receipts, newest first. Query: `limit` (up to 500), `before` (an `idx`, to page). |
| `GET /api/v1/kernel/receipts/verify` | Recomputes every hash, link and signature in order. Returns `ok`, the row count, the first bad row (`receipt_id`, `idx`, `reason`) and `signed_by_previous_key`. |

### The verify rule

An edited row fails with the first bad row named: `payload_hash_mismatch`, `hash_mismatch`, `broken_link` or `bad_signature`. A row signed by a different key than the one in use is not tampering: if its signature verifies against the public key stored on that row, it counts under `signed_by_previous_key` and the chain still passes. A signature that does not verify against its own stored key fails. Deleting or updating a row is refused by database triggers.

## Secrets

No secret value reaches model context. The kernel attaches credentials at the call and masks every tool result before the model sees it.

### `secret.use`

A caller names a secret by handle (`vault:github-deploy`, `computer:vault:github-login`), a purpose (`http_header`, `env_for_process`, `connector_call`, `sign`) and a target host or process. The kernel resolves the value only inside the tool execution and hands it to the code that puts it on the wire. The caller never receives it, and no request, response, receipt or log holds it. A value where a handle belongs is refused with `bad_request`.

The first use of a secret toward a host it has never been used with is `secret_new_host`, a human-only class. Without a token, the kernel writes a receipt, opens an approval request for that exact use and refuses with `approval_required`. After a person approves, the retry binds the secret and the kernel records the pair. Later uses toward the same host are allowed without asking, and each one writes a `secret_use` receipt. A different host is new again.

Hosts are normalised (`https://API.GitHub.com:443/x` is `api.github.com`). Known pairs live in `kernel_secret_hosts` (migration V300), per account and tenant. Rows are written only after a person's approval. Shadow mode binds a new host with a `shadow_would_ask` receipt and records nothing.

Computer `use_credential` follows the same rule. `check` classifies it as `secret_new_host` for a new (credential, domain) pair and `read` for a known one. After an allowed check, `computer_v2::execute_v2` records the pair, but only when that check redeemed a person's token for the same action.

The same call is reachable over HTTP for callers outside the API process, such as Gizzi's shell and connector runtimes: `POST /api/v1/kernel/secrets/use` with a `SecretUseV1` body. Run and service callers only; a person's session is refused. The answer holds `use_id`, `bound`, `redaction_id` and `receipt_id`, never the value. Handles resolve as `vault:<name>` from the account's credential vault. A new host answers `approval_required` with the receipt id and an open request, and the retry carries `approval_token`.

### The redactor

One redactor masks every tool result in allternit-api before it is returned: `execute_tool_internal` (HTTP, MCP `tools/call`, routines), `dispatch_call` (attached MCP servers), MCP `tools/call` as a whole, the computer toolset, and ACI run frames (`scrub_frame`, which it replaced). It masks, in order:

1. **The exact values the kernel attached during the call.** These are the account's vault secrets, a credential bound by `secret.use` or `use_credential` (keychain, Bitwarden and 1Password included), an MCP server's credential headers, and this process's credential-named environment values. Their base64 form is masked too.
2. **Credential-shaped strings:** the `sk-`, `ghp_`, `gho_`, `xox?-`, `AKIA`, `AIza` and `sk_live_` prefixes, PEM private key blocks, JWTs, bearer and basic header values, passwords in URLs, and long or mixed values assigned to a key named like a credential (`password=`, `"api_key":`, `GITHUB_TOKEN=`).

Masked text reads `[REDACTED]`. An approved read of a `.env` or credential file also masks every assignment value, so the model sees the names and not the values.

### Gizzi

Gizzi Code applies the same rules (`shared/util/secret-redactor.ts`, a port tested against the same vectors) to:

- `vault_query` note previews, masked before they are cut. `vault_write` refuses to save a note that holds a credential.
- Bash stdout and stderr, both foreground and background and both local and VM.
- Approved reads of credential paths (`.env`, SSH keys, `credentials`), where every value is masked.

`bash.env_passthrough` and `GIZZI_BASH_ENV_PASSTHROUGH` no longer pass a credential-named variable on their own. The bash tool asks the person once for that exact name (an `env_secret` ask), and a glob never approves one. Paths with no ask, such as the selfhost worker and environment setup, leave it out. An approved value is still masked in the command's output.

### Test vectors

`spec/Contracts/os/v1/conformance/redaction-vectors.json` holds the shared cases. Each case lists an input, the attached values, the strings that must disappear and the strings that must stay. The Rust tests (`authority::redact`) and the TS tests (`test/util/secret-redactor.test.ts`) both read it. A rule change goes into both redactors, with a vector.

## Budget

`budget.reserve` takes an amount before a run spends it, and `budget.commit` records what it actually spent. The limit is the one that already exists: a bot's monthly limit, set in the bot's spend settings (`agents.config.spendLimit.monthlyUsd`). The kernel adds no second limits store. Its own table, `kernel_budget_reservations` (migration V310), holds only the reserve and commit ledger.

| Route | Does |
|---|---|
| `POST /api/v1/kernel/budget/reserve` | Body is a `BudgetReservationV1` without the server fields. Returns it with `status: "reserved"`. |
| `POST /api/v1/kernel/budget/commit` | Body: `reservation_id`, `actual_amount`, `quantity`, `unit`, `idempotency_key`. Returns it with `status: "committed"`. |
| `POST /api/v1/kernel/budget/release` | Body: `reservation_id`. Gives the whole reservation back. |

- **Over the limit.** A reserve fails with `budget_exceeded` and a receipt when committed spend plus live reservations this month plus the new amount pass the limit. The refused call reserves nothing. A principal with no limit set, or a currency other than USD, has no limit to pass: the reservation is still recorded and receipted.
- **Commit below the reservation.** The unused remainder is released at once and counts as free again. Commit above the reservation is allowed only if the extra still fits the limit; otherwise `budget_exceeded` and the reservation stays open.
- **Retries.** A commit repeated with the same `idempotency_key` returns the same result. A second commit with another key is `conflict`. A reservation not committed by `expires_at` stops counting and is marked `expired`.
- **Receipts.** Every reserve, commit, release and refusal writes a `budget` receipt before the change.
- **Money.** Amounts are decimal strings with up to six decimals. A reservation is not a charge: sending an invoice or taking a payment is still the human-only `money` class, and `check` still needs a person's token for it.

## Leases

`computer_control_lease.rs` stays the store for who controls a computer (one controller, 120 second TTL, renewed by a heartbeat, a person can take over from an agent). The kernel shows each live control lease as a `LeaseV1` and runs `lease.acquire`, `lease.heartbeat` and `lease.release` on it.

| Field | Value |
|---|---|
| `lease_id` | `ccl_<computer_id>` |
| `scope` | `["computer:<computer_id>"]` |
| `holder` | `user:<id>`, `agent:<id>`, `bot:<id>` or `session:<id>` |
| `state_version` | always 0; the store keeps no version, so a heartbeat with another value is `conflict` |
| `extensions["x-os-v1"]` | `kind: "computer_control"`, `expires_at`, `holder_label` |

`GET /api/v1/kernel/leases` lists the live leases for your account: those on computers you own (directly or through a bot) and those you hold. It is read-only and writes no receipt. A person's session or a run of the same account may call it; service, API-key and MCP callers may not.

Acquire needs `check_id` to name an `allow` `check` receipt of your account, else `denied`. A scope that is not a single `computer:<id>` is `bad_request`. A computer already leased is `conflict`. A person holds a lease as themselves, a run never holds as `user`. Compute leases (placement, vCPU, memory) are not in this view yet. The old fabric lease client (`fabric/os_client.rs`) stays behind its unset configuration until they are.

## The four depths

The interface is written once and reused unchanged:

1. **Hosted:** in process inside the API server. This gives process separation, not privilege separation.
2. **PID 1:** a Rust init process with separate users.
3. **Own kernel:** kernel IPC.
4. **Hardware:** the same calls on dedicated hardware.

## Standing tool policies and routine receipts

- **Standing Allow.** A person's per-tool Allow in Customize is a standing human decision. The policy lives in the client only, so the client syncs it with `PUT /api/v1/kernel/standing-grants` (`{ "tools": [{ "tool", "policy" }] }`; `allow` records, `ask` and `block` remove). It needs a person's session proof; machine credentials get `person_required`. `check` reads the grants for an `ask` rule only and records `approved_by: standing_grant`. Money, client_message, deploy, secret_new_host and irreversible actions never read it and always need a fresh token.
- **Routine receipts.** A scheduled routine resolves its owner's org (else tenant) before it runs a tool, so its receipts land on the owner's chain and not on `default`.
