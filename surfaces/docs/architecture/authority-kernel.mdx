## The rule

The model is the shell. Deterministic code is the kernel. The model decides what to try; the kernel decides what happens. The model can propose tool calls but receives no executor authority. These are enforced in code, not in prompts:

1. Every tool execution passes `check` first. No `check`, no execution.
2. The model never approves. Only a human session can resolve an approval.
3. No secret value reaches model context. The kernel attaches credentials at the call.
4. Every decision writes a receipt before the action runs.
5. Protected screens are never drawn by a model or an app.

## The six calls plus admit

| Call | What it does |
|---|---|
| `check` | Takes a policy check and returns allow, ask or deny. |
| `lease` | Issues a time-limited grant for a resource or for machine control. |
| `secret.use` | Uses a stored secret toward a host without showing the value. |
| `approval.request` and `approval.redeem` | Ask a human, then redeem the approved token once. |
| `audit.append` | Adds a row to the receipt chain. |
| `budget.reserve` and `budget.commit` | Hold and then spend a budget. |
| `deploy.admit` | Admits a deploy; always human-approved. |

## Action classes and autonomy

Each action has a class: `read`, `ui_layout`, `run_control`, `file_write`, `network`, `app_install`, `inbox_prepare`, `money`, `client_message`, `deploy`, `secret_new_host` and `irreversible`. A class the kernel does not know is `ask`, never allow.

The person picks one of three autonomy levels in onboarding: "Ask me first", "Ask only for risky actions" or "Full autonomy". The level changes what is allowed without asking for the first seven classes.

## Human-only classes

`money`, `client_message`, `deploy`, `secret_new_host` and `irreversible` always need a human approval, at every autonomy level. Policy may allow other classes; it never approves these five.

## Where `check` runs

In allternit-api, `check` runs inside the functions that execute tools, not in the HTTP routes, because some callers (the routine scheduler, the MCP server) never pass through HTTP. Each tool call gets exactly one check:

| Path | Function | How the class is picked |
|---|---|---|
| Native tools (`POST /tools/execute`, MCP `tools/call`, routine monitors) | `tool_routes::execute_tool_internal` | A fixed table: `file.read` is `read`, `file.write` and the shell tools are `file_write`, `http.*` is `network`, `file.remove` is `irreversible` |
| Org server tools | `server_tool_routes::execute_server_tool` | Always `ask`. A server tool can share a name with a native tool, so its name is never trusted |
| Attached MCP servers | `mcp_dispatcher::dispatch_call` | `ask`, except an app's `complete_checkout`, which is `money` |
| Computer members (`read_ui`, `act`, `use_credential`, ...) | `computer_v2::execute_v2` | The computer contract's `risk` field; `use_credential` is `secret_new_host` |
| Agents tools on the MCP server (`list_agents`, `get_run`, `get_run_result`, ...) | `mcp_agents::call_tool` | `read` |
| Agent-interface MCP tools (`agent_send`, `agents_list`, `thread_events`, `approvals_list`, `approval_respond`) | `mcp_server_routes::call_aai_tool` | `agent_send` to one of your own bots is `run_control`; a send that would leave your own agents is `client_message` (human-only). The rest are `read` (`approval_respond` never approves over MCP) |
| MCP `inference.*` built-ins | `mcp_server_routes::handle_builtin_dotted_tool` | `read` (a model turn or a usage read). `time.now` goes on to the native path and is checked there |

A tool that is not in a table is `ask`, never allow. Until onboarding records an autonomy level, every account is "Ask me first".

Every check writes its receipt to the same chain the [receipt routes](#receipt-routes) read: your account plus one tenant value, the same on every path. That value is your organization when you are in one, otherwise your account's tenant, otherwise `default` (`authority::kernel_scope` in allternit-api). So a check made from a native tool, an MCP call or a computer member shows up in `GET /api/v1/kernel/receipts`.

For an `ask` or human-only class, the call must carry an approval token bound to the `sha256:` hash of the canonical action `{tool, args}`. The token goes outside the arguments: `approval_token` on `/tools/execute` and on MCP `tools/call`, `kernel_approval_token` in a computer member's input. Without one, the kernel writes a receipt, opens an approval request for that exact action and refuses with code `approval_required` and the request id (HTTP 202 on `/tools/execute`). After a person approves, the caller retries the same call with the token. A token for a different payload, a spent token or an expired token is refused with a receipt.

### Modes

`ALLTERNIT_KERNEL_CHECK` picks how hard the check bites:

| Value | Receipt | Blocks |
|---|---|---|
| `off` | no | no; only the older permission policy applies |
| `shadow` (default) | yes, with what enforce would have done | no |
| `enforce` (the target) | yes | yes |

Shadow mode lets the build ship without breaking live tool calls while the receipts show what enforce would refuse. In shadow mode a kernel failure is logged and the tool runs; in enforce mode it is a denial (`kernel_unavailable`). Shadow mode logs a failure as a warning once per process (one for a missing signing key, for example when Desktop has not handed it over yet, and one for any other failure), then counts later ones at debug level, so the log does not fill with one warning per tool call. The older permission policy on `/tools/execute` still runs first. A tool runs only when both allow it, so a kernel denial always wins.

## Approval tokens

A request carries the exact action payload and a deadline. A human session resolves it and the kernel issues a single-use approval token. The kernel rejects any resolve from a run token, bot token, agent credential, MCP client token or model request, and writes a receipt for the rejection. A human cannot approve a request made by a run they control.

On Allternit Desktop, approving also needs a user-presence check. Before the approve reaches the kernel, the Desktop app asks for Touch ID on macOS or Windows Hello on Windows. It then attaches a short-lived proof bound to that one request. The kernel refuses a Desktop approve without that proof and writes a receipt. On a computer with neither Touch ID nor Windows Hello (Linux, or a Mac or PC without them), approve from the web or phone app, which use your signed-in session. Deny needs no presence check.

## The signing key

The kernel signs approval tokens and receipts with one Ed25519 key. Where it lives depends on the host:

| Host | Where the key lives |
|---|---|
| Desktop on macOS | macOS Keychain |
| Desktop on Windows | Windows credential protection (DPAPI) |
| Desktop on Linux | Secret Service (GNOME Keyring or KWallet) |
| Cloud computers and servers (headless) | A file only the API's user can read (`0600`): `ALLTERNIT_KERNEL_SIGNING_KEY`, or `<data dir>/kernel/authority-ed25519.key` |

On Desktop the app's main process keeps the key in the OS keystore and passes it to the local API when the API starts. The key never goes in a file or an environment variable there. When you update from a build that kept the key in a file, Desktop moves the key into the keystore and then deletes the file. If the keystore is locked or turned down, approvals stay off until it unlocks. Desktop does not fall back to a new file.

Desktop also never replaces a lost key with a new one. After the first launch it leaves a marker (no key material) next to the data folder. If the keystore entry later reads as missing or damaged while that marker exists, Desktop starts the API without a key and approvals return `kernel_unavailable`, with a clear error in the log. A new key would otherwise leave every old receipt unverifiable without telling you. Restore the entry to turn approvals back on.

## The receipt chain

One append-only log, `kernel_receipts`, kept as a hash chain per principal and tenant (your account in your workspace), not per run and not per kind of receipt. The run a receipt belongs to is a column on the row. Each row holds the previous hash in its chain, its own hash and an Ed25519 signature. The hash covers the previous hash, the kind, the principal, the tenant, a hash of the payload, the decision and the time, so none of them can be edited unnoticed. The row also records which key signed it.

The kernel writes the receipt before it changes anything, in the same database transaction as the change. Request, resolve (approve, deny, expiry), redeem and every denial work this way. If the write fails, the answer is deny (`kernel_unavailable`). Two writers on one chain are serialized, so the chain stays a line. Before extending a chain the kernel checks the last row, and refuses to extend a chain that fails (`chain_broken`).

### Receipt routes

Both routes need a person's session (the same check as resolve) and read only your own chain. A run, agent, bot, MCP client or API key is refused.

| Route | What it returns |
|---|---|
| `GET /api/v1/kernel/receipts` | Your receipts, newest first. Query: `limit` (up to 500), `before` (an `idx`, to page). |
| `GET /api/v1/kernel/receipts/verify` | Recomputes every hash, link and signature in order. Returns `ok`, the row count, the first bad row (`receipt_id`, `idx`, `reason`) and `signed_by_previous_key`. |

### The verify rule

An edited row fails with the first bad row named: `payload_hash_mismatch`, `hash_mismatch`, `broken_link` or `bad_signature`. A row signed by a different key than the one in use is not tampering: if its signature verifies against the public key stored on that row, it counts under `signed_by_previous_key` and the chain still passes. A signature that does not verify against its own stored key fails. Deleting or updating a row is refused by database triggers.

## The four depths

The interface is written once and reused unchanged:

1. **Hosted:** in process inside the API server. This gives process separation, not privilege separation.
2. **PID 1:** a Rust init process with separate users.
3. **Own kernel:** kernel IPC.
4. **Hardware:** the same calls on dedicated hardware.
