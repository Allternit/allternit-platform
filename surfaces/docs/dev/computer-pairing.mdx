## The pairing paths

| Path | Command | Where it lands | Code |
|---|---|---|---|
| Computer pairing code | `allternit computer pair <code>` | `paired_computers` (mesh IP, screen sharing) | `cmd/allternit-cloud-api/src/routes/paired_computers.rs:52` (routes), `:135` (create code), `:165` (redeem), `:220` (pair self); `cmd/cli` `computer-pair.ts` |
| Runtime pairing | `allternit-factory pane fabric pair` (shown to users as `ao fabric pair`), and `gizzi pair` | `runtime_pairings`, then `runtime_devices` | `factory/pane/src/ao/fabric/cloud.rs:94`; `cmd/allternit-cloud-api/src/routes/runtime_pairing.rs:218` (routes) |
| Fabric node enroll | `allternit fabric node enroll` | `/v1/fabric/nodes/enroll` | `cmd/cli/src/commands/fabric.ts:50` |

`ao` is not on users' machines, and the `allternit` npm CLI has no publish step. The command that ships to users with Gizzi Code is `gizzi pair`.

### `gizzi pair` uses the runtime pairing model

- `cmd/gizzi-code/src/cli/commands/pair.ts:86` defines `gizzi pair` ("pair this machine as an Allternit runtime device"), with `--status`, `--force` and `--name`.
- `cmd/gizzi-code/src/runtime/services/pairing/pairing.ts:261` posts `/api/v1/runtime-pairings`, and `:299` posts `/api/v1/runtime-pairings/exchange`. Token rotation uses `/api/v1/runtime-devices/:id/rotate` (`:192`). These are the same endpoints `ao fabric pair` calls (`cloud.rs:94`).

## Target model

Runtime pairing is the model. A paired computer is a `runtime_devices` row. Screen sharing (mesh plus VNC) becomes an optional step after pairing, not part of it. `paired_computers` stays for the mesh and screen-share data and gains `runtime_device_id`, so the console joins the two.

The visible command is **`gizzi pair`**. Install line (from `surfaces/docs/cli/installation.mdx`):

```bash
npm install -g @allternit/gizzi-code
# or
brew tap allternit/tap
brew trust --formula allternit/tap/gizzi-code
brew install allternit/tap/gizzi-code
```

### Aliases (old commands keep working)

| Old command | Becomes |
|---|---|
| `allternit computer pair <code>` | Alias. Redeems the code, creates or links the runtime device, then offers screen sharing. |
| `ao fabric pair` / `allternit-factory pane fabric pair` | Alias of `gizzi pair`. Same endpoints. |
| `allternit fabric node enroll` | Unchanged for fabric nodes. It also creates the runtime device row when a user is signed in. |

No hard cutover: nothing is removed in the first release.

### State machine

```text
unpaired -> code_issued -> approved -> device_token_issued -> online
                |              |                                 |
             expired        denied                      offline (heartbeat lost)
                                                               |
                                              rotating <-> online
                                              revoked (user removes the computer)
```

Optional, after `online`: `screen_share_off` to `screen_share_on` (mesh IP assigned, VNC enabled).

## One row per machine (built, step 2.10)

### The machine key

Every pairing path sends the same key, and the console groups by it when it reads the list. It is the key the active-machine cap already counts machines by (`services::quota_service::machine_key_for`), so one Mac is one machine for billing and for Computers.

1. **`mid:<machine id>`**: the random id in `~/.allternit/machine-id`, made once by whichever client runs first. Desktop (`auth-manager.ts` `machineId()`), `gizzi pair` (`pairing.ts` `machineId()`), `ao fabric pair` (`factory/pane/src/ao/fabric/cloud.rs` `shared_machine_id()`) and `allternit computer pair` (`computer-pair.ts` `machineId()`) all read and write that file.
2. **Hostname key** for clients too old to send a machine id: lower-case hostname without `.local`, then `|platform`. A row without a machine id joins by hostname only when that key names exactly one machine. Generic hostnames (`localhost`, `ubuntu`, `debian`, `vps` and similar) never join by hostname, so two default VPS images stay two rows. Two rows with different machine ids never join, whatever their hostnames, display names or stored runtime links. A code-paired row that supplies a machine id promotes a matched legacy machine to that id, so later pairings cannot replace it.
3. **Stored link**: `paired_computers.runtime_device_id`, written at redeem time when the machine id names a live runtime device.
4. **Same owner and name**, for code-paired rows from before 2.10 that have neither. The name must be nonempty, nongeneric and match exactly one compatible machine. An ambiguous match stays separate.

Shared rows (paired by someone else in your organization) never join your machines.

Why this key: it already exists on every runtime device (migration 119), Desktop and gizzi already share the file, and the cap already treats it as "the machine". Nothing new has to be trusted. The machine id names a machine and is not a credential: grouping happens only inside one account.

### Row id and aliases

| Field | Rule |
|---|---|
| `id` | The code-paired row's id when the machine has one (as before 2.10), else its oldest runtime device's id |
| `aliases` | Every other runtime device id and paired row id of the machine |
| `runtimeId` | The device holding a relay, else the Desktop (it serves host data), else one that reported lately |
| `pairedId` | The `paired_computers.id`, for screen sharing and Factory peer tickets |

Every console route resolves a row id or an alias to the same machine (`computers_host::resolve_target`), so a client that saved an old id keeps working. Nothing is merged or copied in the database. Migration 159 is additive. Keep its columns and table when rolling code back.

### Rename and unpair

- `PATCH /api/v1/computers/paired/:id {name}` stores the name in `computer_machine_names` by machine key, so it covers every alias and survives re-pairing.
- `POST /api/v1/computers/:id/unpair {confirm:true}` revokes every runtime device of the machine, deletes its code-paired rows and its name, in one transaction. A cloud computer is deleted from Settings, not unpaired.
- `DELETE /api/v1/computers/paired/:id` still removes only that code-paired row.

Account erase covers `computer_machine_names`.

### What each old command does now

| Command | Sends | Row |
|---|---|---|
| Allternit Desktop sign-in | `machineId`, hostname, `darwin-arm64` style platform | joins the machine |
| `gizzi pair` | the same | joins the machine |
| `allternit-factory pane fabric pair` (`ao fabric pair`) | `machineId` from the same file (new in 2.10) | joins the machine |
| `allternit computer pair <code>` | `machineId`, `hostname`, `platform` (new in 2.10) | joins the machine; adds `pairedId` and the mesh address |

`POST /api/v1/computers/pairing-codes` now answers `command: "gizzi pair"` (the visible command), `installCommand`, and `codeCommand` (`allternit computer pair <code>`, the optional screen-share step). The ao and `allternit` CLIs print `gizzi pair` as the pairing command for your own computers.

### Existing links (migration 153_computers_console.sql)

```sql
ALTER TABLE public.paired_computers
  ADD COLUMN IF NOT EXISTS runtime_device_id TEXT NULL;
CREATE INDEX IF NOT EXISTS paired_computers_runtime_device_idx
  ON public.paired_computers (runtime_device_id);

ALTER TABLE public.provisioned_instances
  ADD COLUMN IF NOT EXISTS location TEXT NULL,
  ADD COLUMN IF NOT EXISTS template TEXT NULL;
```

Migration 153 uses `provisioned_instances` for cloud computers. Migration 159 adds the machine identity columns and names table. Never drop a column in the same train that stops using it.
