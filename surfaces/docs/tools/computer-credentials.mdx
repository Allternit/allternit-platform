## Overview

Agents sometimes have to type secrets: a password into a login form, a TOTP code into a 2FA prompt. `use_credential` does this without the value ever entering the model context, the prompt, the tool result or the logs. The model sees and sends only the credential's **name**; the executor resolves the value server-side and types it into the **focused field**, and the audit row records the use with the value redacted.

One contract member:

```json
{
  "toolset": "computer",
  "member": "use_credential",
  "input": { "name": "github-login", "kind": "secret", "domain": "github.com" }
}
```

| Field | Meaning |
|---|---|
| `name` | The credential's name in the vault. Required. |
| `kind` | `secret` (default): type the stored value. `totp`: generate a fresh RFC 6238 code from a stored seed and type that. |
| `source` | `vault` (default, then `keychain`), `keychain`, `bitwarden` or `onepassword`. |
| `domain` | The app or domain you are typing into. Required when the credential carries a binding; it must match. |

On non-sandbox targets (this-device, paired computers) a person approves each use, the same rule as the `type` member; sandboxed cloud computers run it under the run's policy.

## Backends

The schema endpoint (`GET /api/v1/computers/:id/toolset/schema`) reports `credential_backends` with what answers on the current machine.

| Backend | Where it resolves from | Status |
|---|---|---|
| `vault` | The sealed per-user credential store (`POST /api/aci/credentials`, AES-256-GCM at rest). Carries optional app/domain **bindings** and TOTP seeds. | Tested |
| `keychain` | macOS Keychain: `security find-generic-password -s allternit.computer -a <name> -w`. Add with `security add-generic-password -s allternit.computer -a <name> -w`. | Tested (macOS) |
| `bitwarden` | The Bitwarden CLI (`bw get password <name>`), for team vaults. Needs `bw` installed and an unlocked session (`BW_SESSION`). | Interface + CLI adapter; untested where the CLI is absent |
| `onepassword` | The 1Password CLI (`op item get <name> --fields label=password --reveal`), for team vaults. Needs `op` installed and signed in. | Interface + CLI adapter; untested where the CLI is absent |

Resolution order with no `source`: vault first, then Keychain. A miss in both answers a plain "no credential named ..." error — the error path carries names only, never values.

## Bindings: a credential types only into its app

A credential can be bound to an app or domain at creation:

```http
POST /api/aci/credentials
{ "name": "github-login", "type": "token", "value": "...", "bind": "github.com" }
```

`use_credential` then refuses to type it anywhere else: pass `domain` equal to the binding or the call fails with "bound to 'github.com', not ...". The binding is a declaration check — the model declares where it is typing — per-domain enforcement against the focused app lands with the safety layer (D5).

`bind` accepts ASCII alphanumerics plus `._-:/` (up to 128 chars), so hostnames (`github.com`), bundle-style ids (`com.apple.Safari`) and URL prefixes all work. `GET /api/aci/credentials/:name` returns the binding; values are never returned by any endpoint.

## TOTP

`{ "kind": "totp" }` generates a fresh 6-digit RFC 6238 code (HMAC-SHA-1, 30-second steps) from a `totp_secret` credential — the same `POST /api/aci/credentials` type with a base32 seed — and types the code. The seed is never typed and never injected into a sandbox environment; only the derived code leaves the vault, once. Codes can also be fetched without typing via `GET /api/aci/credentials/:name/totp`.

## Where the value flows (and where it does not)

1. The model sends only the credential **name** in the tool call.
2. The executor opens the value in memory (`CredentialStore::open_for_computer_use`) — it is never serialized, and the store's `Debug` is intentionally not derived.
3. Typing rides the local driver socket (this-device) or the guest's exec channel, base64-wrapped into a temp file that is removed immediately (guests).
4. The driver-side router audit logs op/app/engine timings only — never tool arguments.
5. The result text is "Credential '\<name\>' typed into the focused field." The policy audit row records the member, risk, target and computer — no value.

Verify a credential use by outcome — the field filled, the redacted audit row — never by echoing the secret.

## Human approval

`use_credential` on this-device returns `409 approval_required` the first time in a run; the normal approval round trip (`POST /api/aci/handoff/:approval_id/approve`, then resend with `approval_grant`) covers it, and gizzi's adapter drives that round trip automatically. The grant binds to the exact action hash, so approving "type github-login into github.com" cannot approve anything else.
