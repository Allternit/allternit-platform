## Overview

Agents sometimes have to type secrets: a password into a login form, a TOTP code into a 2FA prompt. `use_credential` does this without the value ever entering the model context, the prompt, the tool result or the logs. The model sees and sends only the credential's **name** and the **field** to fill; the executor resolves the value server-side and writes it into that field, and the audit row records the use with the value redacted.

One contract member:

```json
{
  "toolset": "computer",
  "member": "use_credential",
  "input": { "name": "github-login", "kind": "secret", "domain": "github.com", "element_id": "e12" }
}
```

| Field | Meaning |
|---|---|
| `name` | The credential's name in the vault. Required. |
| `kind` | `secret` (default): type the stored value. `totp`: generate a fresh RFC 6238 code from a stored seed and type that. |
| `source` | `vault` (default, then `keychain`), `keychain`, `bitwarden` or `onepassword`. |
| `domain` | The app or domain you are typing into. Required when the credential carries a binding; it must match. |
| `element_id` | The password or text field's id from `read_ui` (e.g. `e12`). **Required on this computer** (the person's own Mac or PC); optional on cloud computers. Vision elements (`v…`) are refused. |

### Where the value goes on each computer

| Computer | With `element_id` | Without `element_id` |
|---|---|---|
| This computer (this-device) | Written straight into that element through accessibility (driver `act` with `{op: "set_value", focus: false}`): no focus change, no typing. A field that refuses the write answers an error and stays as it was. | **Refused**, with a message telling the model to pass the id from `read_ui`, or to call `request_human` with `secret` (the masked box, also with `element_id`) or plain `request_human` so the person fills it. |
| Linux / Windows cloud computer | Written into that element (AT-SPI text / UI Automation ValuePattern); if the field refuses, typed into the focused field instead. | Typed into the focused field of the **run's own screen**: the run's own X display on Linux ([Agent displays](/tools/allternit-driver#agent-browsers-on-linux-one-display-per-agent)), the one desktop on Windows, where the control lease lets one agent drive at a time. |

Why: until 2026-11-26 this computer typed the value with desktop-scope keystrokes, which go to whatever window is in front. In the Safari spike a dummy secret landed in a window that wasn't the target. Focusing the field first doesn't fix it either: focusing a field in a background Safari window makes that window key and pulls the person's own typing into it. A value write on one element is the only route that can't reach another window, so it is the only route this computer uses for a secret, and it never falls back to typing.

A person approves each use on every computer: this Mac, paired computers and cloud computers alike (contract `confirm: always`). The approval card names the credential and the domain, never the value. See [Human approval](#human-approval).

## One-off secrets: the masked box

A credential that is not saved anywhere goes through the masked secret box instead: the agent calls `request_human` with a `secret` label, the person types the value into a masked field under the live view, and it goes into the field without reaching the model, the logs or the transcript. On this computer the call must carry `secret.element_id` (the field's id from `read_ui`) and the value is written into that element the same way as `use_credential`; without it the request is refused before the box opens. On cloud computers `element_id` is optional, as above. The person can tick **Save to vault** to keep it as a credential bound to the current domain. See [Masked secret box](/tools/computer-toolset#masked-secret-box).

## Backends

The schema endpoint (`GET /api/v1/computers/:id/toolset/schema`) reports `credential_backends` with what answers on the current machine.

| Backend | Where it resolves from | Status |
|---|---|---|
| `vault` | The sealed per-user credential store (`POST /api/aci/credentials`, AES-256-GCM at rest). Carries optional app/domain **bindings** and TOTP seeds. | Tested |
| `keychain` | The OS credential store. **macOS:** the Keychain (`security find-generic-password -s allternit.computer -a <name> -w`); add with `security add-generic-password -s allternit.computer -a <name> -w`. **Windows:** Credential Manager, a generic credential whose target is `allternit.computer/<name>`; add with `cmdkey /generic:allternit.computer/<name> /user:<name> /pass:<value>`. **Linux:** none — `source: "keychain"` answers an error saying so (never "not found"). | Tested (macOS); Windows needs a real-machine check |
| `bitwarden` | The Bitwarden CLI (`bw get password <name>`), for team vaults. Needs `bw` on PATH (`bw.exe` or npm's `bw.cmd` on Windows) and an unlocked session (`BW_SESSION`). | Interface + CLI adapter; untested where the CLI is absent |
| `onepassword` | The 1Password CLI (`op item get <name> --fields label=password --reveal`), for team vaults. Needs `op` installed and signed in. | Interface + CLI adapter; untested where the CLI is absent |

Resolution order with no `source`: vault first, then the OS credential store (macOS and Windows; Linux checks the vault only). A miss in both answers a plain "no credential named ..." error — the error path carries names only, never values.

## Bindings: a credential types only into its app

A credential can be bound to an app or domain at creation:

```http
POST /api/aci/credentials
{ "name": "github-login", "type": "token", "value": "...", "bind": "github.com" }
```

`use_credential` then refuses to type it anywhere else: pass `domain` equal to the binding or the call fails with "bound to 'github.com', not ...". The [safety layer](/tools/computer-safety#credentials-stay-in-their-domain) also checks the app or page the agent is really typing into, where the executor can see it (this Mac through the Allternit Driver, Linux cloud computers by the active window, the gateway browser by its tab URL). It screens every free-text path for vault secrets: a bound secret typed outside its binding through `type`, `act`, `run_batch`, `form_input` or `run_subtask` inputs is refused, as is one typed where the binding can't be confirmed.

`bind` accepts ASCII alphanumerics plus `._-:/` (up to 128 chars), so hostnames (`github.com`), bundle-style ids (`com.apple.Safari`) and URL prefixes all work. `GET /api/aci/credentials/:name` returns the binding; values are never returned by any endpoint.

## TOTP

`{ "kind": "totp" }` generates a fresh 6-digit RFC 6238 code (HMAC-SHA-1, 30-second steps) from a `totp_secret` credential — the same `POST /api/aci/credentials` type with a base32 seed — and types the code. The seed is never typed and never injected into a sandbox environment; only the derived code leaves the vault, once. Codes can also be fetched without typing via `GET /api/aci/credentials/:name/totp`.

## Where the value flows (and where it does not)

1. The model sends only the credential **name** in the tool call.
2. The executor opens the value in memory (`CredentialStore::open_for_computer_use`) — it is never serialized, and the store's `Debug` is intentionally not derived.
3. On this computer the value rides only the local driver socket, inside one `act set_value` request; the driver's command-line fallback is never used, because its arguments would carry the value. The driver's reply leaves out the element diff, which would hold the new value. On guests it rides the guest's exec channel inside the base64 driver request, or, without the driver, base64-wrapped into a temp file that is removed immediately.
4. The driver-side router audit logs op/app/engine timings only — never tool arguments.
5. The result text is "Credential '\<name\>' written into element \<id\>." (or "...into the focused field." on a guest without `element_id`). The policy audit row records the member, risk, target and computer — no value.

Verify a credential use by outcome — the field filled, the redacted audit row — never by echoing the secret.

## Human approval

Every `use_credential` call asks the person, on every target, cloud guests included. The call returns `409 approval_required`; the normal approval round trip (`POST /api/aci/handoff/:approval_id/approve`, then resend with `approval_grant`) covers it, and gizzi's adapter drives that round trip automatically. The grant binds to the exact action hash, so approving "type github-login into github.com" cannot approve anything else.

Only the run's owner can answer: the user the approval was raised for, the owner of the computer it names (for a bot-owned computer, the bot's owner), or the Desktop app on this device itself (its local access token, not a call the desktop relay forwarded from another device). Anyone else gets `403 {"error": "not_run_owner"}` from approve or deny, and the approval stays pending. cloud-api forwards console decisions signed as the computer's owner, so console approvals keep working.

The refusal body and the stored approval say what is being approved:

```json
{ "error": "approval_required", "approval_id": "3f0c…", "confirmation_class": "irreversible",
  "kind": "credential", "credential": { "name": "github-login", "domain": "github.com" },
  "message": "irreversible action requires human approval before execution" }
```

`domain` is the call's declared `domain`, else the vault binding, lower case without a scheme or `www.` (it is `null` for an unbound credential with no declared domain). The same fields go out as a `computer.confirmation_required` event on the toolset events stream and as an `aci_approval` push (see [Computer toolset events](/tools/computer-toolset#events)), so a phone can approve from the notification. No field ever carries the value.

### Allow for this run

The person can approve with a scope:

```http
POST /api/aci/handoff/:approval_id/approve
{ "scope": "run" }
```

The answer is `{ "approval_id": "…", "status": "approved", "scope": "run" }`. Later fills of the **same credential name into the same domain in the same run** then skip the prompt. A different domain, a different credential, another run or another person still asks. The allowance lives in the API's memory only: it ends with the run (stop, re-run on the Mac, or six hours at most), nothing is written to disk, and nothing is remembered per site. Watch mode still asks every time. A body-less approve, or `scope` on an approval that isn't a credential fill in a run, is single-use (`"scope": "once"`).
