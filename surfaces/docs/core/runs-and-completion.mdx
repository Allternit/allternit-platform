A **Run** is one durable execution of a goal. It is the unit the work runtime carries across time, and it is the object the [Agency API](/api/agency/overview) returns.

<Note>
**Design and status.** This page describes the run model in the kernel contracts and the Agency API v0.3 contract. The work runtime underneath it (node outputs, wait gates, leases and reclaim, campaigns, the attention gate) is live in [CommRails](/core/commrails) today. The fail-closed judge and verifier-owned close are live but opt-in for internal flows. The Agency API that exposes runs over HTTP is not available yet.
</Note>

## What makes a run durable

- The run is persisted before the create call returns. It does not depend on the process that accepted it.
- Run state survives model eviction, cache loss, executor death and process restart.
- Resume works from durable state and receipts, never from a transcript.
- A node that was interrupted in the middle of an effect is not blindly re-run. It resumes only if the effect carries an idempotency key and a receipt. Otherwise the run raises an attention request with reason `unsafe_resume`.
- Every material transition is observable as a typed event or a receipt.

## The work-node lifecycle

A run is a graph of work nodes. Each node moves through one lifecycle:

```text
DECLARE → ADMIT → READY → LEASE → SPAWN → RUN → HEARTBEAT → OUTPUT → VERIFY
        → { COMMIT | CONTINUE | REPLAN | NEEDS_HUMAN } → CLOSE → VAULT / LEARN
```

No executor moves a node from running to done on its own. Closing a node is a system transition backed by completion evidence. `VAULT` and `LEARN` happen after the terminal state and are not shown as a run status.

## Run status

`Run.status` is the aggregate of the node lifecycle and the run receipt's completion status. There are ten statuses.

| Status | Terminal | When it applies |
|--------|----------|-----------------|
| `accepted` | no | The run is persisted. Its nodes are declared, admitted or ready. The run also stays `accepted` until its resolved defaults are recorded on `Run.resolved`; it cannot execute before that. |
| `running` | no | At least one node is leased, spawned, running, heartbeating, producing output, verifying, continuing or replanning. |
| `waiting` | no | Active nodes are on a timer, dependency or event wait gate, or a lease reclaim is pending, and no node is running. Nothing is asked of you. |
| `needs_attention` | no | A node needs a human: there is an open attention request. This includes `budget_exhausted`, which is raised only after billable and effectful execution has been hard-stopped. |
| `paused` | no | An operator paused the run. Nodes stopped at the next safe boundary, in-flight effects finished and were receipted, and leases were released. |
| `cancelling` | no | The cancel request is receipted. No new node is admitted or leased. Effects already dispatched are settling: each completes, times out, or is rolled back where the node declares a rollback. |
| `completed` | yes | The completion predicate evaluated true. |
| `partial` | yes | The run closed with the completion predicate false, and the completion contract has `allow_partial: true`. This is the only way a run ends `partial`. |
| `failed` | yes | The run closed after an unrecoverable failure or a budget stop. A run that stops with unmet criteria and `allow_partial: false` is `failed`. |
| `cancelled` | yes | The run closed after a cancel, once every in-flight effect settled. |

`partial` is never a synonym for failed or unfinished. It means the caller allowed a partial result in advance and the run reports exactly which criteria passed.

When nodes are in different states, the run reports the highest-precedence one:

```text
cancelling > paused > needs_attention > running > waiting > accepted
```

### Control operations

Pause, resume and cancel are asynchronous and idempotent.

| Operation | Effect |
|-----------|--------|
| Pause | Status goes to `paused` at the next safe boundary. Pausing a paused run is a no-op. |
| Resume | Continues from durable state and receipts. |
| Cancel | Status goes `cancelling`, then `cancelled`. Open attention requests are withdrawn. Repeating a cancel returns the current run. Cancelling a run that is already `completed`, `partial` or `failed` is a conflict (`ERR_RUN_TERMINAL`). |

Effects in flight at cancel time are never silently abandoned. Each outcome is receipted and listed in `Run.cancellation.effects_in_flight` until it settles.

## Verifier-owned completion

A model saying "done" is a proposal. It carries no authority. The builder or a decision step may propose completion; verifiers and humans supply evidence; the system performs the close.

A run is complete only when all of the following hold:

```text
COMPLETE(task) :=
      acceptance criteria satisfied
  AND required verifications pass
  AND no unresolved blocking failures
  AND required artifacts exist
  AND policy obligations satisfied
  AND completion evidence references durable receipts
```

Verification results are `pending`, `pass`, `fail`, `inconclusive` or `error`. `inconclusive` is never treated as `pass`. An inconclusive required verification raises an attention request (`verification_inconclusive`) instead of closing the run.

`Run.completion` shows each criterion, its result and the receipt IDs that back it.

## Completion criteria registry

Completion criteria are entries in a versioned, extensible registry, not a fixed enum. Each entry has an `id`, a `version`, a `verifier_kind`, and `verifier_semantics`: the precise text of what a pass means.

Built-in criteria:

| ID | Checks |
|----|--------|
| `tests_pass` | The target tests pass. |
| `no_new_regressions` | No test that passed before now fails. |
| `build_passes` | The build succeeds. |
| `typecheck_passes` | The type checker reports no errors. |
| `lint_clean` | The linter reports no findings. |
| `artifact_exists` | A required artifact was produced. |
| `requirement_verified` | A stated requirement was checked and met. |
| `human_review` | A human reviewed and approved. |

<Note>
The one-line descriptions above are summaries. The authoritative wording for each criterion is its `verifier_semantics` text in the registry.
</Note>

A request refers to a criterion by ID (latest version at resolution time) or by a pinned `{id, version}`. The version that was resolved is recorded on the run, so a later registry change does not alter what an existing run had to prove. Callers can also register custom criteria inline for one run, each with a verifier kind:

`parse`, `format`, `lint`, `typecheck`, `unit_test`, `integration_test`, `build`, `semantic_rule`, `requirement`, `security`, `regression`, `diff_review`, `human`.

The kernel package ships minimum completion evidence for one task type so far, bug fixes: target test passes, affected tests pass, no new failures, a diff-review verdict and a requirement check. Bug-fix runs do not allow partial completion. Evidence sets for other task types are defined as those task types are built.

## Attention and approvals

Agents request attention. They never notify people directly. An attention controller owns delivery, quiet hours, deduplication, quotas and escalation.

A run raises an attention request and moves to `needs_attention` when:

| Reason | Trigger |
|--------|---------|
| `approval_required` | Policy returned ASK for a proposed action. |
| `clarification_needed` | The run needs information only a person has. |
| `budget_exhausted` | A budget limit was reached and spend has been halted. |
| `verification_inconclusive` | A required verification could not reach pass or fail. |
| `low_confidence` | A decision fell below its calibrated threshold. |
| `unsafe_resume` | An interrupted effect cannot be safely resumed. |
| `review_requested` | A review step asked for a person. |

Each request has a `kind`:

- **`approval`** is a policy ASK. If it expires, it resolves as a rejection. This is fail closed.
- **`informational`** asks for input without gating an action. If it expires, it becomes `expired` with no rejection implied.

The first valid answer wins. An answer is written as a receipt before it takes effect. A hard policy deny never becomes an attention request, and an approval can never override one.

## Budgets

A budget sets at least one of a time limit (`max_seconds`) or a cost limit (`max_cost_usd`), and may also cap executed work nodes (`max_steps`) and attention requests (`max_attention_requests`).

On exhaustion the order of operations is fixed:

1. The platform **hard-stops all further billable and effectful execution**. `budget_usage.spend_halted` becomes `true`.
2. Only then does the run ask. With `on_exhaustion: request_attention` (the default) the run moves to `needs_attention` with reason `budget_exhausted`. With `on_exhaustion: stop` the run ends `failed`.

No spend happens while the run waits. Only a human answer can raise the budget. A model can never raise its own budget.

## Authority profiles

Authority is explicit. A run carries a named **authority profile** that compiles into capabilities and policy. A profile is a typed, versioned definition, not a magic string. Runs record the profile as `id@version`.

Three profiles exist:

| Profile | Intent |
|---------|--------|
| `read-only` | Read the workspace. No writes, no effects. |
| `code-safe` | Work on code within the workspace under sandboxing, asking before effects outside it. |
| `code-write` | Write to the workspace paths declared writable. |

<Note>
The intent column is a summary. The exact semantics of each profile are its typed definition: granted and denied capabilities, a filesystem scope (read, write, execute, and deny outside the workspace), a network policy, and an approval requirement per effect type (`never_allowed`, `always_ask`, `ask_unless_granted`, `allowed`). The Agency API will serve these definitions from [`GET /v1/authority-profiles`](/api/agency/catalog#list-authority-profiles).
</Note>

Rules that hold for every profile:

- Grants are explicit, scoped and expire with the run. A grant never outlives its run.
- Extra grants can only add scope within the caller's own entitlement. Nothing can weaken a hard policy deny.
- The interaction mode (`autonomous`, `approval_gated`, `recommend_only`) changes how much discretionary review happens. `autonomous` still stops at every policy ASK.
- **There is no bypass profile.** Names such as `yolo`, `bypass` or `auto-approve` are rejected, and no executor's native bypass mode is honored. See [Policy and safety](/core/policy-and-safety).

## Resolved defaults

A caller may supply only a goal. Whatever is omitted (workspace, authority, budget, completion) is resolved from the agent's and profile's versioned defaults. The resolved values are recorded on the run **before execution** and returned to the caller, along with which defaults filled them.

There are no hidden permissive defaults. If a safe value cannot be resolved, the request fails and no run executes.
