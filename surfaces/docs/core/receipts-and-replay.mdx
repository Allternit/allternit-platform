A **receipt** is the durable evidence that something happened in a run: an effect, an input, a policy decision, a verification result, a control action. Receipts are what completion, resume, audit and replay are built on.

<Warning>
**Status.** Receipts exist today as content hashes. The per-run hash chain, signatures, the verification keys endpoint, and replay with cassette recording are designed and specified but **not built yet**. This page describes the design in the kernel contracts and the Agency API v0.3 contract.
</Warning>

## What a receipt proves

A receipt proves that a specific, typed event was recorded at a specific position in a run's history, with specific content, by the platform.

It does prove:

- **Content.** The receipt body has not changed since it was written (content hash).
- **Order and completeness.** The receipt sits at a fixed index after a specific predecessor, and nothing was inserted or removed before it (hash chain).
- **Origin.** The platform's key signed it, for this schema and this purpose (signature with domain tag).
- **Source and trust.** Each receipt lists where its inputs came from and their trust class (provenance).

It does not prove:

- That a recorded result is correct. A verification receipt records that a verifier ran and what it returned. Whether the verifier is adequate is a separate question.
- Anything about events that were never receipted.

## Receipt types

| Type | Records |
|------|---------|
| `run` | The run's terminal state and what backs it. |
| `tool` | A tool invocation and its result class. |
| `action` | An external or irreversible action. Carries the idempotency key. |
| `mutation` | A change to the workspace, recorded as a unified diff. |
| `verification` | A verifier's result for a criterion. |
| `policy` | A policy decision: allow, allow with limits, ask or deny. |
| `node_output` | An artifact produced by a graph node. |
| `input` | Human or caller input to the run. |
| `attention` | An attention request and its resolution. |
| `control` | Pause, resume or cancel. |
| `spawn` | The start of an executor for a node. |

## Rules

- **Append-only.** A receipt is never edited or deleted. A correction is a new receipt whose `supersedes` field points at the old one.
- **Content-addressed.** Each receipt is identified by the hash of its content.
- **Input before effect.** Human input and control requests are receipted before they take effect.
- **Idempotency before retry.** An action with an external or irreversible effect needs an idempotency key and an action receipt before it may be retried.
- **Sufficient for replay.** Every node emits a receipt or trace event sufficient to reconstruct what it saw and did.

## Hash chain

Receipts for one run form a chain in `index` order.

```text
index 0                 index 1                 index 2
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│ prev_hash: null  │    │ prev_hash: H0    │    │ prev_hash: H1    │
│ content_hash: H0 │◄───│ content_hash: H1 │◄───│ content_hash: H2 │
└──────────────────┘    └──────────────────┘    └──────────────────┘
```

- `content_hash` is SHA-256 over the canonical JSON (RFC 8785, JCS) of every field of the receipt except `content_hash` and `signature`. It is written `sha256:` followed by 64 lowercase hex characters.
- `prev_hash` is the `content_hash` of the previous receipt in the same run. It is `null` only at index 0.

Because `prev_hash` is part of the hashed content, changing, removing or inserting any earlier receipt changes every hash after it.

## Signature and domain tag

Each receipt is signed with Ed25519. The signed material is not the raw content hash alone. It is the JCS-canonical form of this object:

```json
{
  "schema_id": "<receipt schema id>",
  "schema_version": "<receipt schema version>",
  "domain": "allternit.receipt.v1",
  "content_hash": "sha256:<64 hex>"
}
```

Binding the schema ID, schema version and the domain-separation tag `allternit.receipt.v1` into the signature means a signature made for one kind of receipt cannot be presented as a signature over a different schema, a different version, or a different protocol that happens to use the same key.

The signature object carries `alg` (`ed25519`), `key_id`, `value` (base64url), `domain` and `jwks_url`. Public keys are published as a JWKS document at `/.well-known/jwks.json`.

## Verifying a chain

To verify a run's receipts independently:

1. Fetch all receipts for the run in chain order.
2. For each receipt, remove `content_hash` and `signature`, canonicalize the rest with RFC 8785, hash with SHA-256, and compare with `content_hash`.
3. Check that `prev_hash` equals the previous receipt's `content_hash`, and is `null` at index 0. Check that `index` increases by one each step.
4. For each signature, build the four-field object above, canonicalize it, and verify the Ed25519 signature with the JWKS key whose `kid` equals `signature.key_id`.
5. Check that the run's terminal receipt (`Run.output.run_receipt_id`) is in the chain you verified.

The Agency API also offers a server-side check. It is a convenience, not the trust root: a client that needs assurance verifies with the published keys itself. Code for both is in [Agency API: Receipts](/api/agency/receipts#verify-independently).

## Replay

Replay re-runs a finished run at the decision and tool boundary to answer one question: given the same recorded world, does the system make the same decisions?

```text
live run → trace + receipts → cassette → replay → divergence report
```

A **cassette** is the recording of a run's external results, stored by content address. During replay:

- **Effects are recorded-only.** Every external call is served from the recording. This is the only replay mode.
- **Nothing is executed live.** A call with no recording fails that step with `ERR_REPLAY_UNRECORDED`. It is never sent to the real system.
- **Decisions are recomputed.** The replay reconstructs which node ran, the evidence it saw, the capability or tool it resolved, and why it branched. Generated text does not need to be reproduced token for token.
- **Divergence is reported.** The result is `equivalent`, `diverged_expected` (a difference caused by something you deliberately changed) or `diverged_unexpected`.

A replay can vary the authority profile, the completion criteria, the model class constraints or the runtime hints. Everything not overridden comes from the source run's recording. This makes replay the way to test a change to the system against real past runs without touching the outside world.

Replay is on the critical path for the Agency API alpha: the API does not open until a run can be replayed.
