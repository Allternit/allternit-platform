---
title: Starting conversations on a channel (developers)
description: How a bot starts a chat on Telegram, Slack, Discord, Teams, WhatsApp, SMS or email, the rule each platform enforces, and the mail thread list.
---

A bot normally replies to a conversation someone else began. The runtime (`allternit-api`) can also start one. These routes are what the phone's **Start new** sheet calls. User docs: [Your bot's phone](/guides/bot-phone), [Messaging channels](/guides/messaging-channels).

All routes sit under `/api/v1` and need the signed-in user. The bot must be yours, and switched on for a connection of that channel (**Agent Gateway → Messaging**). Nothing here needs new environment variables: a channel that isn't connected answers `409 not_connected`, and a connection whose transport has no credentials answers `503 <provider>_not_configured`.

## List who a bot can start with

```http
GET /api/v1/channels/{provider}/targets?botId={botId}
```

```json
{
  "targets": [
    { "kind": "user", "id": "777", "name": "Eoj", "sub": "2026-10-02T09:12:00Z" },
    { "kind": "group", "id": "-1001234", "name": "Ops chat", "sub": "2026-10-01T18:00:00Z" }
  ],
  "canStartWith": ["user", "group", "channel", "username"],
  "connected": true,
  "notes": "Telegram only lets a bot message a person who has messaged it first. …"
}
```

`provider` is `telegram`, `slack`, `discord`, `teams`, `whatsapp`, `whatsapp-personal`, `sms` (alias `phone`) or `email`. Targets come from what the runtime already knows: conversations stored for the bot's connections, plus (Slack, when the runtime holds a bot token) the channels the bot has joined. `canStartWith` lists the kinds that can be listed (`user`, `group`, `channel`) and the ways to type one in (`username`, `phone`, `email`). `notes` is the platform's rule in one line. A bot with no connection gets `connected: false` and an empty list, not an error. WhatsApp lists only people inside the 24-hour window.

## Start one

```http
POST /api/v1/channels/{provider}/start
```

```json
{
  "botId": "bot_123",
  "target": { "kind": "user", "id": "777" },
  "text": "Following up on the invoice.",
  "subject": "Invoice 42"
}
```

`target` takes `kind` plus one of `id`, `username`, `email` or `phone`. `subject` is for email only. `attachments` is an optional list of files, covered under [Attachments](#attachments). On success:

```json
{ "threadId": "bt_…", "conversationId": "777", "bindingId": "ccb_…", "provider": "telegram", "state": "sent", "remoteId": "777:42", "existing": false }
```

`state` is `sent` (200), or `unconfirmed` / `pending_approval` (202, still on its way). `existing: true` means the person already had a conversation with this bot and the message went into that thread.

The started conversation is a normal Allternit thread with a channel binding. The binding uses the same conversation key the platform's inbound events use, so the person's reply lands in the same thread. The bot's first message is stored as its outbound message, so it shows in the main thread list and in Messages. It goes out through the same send path as any reply, so the bot's channel tool policy (a send rule set to `ask` returns `428 approval_required` with the `threadId` and `approvalId`), the delivery log and the `channel.message.*` events all apply.

A refused start never leaves an empty thread when the platform's rule can be checked first (everything in the table except a refusal from the platform itself). Errors are `{ "error": "<code>", "message": "…" }`:

### Rules per channel

| Channel | Who | Rule | Refusal |
| --- | --- | --- | --- |
| Telegram | a chat id the bot has seen, or a group/channel the bot is in | People must have messaged the bot first. A group or channel is checked with `getChatMember`. `username` resolves public chats through `getChat`. | `user_never_messaged_bot`, `bot_not_in_group` |
| Slack | a channel id (`C…`, `G…`) or a user id (`U…`, `W…`) | Posts with `chat.postMessage`. A user id opens a direct message from the app. The post is top-level and the conversation is bound to its `ts`, so replies in that Slack thread continue it. A person's reply in a DM starts its own conversation. | `bot_not_in_channel`, `channel_not_found`, `invalid_target` |
| Discord | a server channel id, or a Discord user id (`kind: "user"`) | A channel: posts through the Allternit app's channel webhook (the channel must be in the connected server). A user: the Allternit app's bot opens a direct message through the cloud (see [Discord direct messages](#discord-direct-messages)). A legacy single-webhook connection can only continue channel conversations it has seen and can't send DMs. | `channel_not_in_guild`, `discord_webhook_fixed_channel`, `discord_dm_unavailable`, `discord_user_not_in_server`, `discord_dm_closed` |
| Teams | a conversation id | Needs a stored conversation reference: someone installed or messaged the bot. Proactive sending to anyone else is off on the shared app until the two-tenant spike is done (see [Teams](#teams-proactive-messages)). | `no_conversation_reference` |
| WhatsApp (Business) | a phone number | Free-form text only within 24 hours of the person's last message. Template messages are not supported yet. | `outside_24h_window` |
| WhatsApp (personal number) | a phone number or chat id | Unofficial linked device: no window, but WhatsApp can ban numbers that message people who didn't ask. Only when `ALLTERNIT_WA_PERSONAL=1`. | `whatsapp_personal_disabled` (503) |
| SMS / phone | an E.164 number | Uses the same path as `POST /api/v1/phone/text`: texts from the bot's number through the cloud, which enforces consent (the person must have texted or called first, or be an allowed contact) and the STOP list. A text and a later call share one thread. | `no_consent` (403), `invalid_target`, `not_connected` |
| Email | an address | Composes a new message from the bot's mailbox through mailflare. The approval gate stays on: the response is `202 pending_approval` with an `approvalThread` you approve from Mail → Needs OK. The thread uses the same key as an inbound reply, so an answer continues it. | `email_send_disabled`, `not_connected` |

Other codes: `unknown_provider` (404), `bot_not_found` (404), `not_connected` (409), `text_required` (400), `invalid_target` (400), `no_consent` (403), `conversation_belongs_to_other_bot` (409), `channel_policy` (403), `read_only` (403), `channel_rejected` (502, the platform said no; the message says why).

## Discord direct messages

The bot token of the shared Allternit Discord app lives only in cloud-api, so a runtime asks the cloud to open the DM. The route is authenticated like `POST /api/v1/channels/discord/send` (the runtime-device token):

```http
POST /api/v1/channels/discord/dm
```

```json
{ "guildId": "1234567890123456789", "userId": "123456789012345678", "text": "Hi, it's Finance.", "botName": "Finance" }
```

- `userId` is required: a Discord snowflake. `guildId` is optional; without it any server the caller installed the app in counts. A `guildId` that isn't the caller's is ignored, not trusted.
- The cloud only messages a person who is a member of one of the caller's installed servers (`GET /guilds/{id}/members/{user}`), then calls `POST /users/@me/channels` and `POST /channels/{id}/messages`. A DM can't wear a webhook's name or avatar, so with `botName` the message starts with the bot's name in bold.
- Without `text` the cloud only opens the channel. The start route does this first, so the conversation is bound as `discord:<dm channel id>` and a reply from the person lands in the same thread.

```json
{ "channelId": "900100200300400500", "messageId": "900100200300400501" }
```

| Status | `error` | Meaning |
| --- | --- | --- |
| 503 | `discord_not_configured` | The cloud has no Discord app env set (`ALLTERNIT_DISCORD_*`). Nothing else changes. |
| 404 | `discord_not_installed` | The caller has no server with the app installed. The start route answers `409 not_connected`. |
| 403 | `user_not_in_server` | The person shares no installed server with the caller. Start route: `409 discord_user_not_in_server`. |
| 403 | `dm_closed` | Discord error 50007: the person's privacy settings refuse DMs from server apps. Start route: `409 discord_dm_closed`. |
| 400 | `invalid_user_id` | Not a snowflake. |

Discord docs: [Create DM](https://discord.com/developers/docs/resources/user#create-dm), [Get Guild Member](https://discord.com/developers/docs/resources/guild#get-guild-member), [Create Message](https://discord.com/developers/docs/resources/message#create-message).

## Attachments

`attachments` on a start (and on `POST /api/v1/gateway/threads/{threadId}/channel-send` for replies) is a list of files, each `{ "filename", "mimeType", "dataBase64" }`. The file names `name`, `mime`/`type` and `contentBase64` are accepted too. Files are checked before any thread or send exists.

| Channel | How the file goes | Limits |
| --- | --- | --- |
| Telegram | `sendPhoto` for JPEG/PNG, `sendDocument` for everything else. One file carries the text as its caption (up to 1024 characters); more files, or a longer text, send the text first. | 5 files |
| Slack (shared app) | The cloud posts the text as the bot, then uploads the files into that message's thread with `files.getUploadURLExternal` and `files.completeUploadExternal`. The app needs the `files:write` scope, which new installs request; a workspace that installed earlier has to re-authorize before files upload. | 5 files |
| Email | Sent through mailflare's `attachments`. The approval gate stays on. | 10 files |
| SMS | Not sent as MMS. Each file is uploaded to the owner's cloud storage with the runtime's own credential (plan caps apply) and its permanent link is added to the text, one `name: link` line per file. If any upload fails (not paired, over the plan, links not enabled) nothing is sent and the send is rejected. | 3 files |
| Discord, Teams, WhatsApp | Not supported yet. | none |

Every channel: 10 MB per file, 20 MB per message. Refusals: `400 attachments_unsupported` (the channel takes none), `400 invalid_attachment` (no data, empty or bad base64), `413 attachment_too_large` (size or count). Start and channel-send accept request bodies up to 30 MB for this. The cloud's Slack send route takes the same `files` list (`{ "channel", "text", "threadTs", "files": [...] }`) and enforces the same caps. If the text posts but the upload fails, the send is reported as unconfirmed rather than failed, so it isn't posted twice.

### Files in the thread

Files are kept so the thread can offer them as downloads, on Desktop, the ai.allternit.com phone layout and the m.allternit.com app alike. When a bot sends files, and when someone sends a file in Telegram or Slack, the runtime stores each one in the user's files at the cloud ([Files API](/api/files#channel-attachments), plan limits apply) and the thread message event carries:

```json
"files": [
  { "name": "q3.pdf", "mime": "application/pdf", "size": 2516582, "url": "https://api.allternit.com/api/v1/files/<id>/raw?k=<token>" },
  { "name": "huge.mov", "mime": "video/quicktime", "size": 50000000, "error": "too_large" }
]
```

`size` is bytes. `url` is the file's permanent link, so the chip is a real download link and an old message never has an expired one (deleting the file in Settings > Files kills the link). A file that couldn't be kept (`error`: `too_large`, `storage-quota-exceeded`, `file-too-large`, `not_paired`, `slack_reauthorize_required`, or a platform refusal) shows by name with the reason, and the message is never blocked by it. The older `attachments: [name]` list stays on the event.

Inbound, per platform:

| Channel | How the file is fetched |
| --- | --- |
| Telegram | The runtime calls `getFile`, then downloads from `https://api.telegram.org/file/bot<token>/<file_path>` with the connection's bot token. Documents, photos (largest size), video, audio, voice, animations and video notes; Telegram lets bots download up to 20 MB, we keep up to 10 MB. |
| Slack (shared app) | The bot token never leaves the cloud, so the runtime asks `POST /api/v1/channels/slack/file` `{ url, name, mimeType }`; the cloud downloads the `url_private_download` from `files.slack.com` with the install's token and stores it (`201 { fileId, name, contentType, bytes }`). Needs the `files:read` scope: an install without it answers `slack_reauthorize_required`, and the owner re-installs the app ([owner setup](/internal/channel-apps-owner-setup)). |
| Email | Inbound mail attachments are not kept yet: mailflare's inbound webhook carries no attachment list, and that path belongs to the mail rail. Outbound email attachments are kept like the others. |

A message that is only a file (no text) arrives as `[file: name]` so it still reaches a thread and the bot sees that something came. Up to 5 files per message; a platform retry of a message already logged is not downloaded again.

## Teams proactive messages

Not built. Starting a Teams chat with someone the bot has no conversation reference for needs the two-tenant proactive-messaging spike, which needs a second Microsoft tenant to test against. Until then the start route answers `409 no_conversation_reference`: "Teams only lets the bot message a conversation it already has a reference for. Have the person install or message the bot in Teams first."

## Vendor bots

A vendor bot's `post_message` tool (see [Vendor bots use your phone](/guides/vendor-bots-use-your-phone)) calls this same start path with the directing bot, so every rule above, the channel policy and approvals apply. A refusal comes back as one plain sentence (for example "Telegram bots can only message a person who has messaged the bot first."), and a send that needs approval says "That needs the owner's approval in Allternit first."

## Mail threads

```http
GET /api/v1/mail/threads?botId={botId}&folder=inbox|needs_ok|sent
```

```json
{ "threads": [
  { "id": "bt_…", "subject": "Pricing", "from": "pat@example.com", "preview": "…", "at": "2026-10-02T09:00:00Z", "unread": true },
  { "id": "mail:email-out-…", "subject": "Quote", "from": "scout@bots.allternit.com", "to": "pat@example.com", "preview": "…", "at": "2026-10-02T12:00:00Z", "unread": true, "needsApproval": true }
] }
```

- `inbox`: mail the bot received, one entry per sender and subject (without `Re:`), newest first. `unread` is true until the bot's reply was sent or is waiting for approval. Mail dropped by the loop guards is left out. `id` is the bot's thread when one exists.
- `needs_ok`: outbound mail waiting for approval. `id` is the review thread; approve or reject it with `POST /api/rails/mail/decide`.
- `sent`: mail that went out.

An invalid `folder` is `400 invalid_folder`.
