For developers building on Allternit's messaging channels. User docs: [Messaging channels](/guides/messaging-channels), [Calls and texts in threads](/guides/calls-and-texts).

## Thread events

A channel conversation is an ordinary bot thread whose event log carries `channel.*` events. The app folds them with `foldChannelEvents` (`src/lib/gateway/channel.ts`) into `ChannelMessage[]`; the thread's `ChannelConversationBinding` says which provider and whether the bot may reply.

| Event | Meaning |
| --- | --- |
| `channel.message.received` | An inbound message from the platform. |
| `channel.message.sent` | An outbound bot message. Includes `postingIdentity` and `relayed` when the platform cannot post as the exact bot. |
| `channel.message.delivery` | Delivery state: `pending`, `unconfirmed`, `sent`, `delivered`, `read`, `failed`. |
| `channel.message.edited`, `channel.message.deleted` | The platform edited or deleted a message. |
| `channel.reaction.updated` | A reaction was added or removed. |
| `channel.bot.unavailable` | A bot was `@mentioned` but is not switched on for this connection. Payload: `botId`, `botName`, `accountId`, `provider`, `remoteId`. The UI renders the **Turn on** card; the button calls `PUT /api/v1/gateway/bots/{botId}/channels/{accountId}` with `{ enabled: true }`. |

Events carry `ts`, optional `author` (`human`, `allternit_bot`, `vendor_agent`), `replyToId`, `mentions`, `files`, and for email `subject`, `from`, `to`, `cc`.

### Bot channel routes

| Route | Use |
| --- | --- |
| `GET /api/v1/gateway/bots/{botId}/channels` | A bot's connections: `enabled`, `isDefault`, `botCount`, `defaultBotName`. |
| `PUT /api/v1/gateway/bots/{botId}/channels/{accountId}` | Body `{ enabled, isDefault? }`. Returns the updated list. |

## Call events

Frozen contract between the voice engine and messaging (`HANDOFF-realtime-voice-2026-10-02.md` §4.1). Events use camelCase, a `call.*` prefix, a `callId` in every payload, and the idempotency key `call:<callId>:<type>:<n>`. `foldCallEvents` (`src/lib/gateway/call.ts`) turns them into `CallModel[]`.

| Event | Payload |
| --- | --- |
| `call.started` | `direction`, `from`, `to`, `numberId` |
| `call.transcript.delta` | `speaker` (`caller`, `bot`, `human`), `text`, `final`, `segmentId`. Only `final: true` is persisted; interim text is live only. |
| `call.dtmf` | `digits`, `from` |
| `call.state.changed` | `held`, `mutedBot`, `mutedCaller`, `speaker`. The acknowledgement of every control. |
| `call.transferred` | `to`, `mode` (`cold`/`warm`), `ok`, `reason?` |
| `call.takeover` | `by`, `active` |
| `call.voicemail.detected` | `action` |
| `call.ended` | `durationSec`, `reason`, `recordingRef?` |

Tool use during a call reuses the `agent.tool.*` events.

### Call controls

`POST /api/v1/voice/calls/{callId}/control` with `{ action, target?, digits?, to?, mode? }`, where `action` is `hangup`, `mute`, `unmute`, `hold`, `resume`, `dtmf`, `transfer`, `takeover`, `listen` or `release`. The UI renders the state from `call.state.changed`, never from the request. `listen` and `takeover` return a LiveKit `{ token, url, room }` (receive-only and publish-capable respectively) for `joinCallAudio`.

### Components

`CallScreen`, `CallCard` and `SmsThread` (`src/components/gateway/phone/`) take plain data and injected callbacks so a phone connector's MCP App can mount them. Props: `src/components/gateway/phone/README.md`. In the phone shell, `phone.css` makes the call screen and connect wizards full-screen sheets, keyed on `.phone-root` and the `data-call-screen`, `data-connect-wizard`, `data-coming-soon`, `data-wizard-footer`, `data-call-card`, `data-sms-composer` and `data-off-bot` attributes; do not rename those without updating `phone.css`.

## Connect API

`src/lib/gateway/connect-api.ts` is the typed client for the wizards. `createConnectApi(http, cloud, runtimeId)` takes the runtime `HttpLike`, a cloud fetch (`cloudApiFetch`, the signed-in token) and the current runtime id; `connectApi` is the default instance. Each wizard calls the route that implements it:

| Wizard | Routes |
| --- | --- |
| Phone | Cloud `/api/v1/phone/numbers/*` (search, buy with `runtimeId` + `botId`, `registration`, `registration/otp`, `port`); availability from the public `GET /api/v1/channels/availability` |
| Telegram (managed bot) | Runtime `GET /api/v1/gateway/channel-accounts/telegram/managed/available`; cloud `POST /api/v1/channel-onboarding/telegram` and `GET …/:id`. Without the manager bot the wizard falls back to the BotFather token form. |
| Slack | Cloud `GET /api/v1/channels/slack/install` (the Add to Slack link), then runtime `POST /api/v1/gateway/channel-accounts/slack` records the installed workspace (idempotent; 404 until the install lands) |
| Email | Runtime `GET /api/v1/agent-email/status`, `POST /api/v1/agents/:id/identity/email` (the bot's address; `DELETE` then `POST {localPart}` changes it), `PATCH /api/v1/agents/:id` with `identityChannels.email.{replyMode, replyAllowlist}` (`approve` / `auto_known` / `auto`; other email fields are kept) |
| Discord | Cloud `POST /api/v1/channels/discord/install {runtimeId}` (the Add to Discord link), then runtime `POST /api/v1/gateway/channel-accounts/discord {guildId?}` reads `GET /api/v1/channels/discord/installs` and records the server as an app-mode connection (idempotent; 404 until the install lands). Bots answer where they are mentioned. Channel picker: cloud `GET /api/v1/channels/discord/installs/:guildId/channels` (text and announcement channels in position order, each `{id, name, selected}`, plus `allChannels`) and `PUT …/channels {channelIds}` (empty = every channel, also ones made later). Messages from other channels are dropped at the cloud and never reach the runtime; a thread counts as its parent channel; DMs and slash commands are not filtered. 404 `discord_not_installed` for a server that isn't the caller's. |
| Teams | Cloud `POST /api/v1/channels/teams/connect` (Microsoft sign-in URL; the callback records the tenant). Then runtime `POST /api/v1/gateway/channel-accounts/teams {runtimeId}`: points the owner's tenants at this computer (cloud `POST /api/v1/channels/teams/register`), reads cloud `GET /api/v1/channels/teams/installs`, and records the `teams-app:<owner>` connection (404 `not_installed` until the sign-in lands). |
| WhatsApp Business | Cloud `POST /api/v1/channels/whatsapp/connect {runtimeId}` returns a hosted signup page (`/channels/whatsapp/signup?state=`, 30-minute one-time state) that runs Meta's Embedded Signup with Facebook's SDK and completes it (`POST /channels/whatsapp/signup/complete`). Then runtime `POST /api/v1/gateway/channel-accounts/whatsapp {runtimeId}` reads cloud `GET /api/v1/channels/whatsapp/accounts` and records each number routed to this computer, with its relay secret sealed as the account's `appSecret`. Replies go through cloud `POST /api/v1/channels/whatsapp/send`, which accepts the computer's device credential. `whatsappModes()` reports `business` from `GET /api/v1/channels/availability`; the personal (linked device) path stays off. |

A 404 or 503 on a read means the provider's backend isn't there: availability calls resolve to "not available" and the wizard shows its **Coming soon** panel. Company domains for bot email are not built yet; the wizard says so instead of failing. There is no test-message button: a test needs a conversation to send to, so the done step tells people to message the bot on that channel. The email wizard has no test button: it tells people to email the address from their own inbox.

| Area | Methods |
| --- | --- |
| Telegram managed bots | `telegramManagedAvailability`, `createManagedTelegramBot`, `managedTelegramStatus`, `cancelManagedTelegramBot` |
| Email | `emailStatus`, `saveEmailSettings` (`replyMode`: `approve`, `known`, `auto`; `allowlist`), `getEmailSenders(botId)`, `saveEmailSenders(botId, {senderPolicy, allowedSenders})`, `setEmailDomain`, `emailDomainStatus`, `changeEmailAddress(botId, localPart)` |
| Phone numbers | `phoneAvailability`, `searchPhoneNumbers`, `buyPhoneNumber`, `submitPhoneRegistration`, `phoneRegistrationStatus`, `portPhoneNumber` |
| Discord, Slack, Teams, WhatsApp | `startChannelConnect(provider, { botId })`, `channelConnectStatus`, `cancelChannelConnect`, `teamsAdminLink`, `listConnectChannels(provider, guildId)`, `saveConnectChannels(provider, guildId, channelIds)`, `whatsappModes`, `startWhatsAppPersonal` |

Wizards live in `src/components/gateway/connect/`. `ConnectWizard` is the shared step engine (intro, action, form, waiting, code, done); each provider supplies its steps. `ConnectWizardDialog` maps a provider to its wizard and is mounted by `MessagingConnectorsSection` and `BotMessagingToggles`.

## Sender allowlist

Who may make a bot act by messaging one of its channels (`channel_auth.rs`, migration V244). Every inbound binding has `senderPolicy` (`owner` or `anyone`) and `allowedSenders` (a list of platform user ids, phone numbers or email addresses; compared case-insensitively, `@` and phone formatting ignored).

| Binding | Where it's set | "Owner" means |
| --- | --- | --- |
| Messaging connection (Telegram, WhatsApp, Discord, Teams, the Slack app, SMS, phone numbers for calls) | `PATCH /api/v1/gateway/provider-accounts/:id {senderPolicy?, allowedSenders?}`; both are returned on the account | the owner's verified identity on the account (`factory_owner_identities`, the `verify <code>` pairing) |
| Bot email | `GET`/`PUT /api/v1/agents/:id/identity/email/senders` (`ownerAddress` in the response), or `identityChannels.email.{senderPolicy, allowedSenders}` on `PATCH /api/v1/agents/:id` | the owner's account email |
| Slack channel bound through `POST /api/v1/agents/:id/slack-channels` | the same body: a new binding must send `allowedSenders` (Slack user ids) or `senderPolicy: "anyone"`, else 400 | nobody (list only) |
| Slack channel with no binding (the shared default agent) | `ALLTERNIT_SLACK_DEFAULT_ALLOWED_SENDERS` (comma-separated Slack user ids, `*` for everyone; unset = nobody) | — |

New bindings default to `owner`; bindings that existed when V244 ran were set to `anyone` with a `backfilled_open` audit row. A refused sender gets no bot turn and an audit row in `channel_sender_audit` (`rejected`). On a messaging connection they also get one reply naming their id (once per sender per account while the runtime runs). A refused email is acknowledged (`202 {"delivered": false, "senderNotAllowed": true}`) without a reply, and a refused inbound call gets `403` from `POST /api/v1/voice/calls`. A phone number registered without a channel account has no setting and stays open (logged). Policy changes are audited as `policy_changed`. Unknown policy values fail closed.

## Phone device tools

Desktop-only. A paired Android phone is exposed to bots through the `allternit-phone` MCP server: `phone.screenshot`, `phone.tap`, `phone.type`, `phone.swipe`, `phone.open_app`, `phone.task`, `phone.sms.send` and `phone.call.dial`. `phone.sms.send` and `phone.call.dial` always require a confirmation on the computer. The device manager, adb handling and gateway are described in [A phone for your bot](/guides/phone-for-your-bot#for-developers). The renderer reaches Desktop through `window.allternit.phones` (`src/lib/phones-bridge.ts`); outside Desktop that bridge is absent and the Phones section shows "Connect a phone from Allternit Desktop."
