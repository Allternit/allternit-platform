---
title: Let your vendor bots use your bot's phone
description: Connect Claude or ChatGPT to a vendor bot so it can text, call, email and read the threads you share, through your bot's own phone and mailbox.
---

A [vendor bot](/guides/vendor-bots) does not get a phone number of its own. It borrows the phone and mailbox of the bot that directs it, and it acts through **tools**, the same way your bot does. It never drives Allternit's screens.

Because the tools go through the same paths as your bot, the same rules hold:

- **Texts and calls only reach people who contacted the number first, or whom you added as contacts.** Anyone who replied STOP stays blocked. See [Calls and texts in threads](/guides/calls-and-texts).
- **Email is always a draft.** `send_email` waits for your OK before anything is sent.
- **The daily text limit and carrier registration apply.** If a tool is refused, the vendor bot gets one plain sentence saying why.
- **Every message says where it came from:** "Sent by Claude via Gizzi". Calls open with that same line in their brief.

## Connect

1. In Allternit, open the vendor bot and look under **Use the phone**. See [Vendor bots on your bot's phone](/guides/vendor-bots-on-the-phone).
2. The vendor bot uses the phone and mailbox of the bot that directs it. If exactly one of your bots has a phone number, that is the one. With more than one, a developer sets it with the connector API below until the app offers a picker.
3. Copy the connector address, which looks like `https://mcp.allternit.com/mcp/bots/<vendor bot id>`.
4. Add it where the vendor lets you:
   - **Claude:** Settings → Connectors → **Add custom connector**. Paste the address and sign in to Allternit when asked.
   - **ChatGPT:** turn on developer mode, then add the address as a connector and sign in to Allternit when asked.
   - **Grok:** Grok has no custom connectors, so Gizzi relays instead: ask Gizzi to pass the message to your bot.

Under **Use the phone** you can see each app that has used the connector and when. **Revoke** cuts one off at once: its next call is refused.

**The address works from anywhere.** Claude and ChatGPT reach `mcp.allternit.com`, which is hosted by Allternit, not by your computer. Your computer doesn't need to be reachable from the internet. When a call comes in, Allternit checks the sign-in, finds the computer your bot lives on (Desktop or cloud computer), wakes it if it is asleep, and passes the call through. If that takes longer than about 25 seconds, or the computer is offline, the app gets a plain message, "Your Allternit computer is offline; it will be woken — try again in a minute", and you can ask again.

## What the vendor bot can do

| Tool | What it does |
| --- | --- |
| `list_threads` | Lists the conversations it can see, optionally by channel or search word. |
| `read_thread` | Reads the latest messages of one of those threads. |
| `send_text` | Texts a number from your bot's phone. |
| `start_call` | Has your bot's phone call a number, with a brief. |
| `send_email` | Drafts an email from your bot's address. It waits for your OK. |
| `post_message` | Starts a conversation on a messaging channel through your bot. |
| `ask_bot` | Hands off to your bot and returns its reply. |

**Their view.** A vendor bot sees only threads it is attached to, plus threads you share with it. Sharing a thread adds it to that view (a developer shares it with the connector API below). Your bot's other conversations stay private.

Everything works the same on Desktop, the ai.allternit.com phone layout and the m.allternit.com app.

## For developers

**Endpoint.** `POST /mcp/bots/:vendorBotId` (MCP Streamable HTTP, JSON-RPC, protocol `2025-06-18`) is served in two places:

- **Public edge, cloud-api** (`cmd/allternit-cloud-api/src/routes/mcp_edge.rs`), at `api.allternit.com` and `mcp.allternit.com`. Both hosts use the same paths, with no prefix change. This is what Claude and ChatGPT call. It also serves the agents server (`POST /mcp/server`, `POST /mcp`) and the `.well-known` documents below. `GET` on a connector path answers `405` with `Allow: POST` after the token is checked.
- **Runtime, allternit-api** (`cmd/allternit-api/src/mcp_vendor_bots.rs`, next to the agents server in `mcp_agents.rs`), for a signed-in session on the computer itself. The edge never sends the OAuth token here.

**How the edge forwards.**

1. It verifies the Clerk token: signature, issuer, expiry, `aud` equal to the connector's URL, and the scope (`bots:act` for a bot, `agents:read` for the agents server). Nothing is forwarded until all of that passes.
2. It lists the token owner's paired runtimes (connected ones first, then most recently seen) and calls `POST /webhooks/mcp-edge/bots/:vendorBotId` on the first. The call goes over the signed runtime relay (`x-allternit-runtime-sig`, `x-allternit-runtime-ts`, `x-allternit-owner` = the verified user, `x-allternit-mcp-client` = the OAuth client), and the relay wakes a sleeping computer. The runtime accepts only that signature, and only as the owner it is paired as; its own owner checks, revoked-client check and audit run unchanged.
3. A runtime that doesn't hold the bot answers `404 {"error":"not_found"}` and the next runtime is tried. The runtime that answered is remembered for 10 minutes. If none holds the bot the caller gets the same `404` as for someone else's bot id, so there is no way to probe for bot ids. The agents server uses only the best runtime.
4. The whole attempt, including waking a computer, has a 25 second budget. When it is exceeded, or every candidate is offline or still waking, the answer is HTTP `200` with a JSON-RPC error carrying the caller's request id: `{"jsonrpc":"2.0","id":<id>,"error":{"code":-32000,"message":"Your Allternit computer is offline; it will be woken — try again in a minute."}}`.
5. A revoked connection comes back `401` with the `WWW-Authenticate` challenge (the edge adds it, because the relay drops runtime headers).

Until `MCP_PUBLIC_URL` is set on cloud-api, every edge route answers `503 {"error":"mcp_edge_not_configured"}`. DNS for `mcp.allternit.com` and the reverse proxy in front of cloud-api are set up outside this repo.

**OAuth.** Clerk is the authorization server, as for the agents server. Protected-resource metadata is per path (RFC 9728): `GET /.well-known/oauth-protected-resource/mcp/bots/<id>` returns

```json
{
  "resource": "https://mcp.allternit.com/mcp/bots/<id>",
  "authorization_servers": ["https://allternit.com/__clerk"],
  "scopes_supported": ["bots:act"],
  "bearer_methods_supported": ["header"],
  "resource_name": "Allternit vendor bot"
}
```

An access token must have `aud` equal to that resource and the scope `bots:act`. A token minted for `/mcp/server` (`agents:read`) or for another bot is refused with `401`; a token with the wrong scope gets `403`; both carry the `WWW-Authenticate` challenge. The caller must own the vendor bot's execution binding (`bot_execution_bindings.type = 'vendor'`), otherwise the answer is `404`.

**Gates.** The tools call the paths the bot itself uses:

- `send_text` is a message in the `phone:<botE164>:<to>` thread, sent by the `sms` transport to the cloud's `POST /api/v1/channels/sms/send`. The cloud enforces opt-out, consent, registration state and the daily cap (`ALLTERNIT_SMS_DAILY_CAP`).
- `start_call` calls `POST /api/v1/phone/calls/outbound`; `403 no_consent` becomes a tool error.
- `send_email` is `send_email_for_user`, which always queues a mailflare approval.
- `post_message` calls the runtime's channel-start path (`channel_start::VendorStarter`, registered at boot), so each platform's rules, the bot's channel policy and approvals apply. A refusal comes back as one plain sentence. See [Starting conversations](/guides/starting-conversations).
- `ask_bot` is `agent_send` to the directing bot, so its approval flow applies.

**Audit.** Every `tools/call` writes a `vendor_bot_audit` row: owner, vendor bot, directing bot, OAuth client, tool, a SHA-256 hash of the arguments (never the arguments), `ok` and a short result. Migration `V220`.

**Keys page API** (signed-in owner, under `/api`):

| Route | Result |
| --- | --- |
| `GET /v1/vendor-bots/:id/connector` | `{url, metadataUrl, scopes, directingBotId, directingBotName, sharedThreadIds, connectedClients:[{id, client, firstSeenAt, lastUsedAt}]}` |
| `PUT /v1/vendor-bots/:id/connector` `{directingBotId}` | The same document, after setting the directing bot. |
| `DELETE /v1/vendor-bots/:id/connector/clients/:clientId` | `{ok:true}`. The client's next call gets `401`. |
| `GET /v1/vendor-bots/:id/connector/audit` | `{audit:[{id, client, tool, argsHash, ok, result, at}]}`, newest first. |
| `PUT` / `DELETE /v1/vendor-bots/:id/connector/threads/:threadId` | Shares or unshares a thread. |

The connector needs no environment of its own on the runtime. On cloud-api, `MCP_PUBLIC_URL` (for example `https://mcp.allternit.com/mcp`) turns the public edge on and sets the `aud` it expects. `MCP_OAUTH_ISSUER` (default `https://allternit.com/__clerk`) is the authorization server it advertises. The runtime's own `MCP_PUBLIC_URL` / `MCP_OAUTH_ISSUER` behave as before.
