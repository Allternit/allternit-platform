Interactive answers use templates owned by Allternit. The agent supplies data; it cannot change a card's layout, styling, component names or executable actions. The same renderer serves Desktop, the phone layout at ai.allternit.com, and the m.allternit.com PWA.

## How answers are laid out

The app picks one of eight writing outlines from the request: quick answer, how-to, troubleshooting, comparison, decision, plan, research brief or status report. This picker uses whole-word triggers and a fixed priority order. Response style controls the requested length.

Writing outlines are instructions to the model. A model can still omit sections. The rendered interface has a separate enforcement boundary: prose uses the app's fixed Markdown answer view, and interactive cards require a supported template and valid data. Omitting a card does not create an unrestricted UI.

Draft emails, source code, documents and other standalone artifacts keep their own formats.

## Core answer templates

| Template | What it shows |
| --- | --- |
| Quick answer | A title and text |
| Comparison | Options, their points, and an optional recommendation |
| Decision | A question and two to nine choices |
| Plan | A checklist that keeps checked items |
| How-to | Ordered steps and a verification note |
| Troubleshooting | Cause, fix steps and verification |
| Status report | Done, in progress, blocked and next |
| Research brief | Findings with HTTPS source links and open questions |
| Table | Records, headers and a source; optional read-only connector query |
| Chart | A bar, line, area or pie chart with a source |
| Form | Labelled fields and a button that sends current values into the conversation |
| Calculator | Bounded numeric inputs and arithmetic results that update locally |

A card cannot add arbitrary HTML, CSS, JavaScript or component trees. Calculator expressions support only numbers, declared inputs, and addition, subtraction, multiplication and division. Division by zero shows an explanation.

## When a template is required

In a visual-capable app chat, requests such as **Show transactions**, **Compare flights** and **Create a task board** select a template through fixed application rules. You can name any catalog entry with **Use template: task-board**. The app checks the final answer against the selected template before showing it.

A missing card, a different template or invalid data gets one correction attempt. If that also fails, the chat shows a validation failure. It does not show the rejected answer. Stopping a turn does not trigger a formatting retry.

Ordinary conversation, definition questions and code changes can use prose. Text only and an explicit request for plain text also use prose. A selected artifact output keeps its own format. Vendor app turns use the same picker and a durable gateway contract. Group turns keep the real request separate from room history. Replies are validated before transcript and event publication; unsupported vendor output fails visibly rather than becoming a prose fallback.

Required-template enforcement needs both the updated app and an updated paired Gizzi runtime. Keep Desktop, the web app and the PWA on the coordinated release; an older runtime does not gain this response policy from a browser refresh.

On Desktop, use **Allternit Desktop → Check for Updates**, then quit and reopen the app after the runtime has downloaded. Save work and let active turns finish first. Cloud computers apply a staged runtime when Gizzi is idle. Refresh the web app or PWA after updating its paired runtime.

## Local controls and recovery

Calculator and numeric form fields keep your draft as you type. Empty, non-finite, out-of-range and step-invalid values show an inline error. Calculator results are hidden until all numeric fields are valid. A form cannot submit invalid numeric values. Only valid values enter saved calculation state; unfinished drafts stay in the mounted card.

Task boards let you move tasks between supplied stages and mark them complete in the card. Undo restores the last local change and returns keyboard focus to that task. These changes stay with the card and do not update an external task service. The current board state survives reload; the temporary Undo history does not.

Flight cards start without a selection. Choose a flight, then use **Discuss selected flight** to send its supplied details into the conversation. This does not book a flight. The selected option survives reload. A failed send keeps the choice and offers a retry; a pending send blocks duplicate actions.

## How long answers are laid out

Long prose stays in the fixed answer view, with Markdown headings, source links and tables. Length does not make a reply an artifact. Interactive template layouts do not change with model verbosity.

## Streaming, empty data and errors

A streaming card holds a fixed loading state until its JSON envelope is complete. Partial inputs and queries do not mount. Empty datasets get the template's empty view.

The app and server check the version, template ID, field types, limits, table dimensions, chart dimensions, input IDs and calculation references. An invalid card gets readable fallback text and diagnostics. It cannot run as a custom layout. Saved legacy OpenUI programs remain available as readable text.

The bridge checks completed cards and stores diagnostics with the message. A failed card can add one bounded repair note to the next agent turn. This is not a silent second model call or a guarantee that the agent will correct it.

## Controls and saved state

Sliders, form fields and checklists update locally. Choosing a decision option or submitting a form sends the current choice or values as the next message. A form does not directly perform connector writes.

Chat cards retain per-card state on the device and, when the transcript supports it, with the stored message. Pending transcript saves flush when a card closes. Opening a valid card as an artifact carries the current inputs into its versioned data. Owners and editors save later input changes as artifact versions. Read-only viewers keep local changes.

## Connected data

The table template can query a connected tool marked read-only. Tool names and argument schemas come from the user's connectors. The runtime checks read-only status again before execution. Connector permissions still apply.

Writes use the product's existing approval flows, such as ops-sheet actions. A card cannot supply a model-written Mutation or Action expression.

## Custom apps

A requested game, canvas or simulation can still be a custom sandboxed app. Its reply first shows a fixed preview card. No model markup or script runs until the user selects **Run app**. Changed app source requires another click. Partial apps cannot run.

The existing sandbox, network restrictions and heartbeat watchdog still apply after activation. An app fence cannot bypass the default answer-template renderer.

## Design

Design previews use the same validated answer envelopes. DESIGN.md tokens can style the application-owned components; they do not allow an agent to add layout code to a card.

## UI Forge

UI Forge lists the complete catalog with search and category filters. Selecting an entry loads its synthetic example and fixed preview. Reference-derived entries link to the inspected upstream source. UI Forge edits **Template JSON** and previews the same validated cards as chat. Its model manual lists the data contract and available read-only query tools. Invalid JSON gets the same fallback as a chat card.

## Starter examples

Artifacts → **Make something new** includes **Start from an example**. Choose one of the twelve registered starters and select **Open starter**. The app copies the registered source directly, without an agent call. Plan and organization restrictions still apply.

The HTML starters include a kanban board, regex tester, Markdown editor, JSON formatter, KPI dashboard, invoice generator, data table and budget tracker. The Mermaid starters include an ER diagram, org chart, user journey and class diagram.

Starters label their sample data. Replace it before use. The kanban and budget examples use the artifact's account storage bridge. If saving is unavailable or fails, the page states where changes are kept; it does not claim they were saved.

For the wire contract, validation boundaries and maintenance commands, see [Answer template contract](/reference/answer-template-contract).

## Catalog presentation

The prepared visual refresh gives tools compact layouts and gives evidence and explanations more reading space. Cards use a clear title, readable results and grouped supporting details. Travel views include journey routes and boarding details. Agents and people use profile cards. Products use catalogue tiles. Tasks and deals use stage boards. Transactions use a ledger, and research includes reading lists and concept relationships.

The layouts adapt to their card container, including narrow chat columns and phone screens. UI Forge uses labelled synthetic examples. Product examples show the supplied SKU, description, price and availability without invented product photographs. The visual refresh ships with the coordinated app and paired-runtime release.

## Live PR and CI cards

Connect GitHub in Settings on the selected computer. Ask “Show CI checks for https://github.com/OWNER/REPO/pull/128” or “Create a PR”. The fixed picker selects `pull-request`; the assistant gathers the real repository and PR identity. The application reads status from your GitHub connection. The model cannot supply passing checks or invented progress.

The same card refreshes every ten seconds while visible. It follows new revisions and workflow attempts, survives reopening the conversation, and shows merged or closed state from GitHub. Desktop, the web phone layout and the PWA use the same renderer and selected-computer relay. Network failures mark displayed results out of date and disable actions. Missing permissions, missing PRs and an outdated runtime produce readable errors.

Expand the card, filter All, Failed or Running, and open a check for its summary, duration and link to GitHub logs. **Ask agent to fix** sends the exact PR, observed revision and failed check to the current conversation. Normal edit, push and merge approvals still apply. The card follows results when the agent pushes a new revision; it does not claim a repair succeeded before GitHub reports it.

**Rerun failed** and **Review merge** show the repository, revision and workflow attempt before confirmation. Reruns may use billed GitHub Actions minutes. A merge changes the repository and may trigger deployment. GitHub repository protections still apply. If the revision or attempt changes, review the action again. A lost acknowledgement is not automatically retried.

The new card requires the matching runtime release. Source preparation does not deploy it.
