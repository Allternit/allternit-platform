---
title: "Add a connection"
description: "How to add one row to Settings → Connections: the client catalog entry, the cloud or runtime source, the copy, and the checks to run."
---

Settings → Connections ([user guide](/guides/connections)) is built from one registry. Adding a vendor is adding one catalog entry in the app and one source row on a server. Do not build a connect screen for it. The page, the sheet, the model picker, the first-run setup, iOS and `gizzi connect` all read the same entry.

The contract is in [Connections API](/api/connections).

## 1. Add the catalog entry

The client catalog is `src/components/connect-kit/registry.ts` in `allternit-ai`. It holds only what does not change per account.

| Field | Meaning |
| --- | --- |
| `id` | A stable id. The server uses the same id. |
| `group` | One of `brains`, `computers`, `phones`, `tools`, `voice`, `apps`, `channels`. |
| `name`, `logo`, `blurb` | What the row shows. The blurb is the text after "Not connected". |
| `ways` | How it connects. The first is the main way. Values: `oauth`, `code`, `paste`, `scan`, `install`, `pair`, `included`. |
| `runs_on` | `server`, `runner`, `device` or `computer`. This sets the line "Works on any device", "Runs on Allternit · no computer needed" or "Needs your computer". |
| `code_kind`, `code_url`, `code_prefilled` | For the `code` way: a device code or a link and a paste-back code, and whether the code is already in the link. |
| `saved` | Where the sign-in lives: `account`, `device` or `runner`. |

iOS and Gizzi Code keep the same ids and copy. Add the entry to the iOS list and to `gizzi connect` in the same change.

## 2. Add the server row

Account rows come from cloud-api (`connections.rs`). Rows about a computer come from allternit-api on that computer.

| The row is about | Source |
| --- | --- |
| An API key | A provider in `user_inference_keys`, with a validation call for that vendor |
| A voice key | `user_voice_keys` |
| A connector, channel or app | The connector or gateway record |
| A command-line tool on a computer | `cli_provider_detector.rs` and `provider_routes.rs`, plus a login using `cli_tools.rs` |

Rules for the row:

- Return `state` as one of `off`, `connecting`, `on` or `needs`, and nothing else.
- When it needs you, set `reason_code` from the list in [Connections API](/api/connections#reason-codes).
- If the account can't use the row now, set `available: false`, a plain `unavailable_reason`, and up to two `fallbacks` that are other row ids.
- Never return a key or token. Return only a masked tail.
- Keep the kit's routes free of `require_compute`.

## 3. Write the copy

Use plain words and the four status words only. Say what the row needs from a person, not how it works inside. Do not promise a date, a result or a limit for a vendor plan. Use the reason texts in the contract; add a new reason code only by changing the contract first.

## 4. Check it

- Run the registry through the client with the server row off, on and needs, and read each state on the page.
- Confirm a missing server row falls back to the catalog entry with `state: off`.
- Smoke-boot allternit-api after a runtime route change. `design_connector_routes.rs` already matches a `/connections` path.
- Run `python3 surfaces/docs/scripts/check_links.py` and update the [Connections](/guides/connections) guide if the new row changes what a person sees.
