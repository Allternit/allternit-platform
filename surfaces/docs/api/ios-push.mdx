title: iPhone push (APNs)
description: Native push for the Allternit iPhone app. Device token routes, APNs key setup, payload, and how taps open the app.
---

The Allternit iPhone app (`com.allternit.mobile`) gets the same notifications as [Web Push](/api/web-push): rings, missed calls, thread messages, channel messages, and every backbone event the person is notified about. cloud-api sends each one to Apple Push Notification service (APNs) as well as to the browser subscriptions. [Notification preferences](/api/notifications), quiet hours, the per-thread collapse and the hourly cap are applied once, before either transport, so the phone and the browser always agree.

It is off until the APNs key below is set. With it unset, the token routes answer `503 {"error":"apns_not_configured"}` and nothing is sent. The push pipeline itself is switched on by the Web Push VAPID keys, so both sets must be present for iPhones to get pushes. Migration `111_apns_device_tokens.sql` adds the token table and `120_ios_system_surfaces.sql` adds the device details, activity tokens, the read token and status snapshots. The Contabo deploy (`cmd/allternit-cloud-api/deploy-contabo.sh`) applies each file that is not yet listed in `ops_applied_migrations`, before it swaps the binary.

## Turn it on

Create a key in Apple Developer → Certificates, IDs & Profiles → Keys, with **Apple Push Notifications service (APNs)** enabled. Download the `.p8` file once (Apple doesn't let you download it again). Then set these on `allternit-cloud-api`:

| Variable | Value |
|---|---|
| `APNS_KEY_P8` | Contents of the `.p8` file (PEM). Literal `\n` escapes are accepted for one-line secret stores |
| `APNS_KEY_ID` | The key's 10-character id |
| `APNS_TEAM_ID` | The Apple Developer team id |
| `APNS_TOPIC` | Optional. The app's bundle id. Default `com.allternit.mobile` |
| `APNS_ENV` | Optional. `production` (default) or `sandbox`, used for a token whose app didn't say which |

One token-auth key works for every app in the team and for both the sandbox and production gateways. cloud-api signs an ES256 provider token with it and reuses that token for 40 minutes (Apple rejects tokens older than an hour and refreshing more than every 20 minutes).

## Routes

The device token and activity token routes take a Clerk session or a `compute`-scoped API key. The app calls cloud-api directly, never through the runtime relay.

- `POST /api/v1/device-tokens`:

```json
{ "token": "a1b2…(hex)", "platform": "ios", "environment": "production", "deviceId": "6F1C…",
  "osVersion": "26.1", "appBuild": "31", "capabilities": ["actions", "nse", "la_push", "widget_push"] }
```

returns `201 {"ok": true, "id": "apns_…", "readToken": "adr_…"}`. `osVersion`, `appBuild` and `capabilities` are optional; an app that sends none is registered with no capabilities and gets the plain alert. `capabilities` says what this build of the app can handle:

| Capability | Meaning |
|---|---|
| `actions` | It has the notification categories, so a push may carry buttons |
| `nse` | It has the notification service extension, so a private push may carry a generic body that the extension replaces |
| `la_push` | It registers Live Activity push tokens |
| `widget_push` | It registers a widget push token (iOS 26) |

Other values are dropped. `readToken` is new on every registration (the old one stops working) and is shown only once: cloud-api stores only its hash. The app keeps it in the shared keychain for its extensions and uses it on the [device read routes](#device-read-routes) only. `environment` is `sandbox` for debug builds and `production` for TestFlight and App Store builds; the push goes to the matching APNs host. `deviceId` is the app's `identifierForVendor`, so a reinstall replaces the old token. A token belongs to one person: registering it while signed in as someone else moves it. A person may register 10 iPhones. Errors: `400 bad_token | unsupported_platform`, `429 too_many_devices`.

- `DELETE /api/v1/device-tokens` with `{"token": "a1b2…"}` returns `{"ok": true, "removed": true}`. It also removes that device's activity tokens. The app calls it on sign-out, before the session ends.

- `PUT /api/v1/device-tokens/activity` saves a Live Activity or widget push token for a registered device:

```json
{ "deviceId": "6F1C…", "kind": "la_start", "attributesType": "BotActivityAttributes", "activityKey": null,
  "token": "…(hex)", "environment": "production" }
```

returns `201 {"ok": true, "id": "apat_…"}`. `kind` is `la_start` (the push-to-start token for one attributes type), `la_update` (the update token of one running activity, named by `activityKey`) or `widget` (the widget push token). A newer token replaces the older one of the same device and kind (and the same `attributesType` or `activityKey`). Errors: `400 bad_kind | bad_token | device_id_required`, `404 unknown_device` when `deviceId` has no device token for this person, `429 too_many_tokens` (40 per person).

- `DELETE /api/v1/device-tokens/activity` with `{"token": "…"}` returns `{"ok": true, "removed": true}`.

Registering a device token while signed in as someone else removes the previous person's activity tokens for that device.

APNs answering `410`, `BadDeviceToken`, `Unregistered` or `DeviceTokenNotForTopic` deletes the token. Other failures are counted, and a token is removed after 8 in a row. `403 ExpiredProviderToken` makes cloud-api sign a new provider token.

## Device read routes

The notification service extension and the widgets run without the app's Clerk session. They call these two routes with `Authorization: Bearer <readToken>`. Both also take the normal Clerk session. The read token is refused (`401`) on every other route, and it only reads its own person's data.

- `GET /api/v1/status/summary` returns the latest status snapshot of each of the person's computers, newest first, or an empty list:

```json
{ "snapshots": [ { "runtimeId": "rt_1", "snapshot": { "activeBots": 2, "pendingApprovals": 1, "needsYou": ["approval:ap1"] },
                   "hash": "…", "updatedAt": "2026-11-09T18:00:00Z" } ] }
```

- `GET /api/v1/notifications/content/{eventId}` returns the text of one notification, built the same way as the push:

```json
{ "title": "Approval needed", "body": "Raven wants to: send the weekly report",
  "sender": { "name": "Raven", "avatarUrl": null }, "communication": false }
```

It answers `404 not_found` for an unknown id, another person's event, or an event that is never shown as a notification. `sender.avatarUrl` is filled only when the computer's event carries an `https` avatar URL. `sender.avatarUrl` is also read from the event's `botAvatar`; cloud keeps no bot record of its own. `communication` is `true` only for a bot's direct reply (`message.received` with `senderKind: "bot"`). It is the server-side switch for iOS communication notifications (the bot shown as the sender, labelled as an assistant).

A read token that is malformed, replaced by a newer registration, or belongs to an unregistered device gets `401 {"error":"invalid_read_token"}`.

Server: `cmd/allternit-cloud-api/src/routes/device_read.rs`.

## Other push types

`apns::send_raw` sends any APNs push type to one token: `background` to a device token, `liveactivity` to an activity token (topic `com.allternit.mobile.push-type.liveactivity`), `widgets` to a widget token (topic `com.allternit.mobile.push-type.widgets`). It uses the same provider token and the same cleanup as alerts: a gone device token also takes that device's activity tokens with it.

## Payload

Each iPhone gets its own alert. It is built from the same message as the Web Push and shaped by what that app said it supports at registration (`capabilities`):

```json
{
  "aps": {
    "alert": { "title": "Approval needed", "body": "A bot is waiting for your OK." },
    "sound": "default",
    "badge": 1,
    "thread-id": "bot-<botId>",
    "mutable-content": 1,
    "category": "APPROVAL_INLINE",
    "interruption-level": "time-sensitive"
  },
  "type": "event",
  "url": "/?allternit_inbox=approval%3Aap1",
  "tag": "approval-ap1",
  "data": { "event": "approval.requested", "eventId": "…", "inboxId": "approval:ap1", "runtimeId": "rt_1",
            "botId": "…", "threadId": "…", "sessionId": "…", "contentHash": "ab12…", "senderKind": "bot",
            "private": true, "category": "APPROVAL_INLINE", "level": "needs_you" }
}
```

| Device | What changes |
|---|---|
| Any | `sound` on every alert. `thread-id` is `bot-<botId>` (the tag when the push has no bot). `interruption-level: time-sensitive` at the needs-you level and above (approvals, threads waiting on you, sign-in needed, urgent) |
| Without `actions` (apps from before the system surfaces send `capabilities: []`) | No `category`, so no buttons |
| With `actions` | `category` from `data.category` ([categories](/api/notifications#categories)) |
| Without `nse` | The full body, as before. No `mutable-content` |
| With `nse` | `mutable-content: 1`. When `data.private` is true, a generic body ("A bot is waiting for your OK.", "New message", "A bot needs your answer.", "Open Allternit to see it."). The notification extension fetches the real text with `GET /api/v1/notifications/content/:eventId` and the device read token, so private text never rides in the push |
| [Focus filter](/api/notifications#focus-filter) on and muting this alert | `interruption-level: passive`, no `sound`, `apns-priority: 5` |

`type`, `url`, `tag` and `data` are the same as in the [Web Push payload](/api/web-push#what-gets-pushed). The `data` keys are listed under [data keys](/api/notifications#data-keys). `tag` is also sent as `apns-collapse-id` (first 64 bytes), so the phone keeps only the latest of each; a push for an inbox item uses the item as its tag. Calls, urgent pages and needs-you pushes go out at `apns-priority: 10`, everything else at `5`. `apns-expiration` follows the message's TTL. The server keeps no unread count, so `badge` is `1` and the app clears it when opened. Each alert logs one line (`apns alert to <row id>: event=… category=… interruption-level=… mutable-content=… private=…`), never the text.

**Coding-session permission asks** (`source: "gizzi-permission"`) come to the iPhone through this path only. Browsers get them from the gizzi remote-control lane.

**Factory approvals** (`inboxKind: "factory_approval"`) that the runtime already pushed itself (`surfaces` holds `"push"`: its Remote Control Web Push, with the one-time approve code, reached a device) get the iPhone app push only from cloud, so a browser never gets two. When the runtime's push isn't set up (no push worker URL, not paired to the owner, no runtime id) or reached no device, `surfaces` has no `"push"` and cloud sends its Web Push as usual.

**One notification per iPhone.** A Web Push subscription with `platform: "ios-pwa"` is skipped while the same person has an iPhone registered here. A phone with both the app and the home-screen app gets the app's notification only.

## Live Activity pushes

After a changed [status snapshot](/api/notifications#status-snapshots-and-revoke) is stored, cloud merges the person's fresh snapshots (one per runtime, at most 12 hours old) and decides, per device, what to send to its activity tokens. Devices without the `la_push` capability get none. Every push is `apns-push-type: liveactivity`, topic `com.allternit.mobile.push-type.liveactivity`, under 4 KB (the `step` is cut first).

**Tokens the app uploads** (`PUT /api/v1/device-tokens/activity`):

| `kind` | `attributesType` | `activityKey` | Used for |
|---|---|---|---|
| `la_start` | `BotActivityAttributes` | (none) | Push-to-start of the bot activity (iOS 17.2+) |
| `la_update` | `BotActivityAttributes` | `summary` | Updates and end of the running bot activity |
| `la_update` | `LoopActivityAttributes` | the `loopId` | Updates and end of one loop activity (the app starts loops itself) |
| `widget` | (none) | (none) | Widget pushes (iOS 26) |

**Bot activity content state** (`BotActivityAttributes.ContentState`). The six fields the app has, always: `status`, `activityLabel`, `pendingApprovalsCount`, `activeBotsCount`, `attentionBotsCount`, `displayName` (the focus bot's name). Optional, left out when absent: `botId`, `step`, `progress` (0 to 1), `othersCount` (other active bots), `question`, `inboxId`, `runtimeId`, `sessionId`, `contentHash`, `approveInline`. No `Date` values. The focus is the snapshot `focus` that matters most across runtimes: an approval, then a question, then a blocked or failed bot, then work.

`question`, `contentHash` and `approveInline: true` ride only when the focus has `approveInline: true`, `private` is not true, a `contentHash` is present and the question is 140 characters or fewer. Otherwise `question` is a generic line ("Needs your approval", or "Needs your input" for an attention item) with no hash, and the phone shows Open only. Live Activity pushes are not encrypted, so private text never rides in them, in the content state or the alert.

Working:

```json
{"aps":{"timestamp":1794200000,"event":"update","stale-date":1794203600,
 "content-state":{"status":"working","activityLabel":"Working","pendingApprovalsCount":0,"activeBotsCount":2,
  "attentionBotsCount":0,"displayName":"Raven","botId":"b1","sessionId":"s1","runtimeId":"rt_1",
  "step":"Reading mail","progress":0.4,"othersCount":1}}}
```

Needs approval, inline (priority 10, with an alert):

```json
{"aps":{"timestamp":1794200020,"event":"update","stale-date":1794203620,
 "alert":{"title":"Raven","body":"Send the invoice to Acme?","sound":"default"},
 "content-state":{"status":"waiting_approval","activityLabel":"Waiting for approval","pendingApprovalsCount":1,
  "activeBotsCount":1,"attentionBotsCount":1,"displayName":"Raven","botId":"b1","inboxId":"approval:ap1",
  "sessionId":"s1","runtimeId":"rt_1","step":"Drafting the reply","othersCount":0,
  "question":"Send the invoice to Acme?","contentHash":"ab12","approveInline":true}}}
```

Needs approval, private: the same with `"question":"Needs your approval"`, no `contentHash`, no `approveInline`, and the alert body "Needs your approval".

**When each event goes out**

- `start` (to the `la_start` token, priority 10) carries `"attributes-type":"BotActivityAttributes"`, `"attributes":{"mode":"summary"}`, `"input-push-token":1` and an alert with `sound`. Only on idle to active (the merged snapshots had no active bot, attention or pending approval, and now do), at most once per 10 minutes per device, never while [quiet hours](/api/notifications#quiet-hours) hold the level (work is low, an approval is needs-you; default quiet hours hold both), and only when the device has no `la_update` token for the bot activity.
- `update` at priority 5 for progress, at least 15 seconds apart per device. A change inside the window is kept and sent when the window ends, the latest state winning. When the state becomes needs-approval (or a new item becomes the focus), priority 10 with an alert at once; while quiet hours hold it, no alert.
- `end` (priority 10) with the final state and `dismissal-date` 15 minutes ahead when the merged snapshots go idle. Close to 8 hours (7 h 30 min after the update token arrived) cloud ends the activity with an immediate `dismissal-date`, and the next change starts a new one. Cloud removes an update token once APNs accepts its `end`.
- `start` and `update` carry `stale-date` one hour ahead (the runtime only sends a snapshot when something changes). A [Focus filter](/api/notifications#focus-filter) that mutes the focus bot drops the alert's `sound`.

**Loop activities** (`LoopActivityAttributes.ContentState`: `iterationsCompleted`, `maxIterations`, `state`) follow `snapshot.loops` by `loopId`: `update` (priority 5, 15 seconds apart) on a change, `end` when the loop's `state` is no longer `running`, `pending`, `starting` or `paused`, or when the loop is gone from snapshots that all carry `loops` (ended as `stopped`). A snapshot without `loops` (the runtime's loop poll failed) ends nothing.

**Throttle state.** Each "last sent" time is the later of an in-memory map (every attempt) and the token row's `last_ok_at` (every push APNs accepted). After a restart the database times still hold the start, update and widget limits; only a coalesced update waiting for its window is lost, and the next snapshot carries the newer state. Each push logs one line, `live activity push: liveactivity <event> to <token row> (device …, <attributes>) priority=… alert=… bytes=…`, never the text.

## Widget pushes

When what the widget shows changes (the counts, `needsYouRows`, `paused`, `lastRoutine`), cloud sends `{"aps":{"content-changed":true}}` with `apns-push-type: widgets`, topic `com.allternit.mobile.push-type.widgets`, priority 5, to each `widget` token of a device with the `widget_push` capability. At most one per 5 minutes per device; a change inside the window is sent when it ends. A new step or progress is not a widget change. Widget pushes need iOS 26.

Server: `cmd/allternit-cloud-api/src/routes/live_activity.rs`.

## Revoke

When an inbox item leaves the runtime's `needsYou` list ([status snapshots](/api/notifications#status-snapshots-and-revoke)), cloud sends every iPhone of that person a background push (`apns-push-type: background`, `apns-priority: 5`):

```json
{ "aps": { "content-available": 1 }, "data": { "event": "notification.revoke", "tags": ["approval-ap1"] } }
```

The app removes the delivered notifications with those identifiers. It is best-effort: a force-quit app gets no background push, so the app also reconciles on every foreground. Only tags that reached at least one iPhone are revoked (`notification_delivered`).

## In the app

- Permission is asked with a reason on screen, never on first launch: in the **Meet your bots** intro's notifications step, on the empty-chat card, or in Settings → Getting started → Notifications. After that, every launch and every sign-in registers again without asking.
- Tapping a notification opens its `url`: a thread opens its current chat (or the bot's page when the thread has no live session), a channel message opens the bots, `/settings/…` opens Settings, `/computers` opens the computers list. An approval (`data.event` `approval.requested`) opens Decisions, where it can be answered, instead of its `url`.
- The app also opens [Universal Links](#universal-links) to the same screens.

Code: `surfaces/allternit-mobile/ios/Core/PushNotificationManager.swift`, `App/AppDelegate.swift`, `Core/API/PushTokenClient.swift`, `Core/DeepLinkRouter.swift`. Server: `cmd/allternit-cloud-api/src/routes/apns.rs`, called from `web_push::send_to_user`.

## Universal Links

`https://ai.allternit.com` and `https://m.allternit.com` serve `/.well-known/apple-app-site-association` (allternit-ai `public/.well-known/`, copied into the PWA build by `scripts/prepare-fabric-session-pwa.mjs`, served as `application/json`). With the app installed, these open in it:

| Link | Opens |
|---|---|
| `/b/<botId>` | The bot's page |
| `/i/<code>` | The phone invite page, in the app |
| `/settings`, `/settings/<section>` | Settings |
| any path with `?session=<id>` | That chat |

The app needs the `applinks:ai.allternit.com` and `applinks:m.allternit.com` associated domains, and the file's `appIDs` must carry the real team id (`<TEAMID>.com.allternit.mobile`).
