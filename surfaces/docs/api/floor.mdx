These routes are served by the local `allternit-api` under `/api/v1/floor`. They return the signed-in owner's bots only. Threads marked incognito are left out.

## GET /floor/state

Returns every active bot and how the floor groups them.

```json
{
  "v": 2,
  "mainBotId": "bot_main",
  "pods": [
    { "id": "chief", "name": "Chief", "color": "#2F80ED", "kind": "chief", "botIds": ["bot_main"] },
    { "id": "proj_7", "name": "Q4 report", "color": "#27AE60", "kind": "project", "botIds": ["bot_a"] },
    { "id": "team", "name": "Team", "color": "#9B51E0", "kind": "team", "botIds": ["bot_b"] }
  ],
  "bots": [
    {
      "id": "bot_a", "status": "working", "updatedAt": 1790000000000,
      "lastKind": "finished", "lastText": "Sent the draft",
      "pod": "proj_7",
      "needs": { "approval": 0, "question": 1, "suggestion": 2 },
      "lastResult": { "text": "Sent the draft", "at": 1790000000000, "threadId": "th_1" }
    }
  ]
}
```

The v1 fields (`bots[].id`, `status`, `updatedAt`, `lastKind`, `lastText`) are unchanged, so v1 clients keep working.

### Fields added in v2

| Field | Meaning |
| --- | --- |
| `v` | Always `2`. |
| `mainBotId` | The main bot: the bot flagged `botProfile.chiefOfStaff`, or one made from the primary template. `null` when there is none. |
| `pods[]` | `id`, `name` (40 characters at most), `color` (`#rrggbb`, stable for an id), `kind` (`project`, `team` or `chief`), `botIds`. A pod with no bots is not sent. |
| `bots[].pod` | The id of the pod the bot sits in. |
| `bots[].needs` | Counts of things waiting on you. `question` is the bot's threads in the needs-you state. `suggestion` is its proposed threads. `approval` is always `0` for now, because approvals are not yet tied to a bot. |
| `bots[].lastResult` | `{ text, at, threadId }` for the bot's newest finished thread in the last 24 hours (text cut to 120 characters), or `null`. |

### How pods are chosen

1. The main bot sits alone in the `chief` pod.
2. Any other bot goes to the project of its newest working thread.
3. Otherwise it goes to its first project membership, by project id.
4. Otherwise it goes to the `team` pod.

At most 8 project pods are sent, those with the most recent thread activity. Bots in the other projects fold into `team`. Pod order is `chief`, then projects by recent activity, then `team`.

## GET /floor/events

Query: `since` and `until` (ms), `limit` (default 500, at most 2000). Returns `{ "events": [...] }`, oldest first.

| `kind` | Source | Extra fields |
| --- | --- | --- |
| `started`, `finished`, `failed`, `needs_you` | Thread events | `text` when the event has a status line |
| `handoff` | A bot-to-bot hop | `toBotId`, and `label` (60 characters at most) |
| `autopilot` | An Autopilot answer or draft (see [How Autopilot answers](#how-autopilot-answers)) | `ruleId`, `need`, `outcome` (`answer` or `draft`), and `text` (120 characters at most) |

`label` is the title of the thread that received the hop. Hops that link no thread have no `label`.

## GET /floor/autopilot

Returns the Autopilot switch and its rules. With no saved settings, Autopilot is off and there are no rules.

```json
{
  "enabled": true,
  "mainBotId": "bot_main",
  "rules": [
    { "id": "r1", "scope": { "type": "all" }, "need": "question", "level": "draft" },
    {
      "id": "r2",
      "scope": { "type": "bot", "id": "bot_a" },
      "need": "permission",
      "level": "limits",
      "limits": { "maxPerDay": 5, "allowedActions": ["read_file"] },
      "note": "Files only"
    }
  ],
  "updatedAt": 1790000000000
}
```

| Field | Meaning |
| --- | --- |
| `enabled` | The switch. When it is off, every need waits for you. |
| `mainBotId` | The bot that answers for you. `null` means the floor's main bot (see `mainBotId` in `/floor/state`). |
| `rules[].scope` | `all`, or `bot` or `pod` with the bot or pod `id`. |
| `rules[].need` | `suggestion`, `permission` or `question`. |
| `rules[].level` | `draft` (Draft only), `ask` (Ask first), `tell` (Send and tell me) or `limits` (Act within limits). |
| `rules[].limits` | `maxPerDay` and `allowedActions`. Sent only when the rule has a cap or actions. |
| `updatedAt` | When the settings were last saved (ms), or `null`. |

The levels have the same names and meanings as in the autonomy guide. This route stores the settings only (see [How Autopilot answers](#how-autopilot-answers) for what acts on them). Outbound messages keep their own send policy under `/autonomy/policies`.

## PUT /floor/autopilot

Send the same shape as the GET answer (`updatedAt` is ignored). The rule set you send replaces the saved one in a single transaction, and the answer is the saved settings.

- A rule without an `id` gets one.
- A rule without a `level` gets `draft` for questions and `ask` for everything else.
- A question rule at `limits` with no `maxPerDay` gets a cap of 20 a day.
- `mainBotId`, when set, must be one of your active bots.

The request is refused with `400` and `{ "error": "<code>", "rule": <index> }` when one of the cases below applies. `rule` is the index of the rule at fault, when there is one.

| Code | Cause |
| --- | --- |
| `too_many_rules` | More than 50 rules. |
| `bad_scope`, `bad_need`, `bad_level` | A value outside the lists above. |
| `scope_id_required` | A `bot` or `pod` scope with no `id`. |
| `duplicate_rule_id`, `duplicate_rule` | Two rules with one id, or two rules for the same scope and need. |
| `max_per_day_out_of_range` | `maxPerDay` below 1 or above 200. |
| `too_many_actions`, `bad_action` | More than 20 allowed actions, or one that is empty or longer than 40 characters. |
| `note_too_long` | A note longer than 200 characters. |
| `unknown_main_bot` | `mainBotId` is not one of your active bots. |

## How Autopilot answers

When Autopilot is on, each new need from one of your bots is checked once, at the moment it arrives. The switch and rules are read fresh every time, so turning Autopilot off stops it from the next need on.

1. Autopilot off, or no main bot: the need waits for you. With no `mainBotId` saved, the main bot is your chief of staff bot, the same one `/floor/state` reports.
2. The hard floor: the need waits for you, whatever the rules say (see below).
3. The most specific rule for that need kind applies: a `bot` rule, then a `pod` rule, then an `all` rule. With no rule, the need waits.
4. The level decides. `draft` records a proposed answer and answers nothing. `ask` waits. `tell` answers and leaves a note in the thread. `limits` answers without a "tell" note while the rule is under its `maxPerDay` for today (UTC) and the action is in `allowedActions` (when that list has entries). A `limits` rule with no `maxPerDay` stops at 20 answers a day. Past a limit, the need waits.

What each need kind does when it is answered:

| Need | Answer | Notes |
| --- | --- | --- |
| `suggestion` | Goes ahead with the suggestion, exactly as if you pressed Go ahead. | Its action name for `allowedActions` is `task`. |
| `permission` | Approves that one request once. Never "always", never "for this task". | Only for requests from a bot's thread whose kind can be read with confidence (`read`, `glob`, `grep`, `list`, `webfetch`, `websearch`, `codesearch`, `lsp`, `todoread`, `todowrite`, `edit`, `write`, `skill`, `task`). Shell commands and every other kind wait for you. Approval cards from vendor agents always wait for a person. |
| `question` | Not answered yet. | Recorded as a draft. Answering needs a turn in the main bot's own session on your computer, which is not built yet. |

**Hard floor.** These always wait for you: payments, purchases and spending; signatures and contracts; deleting, removing or destroying anything; any thread that includes content from outside your team; and any bot (the one asking, or the main bot) whose envelope is tighter than **Act within limits**. Autopilot checks both the action and the words of the request, so a suggestion titled "Buy the tickets" waits even though its action is `task`.

**Audit trail.** Every answer writes a bot event `autopilot_answer` on the thread, and every draft an `autopilot_draft`, with `{ ruleId, need, text, outcome, silent, action, mainBotId }`. The text starts with "Answered by" and the main bot's name. Answers show in the digest's `answered` list.

## GET /floor/digest

Query: `since`, as RFC 3339 or epoch ms. Without it, the window starts at your last-seen time (see `POST /floor/seen`), or 24 hours ago if you have none. The window never reaches back more than 30 days.

```json
{
  "since": 1790000000000,
  "until": 1790003600000,
  "answered": [{ "botId": "bot_a", "threadId": "th_2", "text": "Chose the morning flight", "at": 1790001000000, "ruleId": "r1" }],
  "waiting": [{ "botId": "bot_a", "threadId": "th_3", "text": "Pick a venue", "at": 1789990000000 }],
  "finished": [{ "botId": "bot_a", "threadId": "th_1", "text": "Sent the Q4 report", "at": 1790002000000 }],
  "suggestions": [{ "botId": "bot_main", "threadId": "th_4", "text": "Clean up the inbox", "at": 1789980000000 }]
}
```

| List | What it holds |
| --- | --- |
| `answered` | Needs your main bot answered on autopilot inside the window. Each item adds the `ruleId` that allowed it. |
| `finished` | Threads that finished inside the window, one item per thread. |
| `waiting` | Threads waiting on you now, whatever the window. |
| `suggestions` | Proposed threads waiting for a go-ahead now, whatever the window. |

Each list holds at most 20 items, newest first. Incognito threads are left out. Apps show the digest when you were away for 30 minutes or more and at least one list has an item.

## POST /floor/seen

Stores now as your last-seen time and returns `{ "previous": 1790000000000, "now": 1790003600000 }` (ms). `previous` is `null` the first time. The time is kept on the server, so a digest you read on one device does not show again on another.
