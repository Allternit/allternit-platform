## Overview

A connected subscription runs in its own browser on the person's Sessions computer. The Allternit API forwards requests to that computer's gateway and adds the gateway token server-side. Every task that would send something through a subscription needs a **human action**: proof that a person sent or confirmed that task. Agents, tools, bots and schedules never get one on their own. They prepare the task on an approval card, and the action is created when a person approves it.

<Note>
This namespace is served by the Allternit API data-plane node (`http://127.0.0.1:8013` on the same machine, or your paired or provisioned node), under `/api/v1`.
</Note>

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/api/v1/subscriptions/human-actions` | Create a human action for a UI surface where a person starts a task directly. Needs a person's session; `chat.send` and `approval.confirm` are reserved for the platform. |
| `ANY` | `/api/v1/subscriptions/gateway/v1/...` | Forward to the gateway. `POST v1/tasks` is checked and stamped as described below. |
| `POST` | `/api/v1/subscriptions/disclosure/ack` | Record the person's acknowledgement of a provider's disclosure. |
| `GET` | `/api/v1/subscriptions/gateway/v1/lanes` | Health of each connected account: state (`green`, `amber`, `red`), last probe, last pass and drift-breaker state, from the 3-minute canary. See [Lane status](/guides/lane-status). |
| `GET` | `/api/v1/subscriptions/gateway/v1/routes` | The deterministic route router view: per vendor, the bound route, the Settings override, and every route with its eligibility and capability-contract result. See [Route router](#route-router). |
| `PUT` | `/api/v1/subscriptions/gateway/v1/routes/:vendor/override` | Pin (`{ "route": "<id>" }`) or clear (`{ "route": null }`) the route override for a vendor. `400 route_not_eligible` when the route is not eligible. |

## Submitting a task

`POST /api/v1/subscriptions/gateway/v1/tasks` with the action in the `x-allternit-human-action` header:

```json
{
  "capability": "presentation.create",
  "prompt": "A 10-slide Q3 review",
  "routing": { "provider": "chatgpt" },
  "options": { "slides": 10 },
  "idempotency_key": "my-tool-call-1"
}
```

The forwarder checks, in order: the body, the provider, the disclosure version, then the human action. The action is used up only when everything passes. It belongs to one user, expires after 10 minutes, and works once; a retry with the same `idempotency_key` may reuse it. Accepted tasks are stamped with `initiated_by: {kind: "human", user_id, action_id}`.

## Approval cards are bound to their task

When a person approves a subscription card, the action created for it can start **only the task on that card**. The card carries the task as `subscription.task`:

| Field | Description |
|-------|-------------|
| `capability` | The capability submitted. `chat.create` and `chat.continue` count as the same task. |
| `provider` | The subscription provider. |
| `prompt` | The full prompt submitted. For a provider question (`kind: "question"`) it is left out: the person's answer is the prompt. |
| `options` | The options submitted, exactly (missing = `{}`; key order does not matter). |

Submit exactly that task with the action. A task with a different capability, provider, prompt or options is refused with `human_action_task_mismatch`, and the action is not used up. The card's preview and provider are taken from `subscription.task`, so what the person reads is the start of what runs.

A card without a complete `subscription.task` (sent by an Allternit runtime from before task binding) cannot be approved: the decision returns `409 task_required`, the card stays open with that message, and the person can reject it and ask again once Allternit has updated.

## Route router

A vendor app can be driven over one of six routes, chosen deterministically — the same (vendor, eligible routes, order, override) always picks the same route, and the choice is logged with its reason. Fixed order: `android-app` → `iphone-app-ictrl` → `desktop-app-cdp` → `desktop-app-ax` → `web` → `iphone-app-usb-agent` (phones first — day-one setup with apps the person is already signed into; vision routes last — slowest).

A route is eligible only when the vendor is signed in on it, it is online, and it passed every item of the vendor's capability contract (start/continue a chat, read the streaming reply and its end, stop mid-stream, send attachments, exact text and files out, list/reopen threads, typed usage-limit/sign-out/verification-wall errors). Results are stored per app version: an app update makes a route ineligible until the conformance suite re-runs. A route that misses even one item is not offered — it never quietly does less. Phone routes report `eligible: false` with their failing items until their adapters (a follow-up task) pass conformance; nothing is assumed.

The chosen route is written into the vendor's binding. Failover to the next eligible route happens only between turns — a turn already streaming never switches. With no eligible route the turn fails typed: `NO_ROUTE` with a plain reason such as "phone offline, no other signed-in route".

`GET /v1/routes` answers:

```json
{
  "vendors": [
    {
      "vendor": "chatgpt",
      "boundRoute": "web",
      "override": "web",
      "routes": [
        {
          "route": "web",
          "eligible": true,
          "signedIn": true,
          "online": true,
          "contract": {
            "passed": ["chat.start_continue", "reply.stream_read"],
            "failed": ["attachments.send"],
            "appVersion": "1.4.0",
            "checkedAt": "2026-10-17T12:00:00.000Z"
          }
        }
      ]
    }
  ]
}
```

`boundRoute` and `override` appear only when set; `appVersion` and `checkedAt` only after the suite has run for the current app version. `PUT /v1/routes/:vendor/override` with `{ "route": "<id>" | null }` pins or clears the override — the pin still has to be eligible, otherwise `400 route_not_eligible`.

The debug-port route (`desktop-app-cdp`) is used only while the shipped app accepts its debug flag unmodified; a launch-time probe records which desktop lane applies per app version. Allternit never patches, re-signs or injects into a vendor binary — when the flag is off, the app routes through accessibility (`desktop-app-ax`) or the phone instead.

### Chats from the model picker use the same routes

A chat with a subscription model from the model picker (`subs-chatgpt`, `subs-claude`, …) is a `POST /v1/tasks` with `capability` `chat.create` or `chat.continue` and `routing.provider` set. At submission — the start of the turn — the gateway asks the same route router a bot turn asks:

- **A phone or desktop-app route** (`android-app`, `iphone-app-ictrl`, `iphone-app-usb-agent`, `desktop-app-cdp`, `desktop-app-ax`): the turn runs through that route's adapter, the same calls a bot turn makes. The task reads exactly like any other task: `task.status` `running`, `reply` events with `reply.text.delta`, then `completed` with `result.text`. `status_detail` names the route (`via android-app: …`). A later turn in the same `thread_id` continues the same conversation in the app. `POST /v1/tasks/:id/cancel` presses the app's Stop button while the reply is running.
- **The web route, or no eligible route:** the task takes the browser path as before, and that path records its own reasons when nothing can serve it.
- **A thread that already lives in a web account** stays there, because the conversation belongs to that account.

An app-route failure ends the task `failed` with a typed error. Examples: `provider_ui_changed` when the app's layout moved, `auth_required`, `rate_limited`, and `timeout` when the app never finished its reply. These errors have `fallback_eligible: true`, so the next turn can pick another route. A running turn never switches routes. Turns that a vendor adapter submits on its own were already routed when they started (`x-subs-route-chosen: 1` over the gateway's socket), so they are not routed a second time.

## Errors

| Status | `error` | Meaning |
|--------|---------|---------|
| 400 | `invalid_task`, `provider_required`, `unknown_provider` | The task body is not usable. |
| 403 | `disclosure_required` | The person has not acknowledged this provider's current disclosure. |
| 403 | `human_action_required` | No `x-allternit-human-action` header. |
| 403 | `human_action_invalid` | The action is unknown, expired, another user's, or already used. |
| 403 | `human_action_task_mismatch` | The action was approved for a different task. |
| 403 | `person_required` | A human action or card decision came from an agent or API token instead of a person. |
| 409 | `task_required` | Approving a card that does not carry its complete task. |
