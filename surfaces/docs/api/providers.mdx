# Providers

The Providers API lists available LLM providers, reports their authentication status, discovers models, and connects subscription or API-key providers through the Gizzi runtime. Provider credentials are stored by Gizzi; the API only reads connection metadata. The same routes are also mounted under `/api` without the `v1` prefix.

<Note>
Existing runtime/provider APIs expose implementation controls intentionally. The Agency API is the abstraction that hides those controls behind capabilities and one durable agent identity.
</Note>

## Base URL

```text
https://api.allternit.com/api/v1
```

For local development:

```text
http://127.0.0.1:8013/api/v1
```

## List providers

```bash
curl https://api.allternit.com/api/v1/providers \
  -H "Authorization: Bearer $TOKEN"
```

### Response

```json
{
  "providers": [
    {
      "id": "provider-a",
      "name": "Provider A",
      "provider_type": "api",
      "base_url": null,
      "api_key_set": true,
      "models": ["model-a-mini", "model-a-large"],
      "status": "active"
    },
    {
      "id": "local-brain",
      "name": "Local Brain",
      "provider_type": "local",
      "base_url": "http://127.0.0.1:11434",
      "api_key_set": false,
      "models": ["local-model:3b"],
      "status": "active"
    }
  ],
  "all": [...]
}
```

### Provider status values

| Status | Meaning |
|--------|---------|
| `active` | Ready to route requests |
| `unconfigured` | No API key or credential detected |
| `missing_key` | Binary or config present but auth missing |
| `offline` | Local or subprocess provider not reachable |
| `unknown` | Reachability not yet determined |

## Install a CLI brain

`POST /api/v1/cli-tools/:id/install` installs a CLI brain (Claude Code, Codex, Grok, Kimi, Qwen, …) on the computer this runtime runs on. Tools the Factory manages run its version-pinned installer, `allternit-factory pane harness install <tool>`, whose pins and licences come from `factory/pane/src/ao/harness/harness.json`. Other catalog tools install from the pinned recipe in the catalog (npm into the harness folder, uv, Homebrew, or an https install script). A custom tool installs with the command you gave it, and always needs `acceptTerms: true`.

Tools are installed into the harness's managed `bin/`: `~/.allternit/factory/harness/bin`, or `$ALLTERNIT_FACTORY_HARNESS_HOME/bin` if that's set. allternit-api and gizzi put that folder first on their `PATH` at startup, so the tool works right away.

On a computer without `npm`, the installer first downloads a private Node 22 from nodejs.org into the same folder and checks it against Node's published `SHASUMS256.txt`. Nothing system-wide is changed. When the install succeeds, gizzi reloads so the brain appears in the model picker.

```bash
curl -N -X POST https://api.allternit.com/api/v1/cli-tools/claude-cli/install \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"acceptTerms": true}'
```

The response is `text/event-stream`. It sends `log` events while the install runs, then one `done` event:

```text
event: log
data: {"line":"== Claude Code =="}

event: done
data: {"ok":true,"path":"/Users/you/.allternit/factory/harness/bin/claude"}
```

| Error | Meaning |
|-------|---------|
| `404 {"error":"unknown_tool"}` | This provider has no one-click install. |
| `409 {"error":"terms_required","license","termsUrl"}` | The tool's maker has its own terms (Claude Code, Cursor, Antigravity, …). Show them and resend with `acceptTerms: true`. |
| `409 {"error":"install_in_progress"}` | An install of this tool is already running. |
| `409 {"error":"install_unavailable"}` | One-click install isn't supported on this computer (Windows today). |

In `GET /api/v1/providers/auth/status`, every CLI row has an `install` object: `{available, requiresTerms, license, termsUrl, pin}`. A CLI whose binary isn't on the computer reports `status: "not_installed"`.

## Coding CLI catalog

`GET /api/v1/cli-tools/catalog` lists every coding CLI Allternit supports, whether or not it is installed, plus the caller's custom tools. It is built from one file, `cmd/gizzi-code/src/runtime/providers/discovery/cli-catalog.json`, which gizzi reads for its CLI brains and allternit-api embeds, so the list, the install recipes and the brains can't drift apart.

```json
{
  "tools": [
    { "id": "claude-cli", "name": "Claude Code", "vendor": "Anthropic", "homepage": "https://claude.com/claude-code",
      "logo": "/assets/logos-apps/claude.svg", "installed": true, "authenticated": true, "status": "ok",
      "install": { "available": true, "requiresTerms": true, "license": "Anthropic Commercial Terms", "termsUrl": "…", "pin": "…" },
      "signIn": "subscription", "custom": false, "runnable": true }
  ],
  "customAllowed": true
}
```

`status` is `ok`, `missing` (installed, not signed in), `not_installed` or `unknown`. `signIn` is `subscription`, `api_key` or `none`. `customAllowed` is `false` on a shared hosted runtime (see below).

## Add your own coding CLI

`POST /api/v1/cli-tools/custom` registers a coding CLI that isn't in the catalog. It then appears in the catalog and in `GET /api/v1/providers/auth/status?kind=cli`, installs and signs in through the same flows, and gizzi can run it as a brain.

```bash
curl -X POST https://api.allternit.com/api/v1/cli-tools/custom \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name":"My Agent","command":"my-agent","promptArgs":["-p","{prompt}"],"modelArgs":["--model","{model}"],"installCommand":"npm install -g my-agent@1.2.0"}'
```

| Field | Rules |
|-------|-------|
| `name` | Shown in Settings. |
| `command` | A bare program name or an absolute path. No shell characters, no `..`. |
| `promptArgs` | An argument array with exactly one element equal to `{prompt}`. The prompt is always passed as one argument, never through a shell. |
| `modelArgs` | Optional; must contain `{model}`. |
| `versionArgs`, `authCheckArgs` | Optional argument arrays. |
| `installCommand` | Optional. Must start with a known package manager (npm, pnpm, bun, yarn, brew, pip, pip3, pipx, uv, cargo, go, gem). Split into arguments without a shell, and it runs only after the person accepts the terms. |
| `homepage` | Optional. |

Each person can add up to 50. `DELETE /api/v1/cli-tools/custom/:id` removes one.

Custom tools run a program on the machine, so only a runtime that belongs to one person accepts them: Allternit Desktop and self-hosted installs. A shared hosted runtime answers `403 {"error":"custom_tools_disabled"}`, never runs them, and reports `customAllowed: false`.

## Connect a provider

```bash
curl -X POST https://api.allternit.com/api/v1/providers/cli-provider/connect \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"remote": true}'
```

For CLI brains, connect starts the CLI's own sign-in on that computer and keeps it running with its output captured. The sign-in link, any device code, and a "paste the code" prompt all come back in `login`, so the user can finish on any device:

```json
{
  "status": "started",
  "provider": "codex-cli",
  "label": "Codex",
  "login": {
    "url": "https://auth.openai.com/codex/device",
    "code": "ZWBG-JYPGA",
    "needsCode": false,
    "exited": false,
    "error": null,
    "hint": "If OpenAI rejects the code, turn on \"device code authorization for Codex\" in ChatGPT Settings → Security, then try again."
  }
}
```

- Send `remote: true` when the user isn't at that computer, for example a cloud computer reached through the relay. Tools with a `loginRemote` command in the CLI catalog (today Codex and Grok, `login --device-auth`) then use device-code sign-in: open the link, enter the code, and it finishes by itself. Other tools run their normal `login` command; `loginRemoteHint`, when set, comes back as `hint`. Without `remote`, the CLI also opens a browser on that computer.
- Claude Code works the same either way. The user opens the link and signs in, and the page shows a code. When `login.needsCode` is `true`, send that code to `/connect/code`.
- `login.url` and `login.code` can be `null` for the first few seconds. Keep polling `/connect/status`.
- A sign-in is stopped after 15 minutes. Starting a new one replaces any earlier one for the same provider.

### Response states

```json
{
  "status": "already_connected",
  "provider": "cli-provider",
  "label": "CLI Provider"
}
```

Possible statuses: `already_connected`, `connected`, `needs_api_key`, `not_installed`, `started`.

## Check connect status

```bash
curl https://api.allternit.com/api/v1/providers/cli-provider/connect/status \
  -H "Authorization: Bearer $TOKEN"
```

### Response

```json
{
  "status": "success",
  "provider": "cli-provider",
  "label": "CLI Provider",
  "login": { "url": "https://…", "code": null, "needsCode": false, "exited": true, "error": null, "hint": null }
}
```

`status` is `success` once the CLI reports signed in, `failed` if its sign-in ended without that (see `login.error`), and `pending` otherwise. When it succeeds, the brain becomes the default and gizzi reloads.

## Paste a sign-in code

```bash
curl -X POST https://api.allternit.com/api/v1/providers/claude-cli/connect/code \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"code": "the-code-from-the-sign-in-page"}'
```

The response is `{"ok": true}`, or `409 {"error": "no_login_waiting"}` if no sign-in is waiting for a code.

## Coding CLI accounts

A coding CLI can hold several sign-ins when its catalog entry has `accountHomeEnv`, the environment variable that points the CLI at its config folder (`CLAUDE_CONFIG_DIR` for Claude Code, `CODEX_HOME` for Codex). The default account is the CLI's own sign-in and needs no row. Each added account has its own folder, `~/.allternit/cli-homes/<id>`, so its sign-in is kept apart; a second Claude Code account gets its own macOS Keychain entry through its own config folder.

```http
GET /api/v1/providers/claude-cli/accounts
```

```json
{
  "accounts": [
    { "id": "default", "label": "Default", "identity": "me@example.com", "authenticated": true, "is_default": true },
    { "id": "a1b2", "label": "Work", "identity": "me@work.example", "authenticated": true, "is_default": false }
  ],
  "multi": true
}
```

`multi` is `false` when the CLI cannot hold several accounts; clients then hide the add button. A server without the route answers `404`.

`POST /api/v1/providers/:id/accounts` takes `{ "label": "Work" }`, creates the account and its folder, and starts the same sign-in as [Connect a provider](#connect-a-provider) with the account's folder set. The response has the same shape. `PATCH` takes `{ "default": true }` or `{ "label": "..." }`. `DELETE` removes the row and its folder; the `default` account can't be deleted. `auth/status` checks each account against its own folder.

A session, bot or brain config may carry `cli_account_id` next to the CLI provider id. The account used is the one named in the request, else the bot's, else the default. The subscription gateway's `POST /v1/tasks` accepts `routing.account_id`, which must be an eligible account of that vendor or the call fails with `409 { "error": "account_not_eligible" }`.

## Error codes

| Status | Code | Description |
|--------|------|-------------|
| `401` | `Unauthorized` | Missing or invalid bearer token. |
| `404` | `not_found` / `unknown_provider` | Provider not found. |
| `502` | `gizzi_provider_error` | Gizzi runtime returned an error for media generation. |
| `502` | `huggingface_error` | Public registry returned a non-success status. |
| `502` | `huggingface_unreachable` | Could not reach the public registry. |
| `500` | `internal_error` | Database or server error. |
