A phone approval hold stops a sensitive phone action until the phone's owner approves it. It covers every way an agent can act on a linked phone: the task loop, saved-skill replay, a bot's direct `phone.tap`, `POST /v1/phones/:serial/tool` and the MCP tools. The check runs in one place, at the Desktop's tool dispatch, and the runtime decides. For the cloud routes, see [Phones](/api/platform/phones).

## Which actions hold

A rule list runs first. It matches the label of the tapped element, and the app, against a fixed English lexicon. The model that drives a task can add a hold by flagging a step as sensitive. It cannot remove one the rules made, so text on the screen cannot talk the agent out of a hold.

A hold has one of these effects:

| Effect | Meaning |
|---|---|
| `pay` | Paying or buying |
| `delete` | Deleting or erasing |
| `send` | Sending a message or post |
| `call` | Placing a call |
| `credential` | Entering or revealing a credential |
| `money_app` | Acting inside a bank, wallet or broker app |
| `security_setting` | Changing a security setting |

These actions make a hold:

- A tap, or `phone.web.click`, whose label matches the lexicon.
- `phone.find_and_tap`, judged by the element it finds, or else by the label it searches for.
- `phone.type` into a secure field, or into a field named password, passcode, card number or CVV.
- The enter key in a message composer. It counts as `send`.
- `open_app` into a bank, wallet or broker app. One hold covers that app for the rest of the run.
- A direct tap with no element. The Desktop reads the screen once and hit-tests the point. If it has no screen read, the foreground app decides.

The label match looks at the first six words of the element's label and at its id. The lexicon is English.

Texts and calls through `phone.sms.send` and `phone.call.dial` use the same hold, as `send` and `call`. The hold is tied to the recipient and, for a text, the message: an approved hold does not cover a different number or a different text, and a retry must repeat the same `to` string.

Web tasks on an app phone (`/api/aci`) go through the same check. A hold that ends such a run shows as an error in its stream. `phone.sms.read` holds as `credential`, because texts carry one-time codes. On Desktop, the owner approves SMS read once for each bot and phone, and later reads by that bot on that phone run without a new hold. A caller that has no bot, and every API-key caller, is asked each time.

Desktop checks every acting call before it runs. If the runtime cannot be reached, Desktop fails closed: the call returns `guard_unavailable` and does not act.

## Hold lifecycle

| State | Meaning |
|---|---|
| `requested` | The hold exists and waits for the owner. The runtime stores this state as `pending`. The API shows `requested`. |
| `approved` | The owner approved it. It can be used once. |
| `denied` | The owner denied it. |
| `expired` | Nobody answered within 5 minutes, or an approved hold was used more than 10 minutes after approval. |
| `changed` | The owner approved, but the screen no longer matched. The approval is not used. |

- **Re-check after approve.** Before the action runs, the loop reads the screen again. If the element hash differs from the one the hold was made for, the hold becomes `changed` and a new hold is made. If the owner approved on the driven phone itself, the loop first returns to the app.
- **Use once.** An approved hold covers one action. It is consumed when the guard answers `allow` for it. A second use of the same hold id makes a new hold.
- **Use within 10 minutes.** A retry more than 10 minutes after approval is not accepted. The hold becomes `expired` and the guard makes a new hold.
- **Deny ends the run.** The run finishes as `denied`. The agent does not continue, because it could reach the same effect another way.

## How each caller sees a hold

| Caller | What happens |
|---|---|
| Task loop and replay | The loop waits in place for up to 5 minutes. The 300 second task budget is paused while it waits. |
| Direct tool caller (a bot, `/tool`, MCP) | The tool result is `{ "ok": false, "error": "approval_required", "approvalId", "inboxId", "expiresAt" }`. After the owner approves, retry the same call with `_hold` set to the approved hold id, within 10 minutes. |
| Cloud API | `POST /v1/phones/:serial/tool` answers `409` with code `approval_required`. |

A retry with the id of a hold that was denied answers `denied` (see the check route below). A direct call does not stay open while it waits, because the Desktop's tool call times out at 80 seconds.

## Runtime routes

These are runtime routes on the project owner's Desktop runtime. The cloud API relays the tool and task routes.

### Check an action

```http
POST /api/v1/phones/guard/check
```

Body: `serial`, `tool`, `args`, `el`, `app`, `ctx` and `holdId`. `ctx` is the caller context: `owner`, `bot_id`, `thread_id`, `session_id` and `source`. `source` is one of `chat`, `sms`, `imessage_ext`, `intent`, `voice`, `api`, `routine` or `skill`. `el`, `app`, `bot_id`, `thread_id`, `session_id` and `holdId` are optional.

It answers one of:

```json
{ "decision": "allow" }
```

```json
{
  "decision": "hold",
  "approvalId": "apr_…",
  "inboxId": "…",
  "effect": "pay",
  "expiresAt": "2026-11-10T15:10:00Z"
}
```

A `holdId` that is approved, not yet used, used within 10 minutes of approval and for the same element hash answers `allow` and is consumed. A `holdId` of a hold that the owner denied, for the same action, answers:

```json
{ "decision": "denied", "approvalId": "apr_…" }
```

A call with no `holdId` that repeats an action which already has an open hold answers with that hold, so the owner sees one item. The route answers an error when the caller has no owner to ask. The owner is always the signed-in caller, never a value in `ctx`.

The runtime's own loops pass the check an internal one-time value, `_pass`, in the tool arguments. The runtime issues it after an approval has been used, and Desktop sends it back once so the same action is not asked about twice. Callers never send it. A request that carries one is not classified: the check answers `allow` with `pass: true`, or `bad_pass` for a wrong, used or expired value, and makes no hold. On `bad_pass` Desktop drops the value, reads the screen and runs the normal check.

### Read a hold

```http
GET /api/v1/phones/holds/:id
GET /api/v1/phones/holds/:id/crop
```

The first returns the hold and its state. The second returns the review image for the hold. Despite the route name, the image is the whole screenshot taken for the hold, not a crop of the element. It is kept on the runtime, and the `crop` route serves it as `image/png` or `image/jpeg` with `Cache-Control: private, no-store`. A hold made without a screenshot has no image and the route answers `404`. Both routes need the owner's signed-in session. The image loads through the relay.

### Start a task

```http
POST /api/v1/phones/:serial/task
```

The task route takes three optional fields: `thread_id`, `session_id` and `source` (the same values as in `ctx`; `source` defaults to `api`). They ride in the task context and come back on the run report as `thread_id`, `session_id` and `source`.

Two checks run before the task touches the phone. Either one refuses the task with `403`:

```json
{ "ok": false, "status": "refused", "reason": "paused", "message": "Your bots are paused, so I didn't start this phone task. Resume them and ask again." }
```

```json
{ "ok": false, "status": "refused", "reason": "owner_only", "message": "Only you can start a phone action from a conversation. The latest message here didn't come from you, so I didn't touch the phone." }
```

- `paused`: the owner turned on the pause switch for their bots.
- `owner_only`: the thread's latest input is not from the owner (a contact, a stranger or another bot; a web page or tool result the bot read mid-turn is not counted, and the owner's own app turns record no label, so nothing since counts as the owner's). A refusal is not a hold: nothing waits in the inbox, no card is posted and the phone is not touched. A task with no thread is not subject to this rule.

Code that starts a task in process calls `phone_task::run_task_ctx(db, data_dir, ctx, run_id, serial, goal, max_steps, model)`. It applies the same checks and answers a refused task with a report of `status: "refused"` and the same `reason`.

### The phone task card

A task started on a thread posts a card on that thread and updates it as the run moves:

```json
{ "type": "phone_task", "runId": "task-9c2e…", "serial": "link:1", "goal": "Open Settings", "status": "running", "step": 0 }
```

`status` is one of `running`, `waiting_approval`, `done`, `denied`, `approval_timeout`, `phone_locked` or `failed`. A `waiting_approval` card also carries `inboxId`, the inbox item that holds the approval. The card is a `phone_task` event on the thread's bot ledger; each change is a new event for the same `runId`, and the newest event is the card's state. A task with no thread posts no card.

### The run's latest screen

```http
GET /api/v1/phones/runs/:runId/thumb
```

Answers the latest kept screen frame of the run as a JPEG, 360 px wide, with `Cache-Control: private, no-store`. A status card uses it as its thumbnail. It needs the owner's signed-in session, like the hold image. It answers `404` when the run has no kept frame, when it is not the caller's run, or when the id is unknown; it never answers `500` for these. Frames are redacted with the same screen check as the run history before they are kept.

## The hold record

A hold is an approval with authority `allternit` and action `phone.<tool>`, for example `phone.tap`. Its correlation id is `phone:<runId>:<step>`. A direct call has run id `direct`. A hold with no thread uses `phone:<serial>` as its thread id and bot id. Creating it writes an `approval.requested` event, the same as any other approval. Its `contentHash` covers the serial, app, tool, element, effect and typed text.

`detail.phone` holds:

```json
{
  "serial": "link:7f3a",
  "phoneName": "Joe's Pixel",
  "platform": "android",
  "app": "com.example.shop",
  "effect": "pay",
  "tool": "phone.tap",
  "element": { "class": "Button", "label": "Pay now", "id": "btn_pay" },
  "typedChars": 0,
  "intent": "Tap Pay now",
  "goal": "Buy the item in my cart",
  "runId": "task-9c2e…",
  "step": 6
}
```

`typedChars` appears only for `phone.type`. It is a count. The typed text is never stored.

A text or call hold also carries `to`, and a text hold carries `text`, because the message is what the owner approves. `botless` is `true` when the task had no bot; the hold is then filed under the owner's main bot so that the approval event and its notification exist, and the inbox item reads "A phone task".

## The inbox item

The hold appears in the owner's "Needs you" list as an inbox item with kind `approval` and `subkind: "phone_action"`.

- It is **Review only**. It has no inline Approve in a notification or on a row. The owner opens it and sees the review image (the screenshot) first.
- It is `private: true`. The review image and the hold detail are not put in push text, in a Live Activity or in the status snapshot's question.
- It carries `contentHash` like every approvable item, and `approveInline: false`. An iPhone notification for it shows **Review**, which opens the item, not Approve.
- The runtime enforces this. `POST /api/v1/inbox/approval:<id>/approve` with `surface` set to `notification`, `live_activity`, `widget`, `control`, `intent`, `siri` or `shortcut` answers `409 {"error":"review_required","code":"REVIEW_REQUIRED","id"}` and approves nothing. Deny (`"decision":"deny"`) is accepted from every surface.
- Approve and Deny are available on the open item, in Allternit Desktop, ai.allternit.com, the PWA, the iOS app and Gizzi Code.

## Run report

A phone run's live status can be `waiting_approval`. A run that waits keeps its concurrency slot.

Final statuses add three values to the existing ones:

| Status | Meaning |
|---|---|
| `denied` | The owner denied a hold. |
| `approval_timeout` | Nobody answered within the wait. |
| `phone_locked` | The phone was locked and the run could not continue. |
| `refused` | The run never started: the bots are paused, or the thread's latest input was not the owner's. The report has `reason` (`paused` or `owner_only`). |

New fields on the run:

| Field | Meaning |
|---|---|
| `held_ms` | Total time the run waited on holds. |
| `holds` | A list of `{ "approvalId", "effect", "state" }`, one per hold. |
| `thread_id`, `session_id`, `source` | The context the task started with. |

`duration_ms` does not include held time, so phone minutes are not billed for the wait.

## Webhooks

| Event | When |
|---|---|
| `phone.approval.requested` | A hold was created. |
| `phone.approval.resolved` | A hold was approved, denied, expired or changed. |

They follow the same delivery rules as the other phone events in [Phones](/api/platform/phones). They carry no screenshots and no crop.

## Unattended replay

A routine that replays a saved skill can reach a hold with nobody there. After the wait, the phone run ends as `approval_timeout` and the hold becomes `expired`. The routine's own run record stays `failed` with the reason `approval_timeout`. An `attention` item appears, "Routine stopped at a step that needs you", with a Retry action. While that item is open, scheduled runs of the routine are skipped; only Retry replays it. A replay has no model to choose again, so when the screen changed after Approve the replay stops as `diverged`. There is no standing permission for any effect.

## Who can approve

- A signed-in person who owns the project. Approval happens in the app.
- **API keys cannot approve.** There is no approve route for keys.
- **No approve by text.** A reply of "yes" to a text message does not approve a hold, because a text sender can be spoofed.

## What a one-task grant covers

A one-task grant lets an agent act without a hold for the rest of one task. It does not cover `pay`, `delete`, `credential` or `money_app`. Those hold even when a grant is live. Only `send` and `call` accept a live grant, and only on a thread. `security_setting` is not covered.

## Not in this version

- Labels in languages other than English. For other languages, only the model's sensitive flag and the money-app rule catch a sensitive button.
- Full coverage. An action that no rule recognises, and that the model does not flag, runs without a hold. Do not treat a hold as a promise that every sensitive action is caught.
- An owner-only rule for channel threads. A phone action that a bot starts from a channel thread is checked like any other and makes a hold when it is sensitive. Refusing phone tools on a thread whose latest sender is not the owner comes in a later version.
- An agent loop that runs on the phone itself. Holds apply to the Desktop-driven loop.
