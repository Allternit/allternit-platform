## Overview

An owner decides how far a bot may go on its own: `draft`, `ask`, `tell` or `limits`. The runtime (allternit-api) checks the policy before every outbound action. The API below is how clients read and change it. See [What your bot can do on its own](/guides/bot-autonomy) for the owner's view.

All routes are under `/api/v1` and need the owner's session.

## Levels

| `level` | Effect |
| --- | --- |
| `draft` | Nothing is sent. The send is refused with `CHANNEL_POLICY` and an `autonomy.draft` Inbox card holds the text. |
| `ask` | The send waits for an approval (`APPROVAL_REQUIRED`, HTTP 428) and an `autonomy.ask` Inbox card is created. |
| `tell` | The send goes out and an `autonomy.digest` Inbox card is added. |
| `limits` | The send goes out silently while inside `limits`; past them it behaves like `ask`. |

The action `payment` is held at every level except `draft`, which keeps it a draft.

## Scope and precedence

A policy has `botId`, `channel` and `person`. Each can be empty, which means "all". `channel` is a provider (`telegram`, `slack`, `email`, `sms`, `call`, ...) or a class: `email`, `sms`, `call`, `chat` (every other provider). The most specific match wins: person, then bot, then provider, then class, then everything. With no match the default applies: `email` is `ask`, `sms` and `call` are `tell`, `chat` is `limits` with `maxMessagesPerDay: 200`.

## Endpoints

### `GET /autonomy/policies?botId=<id>`

```json
{
  "policies": [
    { "id": "pol_1", "botId": "bot-1", "channel": "email", "person": "", "level": "ask",
      "limits": { "maxMessagesPerDay": null, "maxSpendCentsPerDay": null, "allowedActions": ["message", "call"] } }
  ],
  "defaults": [{ "channel": "email", "level": "ask", "limits": { "maxMessagesPerDay": null, "maxSpendCentsPerDay": null, "allowedActions": ["message", "call"] } }],
  "levels": ["draft", "ask", "tell", "limits"]
}
```

### `PUT /autonomy/policies`

Creates or replaces the policy for `(botId, channel, person)`.

```json
{ "botId": "bot-1", "channel": "telegram", "person": "", "level": "limits",
  "limits": { "maxMessagesPerDay": 50, "maxSpendCentsPerDay": 2000, "allowedActions": ["message", "booking"] } }
```

Answers the saved policy. `400` for an unknown level, `404` for a bot that is not the caller's.

### `DELETE /autonomy/policies/{id}`

`{ "ok": true }`, or `404`. The place goes back to the default.

### `GET /autonomy/effective?botId=<id>&channel=<channel>&person=<id>`

```json
{ "level": "limits", "source": "policy", "policyId": "pol_1", "limits": { "maxMessagesPerDay": 50, "maxSpendCentsPerDay": null, "allowedActions": ["message"] },
  "today": { "messages": 12, "spendCents": 0 }, "wouldHold": false }
```

### `GET /autonomy/usage?botId=<id>`

Today's actions (UTC day) by channel and outcome (`sent`, `held`, `drafted`).

## Envelope and guards

`GET /api/v1/agents/{id}/envelope` returns `{envelope, known}`; `PUT` with `{envelope}` sets it. Values: `read_only` (the check returns `Block`), `draft`, `act_after_approval`, `act_within_scope` (default). It is stored at `agents.config.envelope`.

On top of the place level, `evaluate_ctx` applies three guards that can only tighten the verdict: the envelope, the thread's `trust_floor` (a tainted thread holds every send), and egress (a secret in the text blocks and opens an `egress_held` attention item; PII, internal paths, and a destination outside `agents.config.egressAllowlist` that is not an existing counterparty hold). Every egress check is written to `egress_decisions`. A blocked send returns a `Block` verdict (HTTP 403 `egress_blocked` on email). See [Prompt injection defense](/guides/injection-defense).

## Where the check runs

| Path | Where |
| --- | --- |
| Channel replies and starts, SMS text | `channel_gateway::send` |
| Phone calls | `phone_outbound::call` |
| Email sends and bot replies | `agent_email_routes::send_email_inner` and the reply plan |
| AI app and vendor bot tools (`send_text`, `start_call`, `send_email`, `post_message`) | They run through the paths above |

Email only reads an explicit policy; with none set, the mailbox's reply mode stays in charge. A policy can tighten any email send and can loosen a bot reply to direct only on a verified domain, under the reply caps.

## Inbox cards

Held, drafted and told actions are written to `inbox_items` with `type` `autonomy.ask`, `autonomy.draft` or `autonomy.digest`. The id is derived from the correlation id, so a retry never makes a second card. `metadata` carries `channel`, `to`, `level`, `threadId` and, for holds, `approvalId`.

## One-task grants

A one-task grant lets a bot act on one thread without a new approval for the actions it names. The check runs inside `evaluate_ctx`: when the place level holds an action (Ask first, or a limit was hit) and the send's `thread_id` has a live grant covering it, the verdict becomes `Send` with a digest line, and `autonomy_actions` records an extra row with outcome `granted` and the `thread_id`. The envelope, trust floor and egress guards run after the grant and can still hold or block. `payment`, `sign` and `delete` are never covered.

`message` maps to the grant action `send`. The other grant actions are `upload`, `submit`, `booking` and `call`. ACI classes map as `FileUpload` to `upload`, `FormSubmit` to `submit` and `Payment` to `payment`.

`channel_gateway::send` accepts a live `send` grant (plus `upload` when files are attached) in place of a consumed-once `gateway_approvals` row, as long as autonomy itself is not holding. Email sends on a bot thread under a grant skip the review step. Calls pass their thread, so a `call` grant and the trust floor apply to them too.

### `GET /task-grants?thread_id=<thread>`

Live grants on a thread the caller owns: `{ grants: [...], actions: [...], grantedCount }`. `actions` is the union shown in the header chip. `grantedCount` is the number of `granted` outcomes on the thread.

### `POST /task-grants`

`{ threadId, actions: [...], sourceRef? }`. A grant from a card. Needs a person's session proof (the `X-Allternit-Human-Proof` header or a Clerk session token), because an agent authenticates as its owner too. Without one the answer is `403 person_required`. A second card grant on the same thread adds its actions to the live one.

### `POST /task-grants/words`

`{ sessionId, actions: [...], quote, messageId? }`. Called by gizzi's `grant_task_permission` tool. `quote` is the owner's latest non-synthetic message, read by the tool from the session store. Refused with `403` when the thread's trust floor is tainted, when the latest labelled input on the thread is not the owner's, when the quote contains an untrusted fence, or when an action is not named in the quote. Only `send`, `upload`, `submit`, `booking` and `call` can be granted this way.

### `DELETE /task-grants/{id}`

Revokes one grant. The thread close-out hook calls `task_grants::revoke_for_thread` on resolve, archive and pause. Both also clear gizzi's session rules through `POST /permission/task/{sessionID}/clear`.

### Approval cards

`cowork_approvals` content for a gizzi permission ask carries `grantKey` (the grant action) and `scopes` when the class may be granted. It is never set for `subscription`, `mcp_app`, payment, sign or delete classes. The same `grantKey` rides on the `tool_permission` SSE metadata. `POST /cowork/approvals` accepts `scope: "task"`: with a person's proof it relays reply `task` to gizzi and records a `card` grant for the session's thread. Without proof it counts as once. `scope: "always"` relays gizzi's project-scoped `always` when the card has `always` patterns.

In gizzi, reply `task` adds session-scoped allow rules that are never written to disk and are dropped when the session is deleted or the thread closes. It counts as once for always-ask classes and for payment, sign and delete classes.

The plan card's answer **Approve plan and allow its sends and uploads**, sent with a person's proof to `POST /questions/{id}/reply`, records a `card` grant for `send` and `upload` on the plan's thread.

## Storage

Runtime migration `V233__autonomy_policies.sql`: `autonomy_policies` (the settings) and `autonomy_actions` (what was done, used for the daily limits). `V276__task_grants.sql` adds `task_grants` (one-task grants, `actions_json`, `source` `card` or `words`, `expires_at` 7 days out, `revoked_at`) and `autonomy_actions.thread_id`. All three are in the runtime database. There is no cloud-side table.
