Settings → Connections ([user guide](/guides/connections)) is built from one list of rows. Two servers answer it, and the app merges the answers. This page is the contract (version 1). To add a row, see [Add a connection](/build-on-allternit/add-a-connection). Older endpoints that still back parts of the page are in [Older endpoints and Desktop bridge](#older-endpoints-and-desktop-bridge).

## GET /api/v1/connections

Session auth only. A platform API key gets `403`.

Two servers answer the same path:

- **cloud-api** returns the account's rows.
- **allternit-api** on the active computer returns the rows that live on that computer, with `source: "runtime:<runtime_id>"`.

The client merges both lists. A runtime row replaces a cloud row with the same `id` only when its `state` is `on`.

```json
{
  "version": 1,
  "connections": [{
    "id": "anthropic-key",
    "group": "brains",
    "state": "off",
    "found": "Key works · Claude models",
    "reason": null,
    "reason_code": null,
    "runs_on": "server",
    "available": true,
    "unavailable_reason": null,
    "fallbacks": [],
    "terms": "cleared",
    "saved": "account",
    "models": ["anthropic/claude-sonnet-…"],
    "source": "cloud"
  }]
}
```

| Field | Meaning |
| --- | --- |
| `id`, `group` | The row's id and group. Groups are `brains`, `computers`, `phones`, `tools`, `voice`, `apps`, `channels`. |
| `state` | `off`, `connecting`, `on` or `needs`. The row text is "Not connected · blurb", "Connecting…", "Connected · found" and "Needs you · reason". |
| `found` | What was found, for example a plan name or "Key works". Set when `state` is `on`. |
| `reason`, `reason_code` | Why a row needs you. `reason_code` is one of the [reason codes](#reason-codes). |
| `runs_on` | `server`, `runner`, `device` or `computer`. |
| `available` | `false` when this account can't use the row now. |
| `unavailable_reason` | The plain line shown when `available` is `false`. |
| `fallbacks` | Up to two row ids to offer instead. |
| `terms` | The vendor-terms status the server holds for the row: `cleared`, `pending` or `blocked`. |
| `saved` | Where the sign-in lives: `account`, `device` or `runner`. |
| `models` | Model ids the row adds, when it has any. |
| `source` | `"cloud"` or `"runtime:<runtime_id>"`. |

Clients ignore ids they don't know. An id missing from the response falls back to the client catalog with `state: "off"`.

Coding tools and the local brain are `available: false` on cloud-api when no computer is online, with the reason "Runs on a computer." and the fallback `this-mac`. Their live state comes from the runtime.

## Actions

| Call | Body | Returns |
| --- | --- | --- |
| `POST /api/v1/connections/{id}/connect` | `{ "way"?: string }` | `{ "login": … }`, or `{ "state": "on" }` for ways that finish at once |
| `POST /api/v1/connections/{id}/submit` | `{ "value": string }`, a pasted key or a paste-back code | The updated row |
| `GET /api/v1/connections/{id}/login` | none | `{ "status": "pending" \| "done" \| "expired" \| "failed", "row"?: … }` |
| `DELETE /api/v1/connections/{id}` | none | `204`. Removes the connection from the account (cloud) or from that computer only (runtime). |

Clients poll `/login` every 2 seconds and stop on `done`, `expired` or `failed`.

### The login object

```json
{
  "login": {
    "kind": "device_code",
    "code": "KQ7M-24TX",
    "url": "https://example.com/device",
    "url_with_code": "https://example.com/device?user_code=KQ7M-24TX",
    "expires_at": "2026-11-13T12:00:00Z",
    "poll": true
  }
}
```

| `kind` | What the client shows |
| --- | --- |
| `device_code` | A code and a link. The code can already be in `url_with_code`. |
| `link_paste` | A link, then a field for the code the vendor shows. The code goes to `submit`. |
| `oauth` | A redirect to the vendor and back. |
| `browser_redirect` | Desktop's ChatGPT device sign-in: open the authorize URL, then poll status. It finishes by itself. |
| `paste` | A field for a key. The key goes to `submit`. |
| `scan` | A QR code for the phone. |
| `pair` | A one-time code. |

### Keys

- A key is checked with the vendor before it is stored: OpenAI `GET /v1/models`; Anthropic `GET /v1/models` with `x-api-key` and `anthropic-version`; Google `GET /v1beta/models?key=`; xAI `GET /v1/models`; OpenRouter `GET /api/v1/key`.
- A `401` from the vendor sets the row to `needs` with `key_rejected`.
- Keys are stored with AES-GCM through `CredentialCipher`, the same pattern as `inference_keys.rs`.
- The API never returns a key, only a masked tail.

### Logins on a computer

`connect` for `codex`, `grok-cli`, `kimi-cli` and `claude-code` reuses `start_login_with_env` in `cli_tools.rs` and the `login_remote` argv. The runtime polls the tool's own status and reports it from `/login`.

| Tool | `login.kind` |
| --- | --- |
| Codex | `device_code` |
| Grok | `device_code`, with `url_with_code` |
| Claude | `link_paste`. `submit` takes the pasted code. |

## Plan runner rows

`claude`, `chatgpt`, `grok` and `kimi` run on a private box per person on an Allternit server. The box runs the vendor's command-line program, the person signs in to the vendor themselves, and only messages the person sends go to it. Send `GET /api/v1/connections?caps=runner` to get these rows as available. Unknown `caps` values are ignored.

On these rows:

| Field | Value |
| --- | --- |
| `runs_on` | `"runner"` |
| `terms` | `"pending"` |
| `disclosure` | `{"version": "2026-11-14.1", "accepted_at": null}` before the person accepts, an ISO 8601 UTC string after. A new `version` makes `accepted_at` null again. |
| `models` | `plan/<vendor>/<model>` ids, listed only while `state` is `on`. |
| `person_only` | `true`. Keep any model with this flag out of bot, routine, schedule, mission and sub-agent pickers. |
| `source` | `"cloud"` |

States: `connecting` while the box wakes or a sign-in is pending; `on` with `found` set to the plan when known; `needs` with `login_expired` or `vendor_limited`; `could_not_start` when the box fails to create.

The sign-in kind per vendor: Codex `device_code`; Grok `device_code` with `url_with_code`; Claude `link_paste`; Kimi `device_code` if its program offers one, otherwise `link_paste`.

For `chatgpt`, the row from an online computer that reports `state: "on"` wins over the runner row. On Desktop, the iPhone app and Gizzi Code, a device sign-in (below) comes first.

### Connect and the disclosure step

`POST /api/v1/connections/{id}/connect` on a plan row takes an optional body:

```json
{ "accept_disclosure": "2026-11-14.1" }
```

| Case | Response |
| --- | --- |
| The version matches the current one, sent now or already stored for this account and vendor | `200` with `{ "login": … }` |
| The version is missing or stale and none is stored | `409` `disclosure_required` |
| The row is not offered to this client (no `caps=runner`, kill switch, vendor off the list) | `404` `not_found` |
| No box is free within a 10 second wait | `503` `runner_busy`, message "Busy. Try again" |
| The box could not be created | `502` `could_not_start`, message "Could not start. Try again" |

```json
{
  "error": {
    "code": "disclosure_required",
    "disclosure": {
      "version": "2026-11-14.1",
      "title": "Before you connect your Claude plan",
      "body": ["…", "…", "…", "…"],
      "accept_label": "I understand, connect",
      "decline_label": "Use a key instead"
    }
  }
}
```

`title` and `body` carry the vendor's display name. Show the text as given and never a copy of your own. When the person declines, open the key sheet and send nothing. Accepting stores the account, vendor, version and time; the record is kept when the vendor is disconnected and erased with the account. `submit` and `login` for a vendor with no stored acceptance return the same `409`.

`DELETE /api/v1/connections/{id}` on a plan row returns `204` after the sign-out on the box, the deletion of that vendor's sign-in files, and the removal of the row's state. When it was the person's last vendor, the box is destroyed. A failed sign-out still deletes the files and returns `204`.

### Chat with a plan model

A plan model id is `plan/<vendor>/<model>`, for example `plan/claude/sonnet`. These ids are not in the model catalog and `GET /v1/models` does not list them; take them from the `models` field of a row that is `on`. Send the turn to `POST /v1/chat/completions` as for any cloud model, with `stream: true` for OpenAI-compatible deltas. The server sends the `messages` you supply on every turn; there is no session to resume.

Set the header `X-Allternit-Turn: person` only on a message the person sent from the composer. The server removes `tools` and `tool_choice` before the turn runs, and replies carry no tool calls.

| Status | `error.code` | When |
| --- | --- | --- |
| `403` | `plan_person_only` | The token is a device token, a platform project key or a playground key; the header is missing or not `person`; or the request comes from a bot, routine, schedule, mission or sub-agent run. Other model routes (`open_lane`, platform responses, artifact runtime) return this for any `plan/…` or `copilot/…` id. |
| `403` | `plan_not_connected` | There is no connected plan row for that vendor. |
| `400` | `plan_no_tools` | A message has `role: "tool"`. |
| `409` | `plan_turn_in_flight` | A second turn for the same account while one is running. |
| `429` | `plan_rate` | More than 20 turns in 5 minutes for the account. |
| `503` | `runner_busy` | The box budget is full after a 10 second wait. "Busy. Try again" |

Plan turns are not metered against Allternit credits. A `developer` message is sent as `system`. After the turn, save the chat with the [plan chat store](#plan-chat-store) so it syncs to the person's other devices with no computer. Errors after a streamed turn starts arrive as one `data: {"error":{…}}` line, then `data: [DONE]`; without streaming they are `409 login_expired`, `409 vendor_limited` or `502 could_not_start`.

### ChatGPT sign-in on the person's device

On Desktop (through Gizzi Code, the engine under it), the iPhone app and Gizzi Code, ChatGPT uses OpenAI's open-source Sign in with ChatGPT on the device. Nothing is sent to cloud-api: the tokens stay in the device's keystore and chat goes from the device to OpenAI. The Desktop runtime's `chatgpt` row (`runs_on: "computer"`) starts the sign-in with `login.kind` `browser_redirect` and reports its status. The disclosure text shows before the first connect, and the acceptance is recorded on the device. Model ids are `chatgpt/<model>`, separate from `plan/chatgpt/<model>`. A usage limit from OpenAI shows as **Needs you · ChatGPT limit reached**. These models follow the same person-only, chat-only, no-tools rules.

### Plan chat store

Chats with plan (`plan/<vendor>/<model>`) and Copilot (`copilot/<model>`) models are saved on cloud-api so they sync across the person's devices with no computer. The turn itself goes to `POST /v1/chat/completions`; afterwards the client saves the person's message and the reply here. These routes need a signed-in session (an API token gets `403`, none gets `401`), are scoped to that person (another person's thread is `404`), never need a computer, and are erased with the account.

| Call | Body | Returns |
| --- | --- | --- |
| `POST /api/v1/plan-threads` | `{ "model": "plan/claude/sonnet", "title"?: string, "messages"?: [msg] }` | `201` with a summary |
| `GET /api/v1/plan-threads` | none | `{ "threads": [summary] }`, newest first, at most 200, no messages |
| `GET /api/v1/plan-threads/{id}` | none | The summary plus `messages` |
| `POST /api/v1/plan-threads/{id}/messages` | `{ "messages": [msg] }`, 1 to 50 | `200` with the summary |

- `msg` is `{ "role": "user" | "assistant" | "system", "content": string, "model"?: string }`. Content is up to 200,000 characters. Any other role, such as `tool`, is `400`. A stored message also has `at`, an ISO 8601 UTC time set by the server.
- A summary is `{ "id", "title", "model", "message_count", "created_at", "updated_at" }`. Ids start with `pth_`.
- `model` on create must be a `plan/…`, `plan-…` or `copilot/…` id, otherwise `400`. A title is cut to 200 characters. A thread holds at most 5,000 messages.
- Deleting a thread is not in this version.

### GitHub Copilot

`copilot` is a server row that signs in with a GitHub App (`allternit-copilot-connect`) user token. It is `available: true` only when the server has `ALLTERNIT_COPILOT_CLIENT_ID`, `ALLTERNIT_COPILOT_CLIENT_SECRET` and `ALLTERNIT_CREDENTIALS_KEY` set. Without them it stays "Coming soon." and `connect` returns `409 not_available`. It carries `person_only: true` and no `disclosure`; the GitHub consent screen is the consent.

| Call | Notes |
| --- | --- |
| `POST /api/v1/connections/copilot/connect` | Body `{ "return_to"?: string }`. `return_to` must start with `https://ai.allternit.com/`, `https://m.allternit.com/`, `allternit://` or `gizzi://`, otherwise `400`. Returns an `oauth` login. |
| `GET /api/v1/connections/copilot/callback?code&state` | GitHub's redirect. No session header; the signed `state` identifies the account. Always answers `302` to the return URL with `connected=copilot`, or with `error=` one of `bad_state`, `denied`, `exchange_failed`, `no_copilot`, `could_not_start`, `not_configured`. |
| `GET /api/v1/connections/copilot/login` | `pending` while the sign-in is open, `done` once the row is `on`, `failed` when it needs you. |
| `DELETE /api/v1/connections/copilot` | `204`. Revokes the grant at GitHub (best effort) and deletes the stored tokens. |

`no_copilot` means the GitHub account has no Copilot; the grant is revoked and nothing is stored. While `on`, `found` is "GitHub · @login" and `models` are the account's Copilot chat models as `copilot/<id>`, read once at sign-in. The row is `needs` with `login_expired` when GitHub refuses the refresh token. The tokens are stored encrypted with `CredentialCipher` and erased with the account.

Chat uses `POST /v1/chat/completions` with a `copilot/<model>` id and `X-Allternit-Turn: person`. The same refusals apply as for plan models (`plan_person_only`, `plan_no_tools`, `plan_rate` at 20 turns in 5 minutes, `plan_turn_in_flight`, `plan_not_connected`). Copilot adds `409 login_expired`, `409 vendor_limited`, `400 model_not_available` and `502 could_not_start`. Copilot turns are not metered, and tools are off.

## Route telemetry: GET /v1/routes

`GET /api/v1/subscriptions/gateway/v1/routes` is the route router view described in [Subscription gateway › Route router](/api/subscription-gateway#route-router). Each route row can carry a `telemetry` object:

```json
{
  "route": "iphone-app-ictrl",
  "eligible": false,
  "signedIn": true,
  "online": true,
  "contract": { "passed": [], "failed": ["chat.start_continue"] },
  "telemetry": {
    "lastOkAt": "2026-10-18T09:12:44.000Z",
    "lastUsedAt": "2026-10-18T09:12:44.000Z",
    "latencyMs": 4210,
    "successRate7d": 0.92,
    "tasks7d": 25,
    "reliability": "best_effort"
  }
}
```

| Field | Meaning |
| --- | --- |
| `lastOkAt` | When a task turn last finished (`success` or `partial`) or a lane probe last passed on this route. `null` when neither has happened in the last 7 days. |
| `lastUsedAt` | When a task turn or lane probe last ran on this route, whatever the result. `null` when none ran in the last 7 days. |
| `latencyMs` | Median time to a reply over the last 7 days: task turns when there are any, otherwise lane probes. `null` with no data. |
| `successRate7d` | Finished task turns divided by all task turns in the last 7 days, from 0 to 1. `null` when there were no turns. |
| `tasks7d` | Task turns in the last 7 days. `0` when there were none. |
| `reliability` | How the route reads the app: `exact` (its own written adapter), `structured` (a generic accessibility reader), or `best_effort` (generic screen reading, such as a linked phone with no written adapter for the app, or the USB Agent). Absent when nothing serves the route. |

The numbers are computed when the request is read, from the gateway's `task_attempts` and `canary_runs` tables, for the adapters that implement the route. Nothing is estimated: a route with no rows behind it gets `null`s and `tasks7d: 0`. `telemetry` is left out entirely when nothing serves the route (no adapter and no linked phone), so the UI never shows a row of zeros for a way that doesn't exist.

"Used first" in the UI is the vendor's `boundRoute`, and "Pin" is `PUT /v1/routes/:vendor/override` with `{ "route": "<id>" }` (clear it with `{ "route": null }`). A pin must be eligible, otherwise `400 route_not_eligible`.

On the web, cloud-api answers the same path itself and does not relay it, so ai.allternit.com and the PWA get the current catalog even when the paired computer runs an older runtime.

## Coding tools: GET /api/v1/providers/auth/status?kind=cli

The Coding tools tab lists only CLI brains. `kind=cli` limits [`GET /api/v1/providers/auth/status`](/api/providers) to CLI rows; each row has its `status` (`not_installed` when the binary isn't on the computer) and an `install` object `{available, requiresTerms, license, termsUrl, pin}`. Local models are listed under Settings → Models and API-key providers under Settings → API Keys, so they are not in this response.

## Desktop IPC: phone-link:open-app and phone-link:check-app

Allternit Desktop exposes two calls on `window.allternit.phoneLink` for the connect wizard. Both take the linked phone's `deviceId` (from `phoneLink.devices()`) and the app's catalog id (`id` in `surfaces/allternit-desktop/src/main/phone-app-catalog.json`, such as `chatgpt` or `slack`). On web, the phone layout and the PWA, and on older Desktop builds, the functions are absent; the wizard checks for them first.

```ts
interface PhoneLinkAppResult {
  ok: boolean;
  signedIn: boolean | null;          // null = the screen didn't show either way
  account?: string | null;           // an email or @handle the app plainly shows
  error?: { code: string; message: string; retryable: boolean };
}

window.allternit.phoneLink.openApp({ deviceId, app }): Promise<PhoneLinkAppResult>;
window.allternit.phoneLink.checkApp({ deviceId, app }): Promise<PhoneLinkAppResult>;
```

- **`openApp`** (IPC `phone-link:open-app`) opens the app on the phone so the person can sign in there. It maps the catalog id to the iPhone bundle ids (`ios`) or Android packages (`android`) and launches through the same Phone Link lane as the `phone.open_app` bot tool (iCTRL `launch_app`). It always answers `signedIn: null`.
- **`checkApp`** (IPC `phone-link:check-app`) opens or foregrounds the app, waits for it to draw, reads its screen through the same path as `phone.screen_text` (falling back to `phone.read_ui`), and decides:
  - `false` when a sign-in screen is showing: a whole label such as "Sign in", "Log in", "Sign up", "Create account" or "Continue with Google". This wins over everything else, because some apps show their main screen and a "Log in" button while signed out.
  - `true` when the app's main screen is showing: for the AI chat apps (catalog category `AI chat`), the chat composer ("Message ChatGPT", "Ask anything", "New chat"); for other apps, main-screen labels for their category (for example "Inbox" for email, "Direct messages" for chat apps), or a "Sign out" / "Log out" control.
  - `null` otherwise. It looks a second time before answering `null`.

  `account` is an email address or an `@handle` that is shown on the screen, only when `signedIn` is not `false`; otherwise `null`. The result is saved on the phone's cached app list, so `phoneLink.devices()` reports the app's `signedIn` until the next check.

Both calls are read-only on the phone beyond opening the app: they never type, never tap a sign-in button and never read a password field. The code is in `surfaces/allternit-desktop/src/main/phone-app-signin.ts`.

| `error.code` | When | `retryable` |
| --- | --- | --- |
| `invalid_args` | `deviceId` or `app` missing. | no |
| `device_not_found` | The phone isn't linked to this computer. | no |
| `unknown_app` | The id isn't in the catalog, or the app has no build for this phone's platform. | no |
| `not_installed` | The app isn't installed on the phone. | no |
| `device_locked` | The phone is locked ("Unlock your phone."). | yes |
| `device_offline` | The phone doesn't answer at its saved address. | yes |
| `pairing_invalid` | The phone no longer accepts this computer's key. Pair it again in Settings → Connections › Setup. | no |
| `accessibility_off` | Android: Phone Link's accessibility service is off, so it can't read or tap the screen. The message says to turn it on in Settings › Accessibility › Allternit Phone Link on the phone, or to run Phone Link setup again. | no |
| `helper_not_responding`, `developer_image_remount_required`, `signature_renewal_required` | The phone's health state, with the same wording as Settings → Connections › Setup. See [Phone Link › Health](/guides/phone-link). | per state |
| `phone_failed` | The phone answered with an error. The message is the phone's own error. | yes |

`not_installed` is reported only when the phone's own app list doesn't have the app, or every launch attempt said the app is missing. Other launch failures (accessibility off, locked, offline, or the phone refusing to start the app) come back as their own code and message.

## Desktop IPC: phone-link:read-account

`window.allternit.phoneLink.readAccount({ deviceId, app })` (IPC `phone-link:read-account`) checks any catalog app on a linked phone: whether it is signed in, which account, and the plan and usage windows when the app shows them. Like the wizard calls, it is absent on web, the phone layout, the PWA and older Desktop builds.

```ts
interface PhoneLinkAccountResult {
  ok: boolean;
  signedIn?: boolean | null;         // false = the app opened on its sign-in screen; absent on failures
  account: string | null;            // the person's email, @handle or name, by the app's account rule
  plan: string | null;               // "Free", "Plus", "Pro", "Max", "SuperGrok", "Moderato", …
  usage: {
    windows: Array<{
      id: string;                    // "five_hour", "current", "weekly", "weekly_opus", "daily", "monthly", "messages"
      label: string;                 // "5-hour", "Weekly", "Weekly (Opus)", …
      remaining_pct: number | null;  // 0–100
      resets_at: string | null;      // ISO time
    }>;
    observedAt: string;              // ISO time of the read
  } | null;
  error?: { code: string; message: string; retryable: boolean };
}

window.allternit.phoneLink.readAccount({ deviceId, app }): Promise<PhoneLinkAccountResult>;
```

How it reads:

- Every read starts with the sign-in check (`classifySignIn` on the app's first screen, one more look while it is still drawing). A sign-in screen ends the read with `signedIn: false`, and the app record's account, plan and usage are cleared.
- Apps with navigation specs in `surfaces/allternit-desktop/src/main/phone-account-specs.ts` then walk them. A spec is a list of paths; each path is a series of taps, each with candidates: a whole label, `id:<accessibility or resource id>`, or `re:<pattern>` for a label that carries the person's name (Discord's "`<name>`, Online"). A tap step with `scroll: n` swipes up at most n times looking for its row. A path marked `verifiedOn: 'ios' | 'android'` was walked on a real phone; once a platform has verified paths for an app, only those run there. Verified paths start with optional Back / Close taps, because an app reopens on the screen it was left on. An app without a spec gets only the sign-in check.
- Each spec has an `account` rule list: `email`, `handle` (a whole-label @handle), `match` (a pattern), or `after` / `before` an anchor label. Feed apps use their own rule so other people's handles and emails on a feed are never taken. Without rules (the AI chat apps), the first email, else a whole-label @handle.
- When a tap leaves the top of the screen unchanged (some apps ignore an accessibility click, LinkedIn's profile button), the reader taps once more where the element's label shows. A required tap step that finds nothing waits and looks once more; an empty read gets two more looks while the screen draws.
- Android tree lines end with flags after the bounds (`, clickable long-clickable`); both parsers accept them.
- Taps go through `phone.find_and_tap` with exact matching, and only to an element whose whole label or id is a spec candidate. A label that is only visible text, with no element (Telegram's tab bar, TikTok while its element tree is busy), is tapped at the text's position with `phone.tap`. A deny-list is checked before every tap: anything matching sign out, log out, delete, remove, upgrade, buy, subscribe, cancel, billing, payment, manage subscription, reset or sign in is never tapped, and neither are switches, toggles, check boxes or sliders. Nothing is typed.
- The reader always ends with Home, even after a failure. On Android it also steps back out of each path it tried.
- Parsing is in `phone-account-reader.ts` and never guesses. `account` is a visible email or @handle. `plan` is a known plan name for that vendor, shown as "ChatGPT Plus", "Max plan" or "Plan: Pro", or as a one-word name right after a "Plan" or "Subscription" label. A screen that shows two different plans, such as a plan comparison, gives `null`. Usage windows come from a header such as "Current session" or "Weekly limits", followed by "34% used" (`remaining_pct` 66), "66% left" or "12 of 40 messages left", and "Resets in 2 hr 10 min" or "Resets Thu 9:00 AM". The reset time is turned into ISO in the computer's local time. Anything else is `null`.

A read that saw anything is saved on the phone's app record; a read that saw nothing keeps the last account, plan and usage and only updates `signedIn`. `phoneLink.devices()` then returns `signedIn`, `account`, `plan`, `usage` and `accountCheckedAt` on each app in `apps`, plus `reader: 'verified'` on apps with a path verified on that phone's platform (the drawer shows **Verified reader**).

Desktop also checks apps in the background (`PhoneAccountScheduler`), kept rare because each check opens the app on the phone: every app once when it is first seen (no `accountCheckedAt` and `signedIn: null`), signed-in AI chat apps (catalog category `AI chat`) again every 6 hours for their usage windows, and an app right after the wizard's **Check** finds it signed in. Other apps are never re-read on a timer. A timed or first check runs only after the phone has sat on its Home screen for 4 minutes (`onHomeScreen`: the iPhone tree has no `Application` root, an Android window belongs to a launcher package), on a phone that works (`HEALTHY`, or `SIGNATURE_RENEWAL_REQUIRED` while the signature hasn't lapsed), that no bot used in the last 10 minutes and whose live screen isn't open. A check right after the wizard skips the Home-screen wait. One app is checked at a time.

| `error.code` | When | `retryable` |
| --- | --- | --- |
| `phone_busy` | A bot is using the phone, or someone is watching its live screen. The read stops before it starts, or between steps. | yes |
| `accessibility_off`, `device_locked`, `device_offline`, `pairing_invalid`, `not_installed`, … | As for `checkApp` above. | as above |

An `ok: true` result with `null` fields means the app opened, but the reader couldn't find those facts on the screens it reached.

## Health state ACCESSIBILITY_OFF

`phoneLink.devices()` reports `health.state: 'ACCESSIBILITY_OFF'` for an Android phone whose Phone Link app answers but whose accessibility service is off. The probe sees this from `device_info` (`system.accessibility_enabled: false`) or from `is_locked` failing with the helper's "accessibility service is not running" error. A screen read that fails this way also sets it, for 5 minutes or until a read succeeds. Its `recovery` is `manual`, and its `action` tells the person to turn on **Allternit Phone Link** in Settings › Accessibility on the phone, or to run Phone Link setup again. On iPhone, a runner that answers but can't read the screen is reported as `HELPER_NOT_RESPONDING` in the same way.
