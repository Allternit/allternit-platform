## Overview

`allternit-desktop` (`@allternit/desktop`, in `surfaces/allternit-desktop`) is the Electron shell that bundles the whole stack so it runs locally out of the box: the workspace web UI, the Rust `allternit-api` server, `gizzi-code`, and supporting services (mux, voice, connector sidecar, office engine, computer-use driver). You can also point it at your own Allternit instance. See [BYOC overview](/byoc/overview).

The workspace UI is a Vite + React app built from the separate `allternit-ai` repository. `scripts/prepare-platform-static.cjs` packages its static export into the app; set `ALLTERNIT_AI_PATH` to build against a specific checkout.

## Build and package

```bash
npm run build:electron       # full packaged build (stages platform static, office add-ins, api binary, sidecars)
npm run build:electron:dmg   # same, DMG target
```

`build:electron` runs `prepare:*` steps first (platform static, computer-use driver, ACU gateway, Lima, Lume, mux, mesh node, office engine, API binary, connector catalog and sidecar) and `verify:packaged-resources`.

### macOS signing

There is no Apple Developer ID yet, so Mac builds are ad-hoc signed (`mac.identity: "-"` in `package.json`) and not notarized. Don't set the identity back to `null`. A `null` identity skips signing, so only the main binary keeps the linker's signature and the bundle has no sealed resources. macOS then reports a downloaded copy as **damaged** and offers only Move to Trash, which is what 1.1.8 and earlier did. An ad-hoc build gets the normal "Apple could not verify" prompt with **Open Anyway** instead (see [Installing on a Mac](/quickstart#installing-allternit-desktop-on-a-mac)).

Two rules keep the seal valid:

- **No dangling symlinks in the bundle.** Signing fails on them. The ACU gateway therefore does not ship a venv, because a venv links to the build machine's Python. `prepare:acu-gateway` installs its packages per target into `resources/computer-use/acu-site/<os>-<arch>`, which is packaged as `computer-use/acu/site-packages`. The gateway runs on the bundled driver Python with that folder on `PYTHONPATH` (`bundledAcuPython` in `src/main/acu-gateway-manager.ts`).
- **Nothing writes inside the installed app.** The packaged app sets `PYTHONPYCACHEPREFIX` to `<userData>/pycache` at startup, so the bundled Pythons don't write `__pycache__` into `Contents/Resources`.

**Keychain prompt after each update.** macOS ties a Keychain item's **Always Allow** to the app's exact code, and every ad-hoc build has new code. So after each app update, the first launch asks for the Mac password to use **Allternit Desktop Safe Storage**. `safeStorage` reads run on the main process and wait for that answer, so until the user answers, the app does not respond: startup stops after the backend comes up, and Quit times out. The prompt often opens behind other windows. If a Mac build hangs right after an install, check for it first (`pgrep SecurityAgent`, or `sample <main pid>` showing `SecItemCopyMatching` on the main thread). A stable signing identity would end this.

**No in-app app updates.** `update-electron-app` (update.electronjs.org) cannot update these builds. On macOS, Squirrel.Mac needs the new app's signature to match the old one, which ad-hoc signing never does. On Windows, the service serves Squirrel.Windows packages, and Desktop ships an NSIS installer. New app versions come from Homebrew (`brew upgrade --cask allternit`) or a fresh download. Runtime packages (below) still update the parts inside the app.

Check a build with `codesign --verify --deep --strict "Allternit Desktop.app"`. Proper notarization needs a Developer ID certificate and the `APPLE_ID`, `APPLE_ID_PASSWORD` and `APPLE_TEAM_ID` secrets (`scripts/notarize.cjs`).

## Cloud sign-in

Desktop holds two sign-ins. The **device pairing** (a runtime token) keeps the computer linked to your account. The **cloud sign-in** (a Clerk session) is what cloud features such as artifacts use. Desktop renews the cloud sign-in in the background from a hidden sign-in window. When the Clerk session itself has ended, the background renewal can't work, and cloud views show **Sign in to see your artifacts**.

Press **Sign in** there. A sign-in window opens; sign in with the account this device is paired to and the list loads. The device stays paired, so nothing has to be set up again. Signing in with a different account is refused and names the right one.

For developers: the renderer calls `window.allternit.auth.reconnectCloud()` (IPC `auth:reconnect-cloud`, `AuthManager.reconnectCloud` in `src/main/auth-manager.ts`). It returns `{ ok: true }` or `{ ok: false, error }`. The account check is `cloudAccountMismatch` in `src/main/cloud-account.ts`. On the web and in older Desktop builds, `signInToCloud()` (`allternit-ai/src/lib/cloud-sign-in.ts`) falls back to `/sign-in` or the full device sign-in.

Cloud calls carry only the Clerk bearer (and `X-Allternit-Tenant-Id`). `buildAuthHeaders(targetUrl)` adds the Desktop identity headers (`X-Allternit-User-Id`, `X-Allternit-User-Email`) only for the app's own origin and the loopback runtime: api.allternit.com reads identity from the JWT, and its CORS preflight refuses those headers, which made every direct cloud call fail as if offline. Pass the request URL when calling it for a cloud route.

**When the cloud can't be reached.** The local API checks the device token with api.allternit.com (`verify_runtime_device_token` in `cmd/allternit-api/src/connector_routes.rs`). If the cloud can't be reached (no network, DNS failure, a 5xx or 429), it uses this device's last successful check instead, for up to 7 days, so Desktop keeps working on your own files. The last check is kept in `device-identity-cache.json` in the data folder, keyed by a SHA-256 of the token (never the token itself). A token the cloud rejects is refused straight away; the saved check never covers a rejection.

## Code mode panes

The **Panes** menu at the top right of a Code session lists Terminal, Changes,
Browser, Computer, Files, Artifacts, Transcript, Tasks and Code map. A new session opens
with Terminal.

- **Pick a pane** to show it in place of the one you're using. Picking a pane
  that's already open (checked) closes it.
- **Open beside** opens a pane as its own card next to the others. Each card
  docks left, right or bottom, resizes, and can open in a new window from its
  own menu.
- Opening a file from the console's Problems tab switches to Files.
- **Changes** shows the session folder's uncommitted work: changed files and
  new (untracked) files, with line counts. It reads `POST /api/v1/git/diff` on
  the local API (`cmd/allternit-api/src/git_routes.rs`).
  - **Edit** (pencil) turns that file's diff into an editor in place. Save
    with ⌘S or **Save** and the diff comes back updated. **Open beside** opens
    it in the Files pane instead.
  - **Undo** on a block of changes puts just that block back. **Undo all
    changes** on a file puts the whole file back to its last saved-in-git
    version; for a new file it deletes the file, after you confirm.
  - Both use `POST /api/v1/git/discard` (`{ path, file, patch?, untracked? }`):
    with `patch` it reverses one hunk after `git apply -R --check`; without it
    runs `git checkout -- file`, or deletes an untracked file only when
    `untracked: true`.

- **Code map** opens on the file the agent is working on, with what it
  uses, what uses it and what a change could break, like the dependency map;
  **Whole repo** draws every file by import graph. Files the agent reads show
  blue and edits show coral; click a file to centre on it or open it in Files. A line under the chat shows how much of the repo map the last
  prompt carried. See [Live code map](/cli/code-intelligence#live-code-map).

- **Panels** lists the project's own panels, the files in
  `.allternit/panels/`: ops sheets and MCP Apps the project keeps with its
  code. See [Project panels](/guides/project-panels).

On a phone, each pane opens full screen from the header's pane menu.

Code: `allternit-ai/src/views/code/pane-manager/` (`switchPane`, `openPane`).

The rail's Code session list, its row menu and shortcuts are in [Code session list](/guides/code-session-list). Pull requests a session opens show on its row; see [Linked pull requests in Code](/guides/code-linked-prs).

## Replies that stop streaming

A session shows **Working** while its reply streams in. If the stream goes
quiet for 30 seconds, or you open a session that still says Working, the app
checks the saved conversation. When the agent's reply is already finished
there, the session stops showing Working and shows the saved reply. A turn
that is still running is left alone. This covers a reply stream lost across a
Desktop restart; the turn itself still runs and saves normally.

Code: `allternit-ai/src/lib/agents/mode-session-store.ts` (`reconcileStream`,
`serverTurnFinished`).

## Quitting with work in progress

When Desktop quits, it hands work that has **started** (a cowork job that is
leased or running) to the cloud continuation so it can finish. Idle Cowork
sessions and queued jobs stay on this computer and are picked up again on
the next launch; they are not sent to the cloud.

Code: `handoffInFlightToCloud` in `surfaces/allternit-desktop/src/main/unified-main.ts`
calls `POST /api/v1/fabric/transport/continuation/handoff-all`, which runs
`handoff_all_in_flight` in `allternit-cowork-runtime/src/sqlite_store.rs`.

## How this relates to the Agency Kernel

## Runtime updates

The app itself updates by installing a new version (Homebrew or a download, see [macOS signing](#macos-signing)). The parts inside it (the local API, Gizzi, the factory and the screens) update separately and more often, as a signed **runtime package** from runtime.allternit.com. Desktop checks a minute after it starts, then every 6 hours. **Check for updates** in the app menu also checks the runtime. A downloaded update is installed the next time Desktop starts.

- Only files that changed are downloaded, and the rest are copied from what is already installed.
- If a download stops partway (a slow connection, quitting the app), the next check carries on from where it stopped instead of starting over.
- A failed check tries again after 1, 5, 15 and then 60 minutes.
- It also checks when the local API fails to start, because an update may be the fix.

For developers (`surfaces/allternit-desktop/src/main/runtime-package.ts`, scheduling in `unified-main.ts`):

- `fetchToFile` aborts an object after `STALL_MS` (60 s) with no bytes, or when it runs below `MIN_BYTES_PER_SEC` (16 KB/s) after 20 s, and retries 3 times. Each retry is logged as `[Runtime] retrying`.
- `stageDelta` downloads through a pool of 8, logs `[Runtime] downloading n/total` every 10 s, and writes each object to `*.download` before renaming it into place.
- A `<version>.partial` folder survives a failure or quit, and `prune` keeps it. The next check for the same version counts complete files as done. The final deep verify still hashes every file.
- `latest.json` and its `.sig` are published one after the other. A mismatched pair is read again once after `feedRetryMs` (5 s).
- `checkRuntimeNow` backs both the schedule (`RUNTIME_RETRY_MS` backoff) and the manual check. `main.log` keeps 10 MB, so `[Runtime]` lines survive.

**Quitting.** Quick Chat hides instead of closing, except while the app quits. Crash reports use a non-blocking dialog. Once quit cleanup has run, a second quit exits at once, so nothing can hold the app open.

Desktop hosts the Allternit API and Gizzi runtime locally. It is not part of the [Agency Kernel](/architecture); the kernel's Agency API is a Cloud API surface. See [Architecture](/architecture).

## Run line

Under the latest reply, the run line shows what the run took: the model, time, tokens in and out, tool calls, **failed** tool calls (in red, when any failed), cost, context used and the cache state. Click it for the full breakdown.

In Code it stays in view, because it is part of reading the run. In Chat, Cowork and bot chats it appears when you hover or focus the reply's footer. On touch screens (the phone layout and the m.allternit.com app) it is always shown, since there is no hover.

For developers: `RunTelemetry` (`src/components/chat/RunTelemetry.tsx`) renders the line from the message's `metadata.telemetry` (`toolCalls`, `toolFailures`, `usage`). `StreamingChatComposer` takes `runLine: 'hover' | 'always'`; `CodeCanvas` and `CodeCanvasTileSession` pass `'always'`. The hover wrappers (also in `RunFooter`) add `[@media(hover:none)]:opacity-100`. In bot chats, `RunFooter` wraps the run line and `RunStrip` as one line that grows in height (`min-h-5`, not a fixed `h-5`, which clipped wrapped lines into the composer on phones); beside the run line `RunStrip` takes `besideSummary` and shows only tok/s and kernel fields, since time, tokens and cost are already in the run line. Items never break inside themselves (`6 in / 556 out` stays together); the line wraps between them.

## Prompt-cache countdown

After a cache-bearing response, Gizzi Code shows a separate cache row under
its model/context footer. Desktop and the web/phone/PWA workspace show the
same indicator inside the latest reply's post-run orb telemetry, alongside
time, tokens, and cost. Clicking the telemetry also includes a Cache row in
the details. Existing custom
status-line commands are preserved.

The row updates every 30 seconds without sending a model request. Green means
warm, amber means less than 20% of the TTL remains, and red means the estimated
TTL has elapsed. The block bar shows time remaining. `last hit` is the share
of the latest request's input read from cache, not a session-wide hit rate.
When cold, `may re-cache` shows the latest reported input footprint.

Expiry is an estimate from the request TTL, not a guarantee that the provider
still holds the cache. Changes to model, tools, or context may invalidate it
earlier. Unknown provider TTLs have no countdown. Native requests with a known TTL
currently use five-minute ephemeral markers; Gizzi's interactive cache path
uses its configured five-minute or one-hour TTL. No keepalive requests
are sent. Miss counts and causes are omitted when not reported.

## Mode controls and rail selection

Use the floating mode icons to switch between Home, Bots, Code and ACI. Scroll over the mode wheel to cycle through modes, or hover or focus it to reveal the other modes. The selected mode and rail tab have a translucent glass highlight with a fine Allternit double-slash detail. Icons respond to hover and press; keyboard focus stays visible. Motion and transparency follow your system accessibility preferences.
