## Overview

`gizzi exec` is a pipe-safe, non-interactive alias for `gizzi run`. It prints the response and exits without launching the TUI — ideal for scripts, CI pipelines, and shell automation.

Both exit as soon as the run finishes. When the model is an installed coding CLI, the run serves its session tools to that CLI on a loopback port (`--port` picks it; a free port by default). `gizzi run --attach <url>` sends the run to an already running `gizzi serve` instead.

## Basic usage

```bash
# Single prompt
gizzi exec "Write a commit message for the staged changes"

# Pipe input from another command
git diff --staged | gizzi exec "Summarize these changes"

# Explicit command with piped context
cat error.log | gizzi exec "Diagnose the root cause"
```

## Output formats

| Flag | Output |
|------|--------|
| *(default)* | Plain text response |
| `--output-format json` | JSON response object |
| `--output-format stream-json` | Streaming JSON event objects, one per line |

```bash
gizzi exec --output-format stream-json "List the top 5 TODO items in this repo"
```

Each `stream-json` event is a JSON object with a `type` field (`message`, `tool_use`, `result`, etc.), suitable for piping into `jq` or another tool.

## Permission modes

In headless mode, `exec` defaults to the `dontAsk` permission mode — commands and edits run without interactive confirmation.

Override with a named profile:

```bash
gizzi exec --permission-profile strict "Refactor the auth module"
```

See [Permission Profiles](/cli/permission-profiles) for profile syntax.

## Piping and composition

Because `exec` is pipe-safe, it composes naturally with standard Unix tools:

```bash
# Summarize and pipe into a notification
gizzi exec "Summarize today's git log" | notify-send "Daily summary"

# Chain multiple agent passes
gizzi exec "Draft release notes from CHANGELOG.md" \
  | gizzi exec "Proofread and tighten the language"
```

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | Agent returned an error or was interrupted |
| `2` | Configuration or authentication failure |
| `3` | `--review`: the reviewer returned **FAIL** |
| `4` | `--review`: the reviewer returned **PARTIAL** (something could not be checked) |

A run whose session pauses before a usage limit (for example the Allternit Cloud free monthly limit) ends at once with exit code `1` and the message `Paused before a usage limit (…) until <date>`. In JSON output it is an `error` event named `SessionPaused`. Run again with `--model` on another provider.

## Review in CI

`gizzi run --review` asks a fresh reviewer to check the uncommitted changes (after the run, or on its own when you give no prompt). The reviewer starts with no knowledge of how the code was written, reads the changed files and their callers, and returns a verdict:

- **PASS** (exit `0`): what it verified.
- **FAIL** (exit `3`): each problem with its file and line.
- **PARTIAL** (exit `4`): what it could not verify and why.

With no changes there is nothing to review: no model is called, the exit code is `0`, and `--format json` reports `"verdict": null`, so a pipeline never mistakes "nothing reviewed" for "checked and passed".

```bash
gizzi run "Fix the flaky pagination test" --review
gizzi run --review --format json        # review only, JSON line {type:"review", verdict, review}
gizzi run --review-until-pass 5          # fix and re-review up to 5 rounds
```

`--review-until-pass [rounds]` sends each non-PASS verdict back to the coder as a turn, then reviews again, until PASS or the round limit (default 5, max 12). The reviewer uses the `review` job model when one is set (see [Configuration](/cli/configuration#models-for-each-job)), else the session's model.
